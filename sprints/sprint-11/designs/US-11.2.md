# Design for US-11.2: Add DoRA training mode to finetune-gemma.py

**Sprint:** 11 | **Priority:** P0 (Wave 0) | **Risk tier:** LOW | **Estimate:** S

## Approach

DoRA in `mlx-lm-lora` is a drop-in replacement for LoRA: the upstream CLI
already accepts `--train-type dora` wherever it accepts `--train-type lora`.
Our wrapper script `scripts/finetune-gemma.py` currently hardcodes
`"--train-type", "lora"` in two places (`run_sft` line 262, `run_dpo` line 507)
and exposes no CLI flag for it. This story is pure **flag plumbing**: add
`--train-type {dora,lora}` to `main()`'s argparse, default it to `dora`, and
thread the resolved value through to both subprocess invocations and into the
`train_config.json` written by the versioning step.

Why this design and not alternatives:

- **Why argparse choice over free-form string?** mlx-lm-lora accepts other
  values (`full`, `prompt-tuning`) we don't want to silently expose; restricting
  to `{dora, lora}` makes the contract explicit and matches AC-11.2.1/.3 exactly.
- **Why default to `dora` (changing the default)?** AC-11.2.2 is explicit:
  *"the default is `dora` (upgrading the prior default of `lora`)"*. Downstream
  P0 stories (US-11.4 DPOP, US-11.5, US-11.8) all assume DoRA is the baseline.
- **Why no separate `--dora` boolean flag?** Two flags (`--train-type` and
  `--dora`) would create ambiguity (what does `--train-type lora --dora` mean?).
  One flag, one source of truth.
- **Why thread through both `run_sft` and `run_dpo`?** Both invocations train
  the same adapter; mixing DoRA-SFT with LoRA-DPO would silently corrupt the
  adapter shape. They must agree.

## Implementation steps (for the implementer agent)

1. **Add the CLI flag** in `main()` argparse block (between `--rank` and
   `--target-modules`, near line 972):
   ```
   parser.add_argument("--train-type", choices=["dora", "lora"], default="dora",
                       help="Adapter type: dora (default, US-11.2) or lora. "
                            "DoRA closes ~93%% of the LoRA-to-full-FT quality gap "
                            "at the same rank with no inference overhead.")
   ```

2. **Replace hardcoded strings** in `run_sft` (line ~262):
   `"--train-type", "lora"` → `"--train-type", args.train_type`
   and in `run_dpo` (line ~507): same substitution.

3. **Thread through synthetic Namespaces** (no defaults — must propagate the
   operator's choice):
   - `run_speculative_draft_training`: add `train_type=args.train_type` to the
     `draft_args = argparse.Namespace(...)` block (~line 585).
   - `run_train_all`: add `train_type=args.train_type` to the `target_args`
     Namespace (~line 893).

4. **Record in train_config.json** (AC-11.2.5) — in `run_finetune`, line ~811,
   add to the `lora_config` dict: `"train_type": args.train_type`.

5. **Write the four tests** in `tests/test_finetune_gemma_dora.py`. Use
   `unittest.mock.patch("subprocess.run")` to capture the argv list passed to
   `mlx_lm_lora.train`; assert positionally.

6. **Smoke-check locally**: `python3 -m pytest tests/test_finetune_gemma_dora.py -v`

7. **Run AC-11.2.4 check**: `bash scripts/check-lora-baseline.sh` against a
   DoRA-produced fixture adapter (or assert it's structurally a no-op for DoRA
   adapters; if the script rejects DoRA, that's a defect surfaced by this story
   and we file it as a follow-up — do NOT modify check-lora-baseline.sh in
   this story unless it actively rejects DoRA adapters).

## Test strategy

All deterministic. Zero real subprocess execution; zero real GPU calls.

| Test | AC | What it does |
|---|---|---|
| `test_default_train_type_is_dora` | 11.2.2 | Run with no `--train-type` flag; mock subprocess; assert `argv` contains `["--train-type", "dora"]` |
| `test_dora_flag_propagated_to_mlx_cmd` | 11.2.1 | Run with `--train-type dora`; assert same; assert it appears in BOTH SFT and DPO calls when `--dpo` is on |
| `test_explicit_lora_flag_respected` | 11.2.3 | Run with `--train-type lora`; assert `argv` contains `["--train-type", "lora"]` and DOES NOT contain `"dora"` anywhere |
| `test_train_config_records_dora` | 11.2.5 | Inspect `train_config.json` after a (mocked) run; assert `train_type == "dora"` |
| `check-lora-baseline.sh` exit 0 | 11.2.4 | CI gate against the DoRA fixture adapter built in a prior CI step or test fixture |

**Mock strategy:** patch `subprocess.run` to a `MagicMock` returning
`returncode=0`; capture `call_args_list[i][0][0]` (the cmd list). Patch
`stop_mlx_server`, `start_mlx_server`, `time.sleep` to no-ops to keep tests
fast and deterministic. For the train_config.json test, the mock for
`subprocess.run` should also touch the expected `adapters.safetensors` file so
the version step doesn't error out — use a `side_effect` that writes a stub.

**Size guard (AC-11.2.4):** the check-lora-baseline.sh script asserts the
adapter is loadable. DoRA adds magnitude vectors (≈2-3% more params per rank).
Adapter file size for the e4b target was ~17MB pre-DoRA; expect ~17.5MB post.
If `check-lora-baseline.sh` has a hard size ceiling, the implementer will need
to bump it by 5%. Document this in the PR description if it triggers.

## Risks

- **Backward compat / silent default change (MED probability / SMALL impact):**
  changing the default from LoRA to DoRA will produce a different adapter shape
  than prior runs. Any operator with an `adapters.safetensors` in
  `~/.human/training-data/adapters/seth-lora/` from a prior LoRA run who passes
  `--resume` will hit a shape mismatch. *Mitigation:* the `--resume-adapter-file`
  path in `run_sft` is only hit when `args.resume` is set. We accept this
  break; mlx-lm-lora will surface a clear shape-mismatch error. Document in the
  PR body that operators with prior LoRA adapters should either delete them or
  pass `--train-type lora` to retain old behavior.

- **DoRA memory footprint (LOW / SMALL):** DoRA adds 2-3% trainable params over
  LoRA. At rank 32 on Gemma-31B with our defaults this is well below the memory
  headroom margin on M-series Macs. *Mitigation:* none required for this story;
  if memory pressure surfaces post-merge it's a separate tuning task (lower
  `--num-layers` or `--rank`).

- **`check-lora-baseline.sh` may reject DoRA adapters (LOW / MED):** the script
  may pattern-match `adapter_config.json` for `"peft_type": "LORA"` or assume a
  LoRA-only field shape. *Mitigation:* the implementer should read the script
  before claiming AC-11.2.4 passes; if it does reject, surface as a blocker
  rather than silently editing the gate.

- **Concurrency / data integrity:** none. This is single-process flag plumbing.
  No shared state.

- **Observability:** the existing `run_finetune` print block (lines 753-780)
  prints `args.target`, `args.rank`, etc. Add `Train type: {args.train_type}`
  to that block so operators see at-a-glance which mode is active.

## Sequencing

1. Add the argparse flag (no behavior change yet — default unused).
2. Add the 4 unit tests (all should FAIL because hardcoding still wins).
3. Replace the 2 hardcoded `"lora"` strings; thread through synthetic Namespaces.
4. Add `train_type` to `lora_config` dict.
5. Re-run pytest — all 4 should now PASS.
6. Add the observability print line.
7. Run `scripts/check-lora-baseline.sh` against a real DoRA fixture adapter
   (or document why it's not available in this worktree and defer to CI).
8. `/verify` to confirm; commit; PR.

Each step is reversible and individually testable.
