# Design for US-11.10: Twin-2K-500 forced-choice secondary metric

**Sprint:** 11 | **Priority:** P2 (Wave 3; stretch) | **Risk tier:** MEDIUM | **Estimate:** M
**Depends on:** US-11.6 (twin-eval command with `--protocol` mode-switching and a working `hu_ml_nll_compute_fn_t` seam)

## Approach

US-11.6 ships the primary `human ml twin-eval` command computing held-out
next-utterance NLL on chat.db (YNTP protocol). US-11.10 adds a **second
protocol mode** to that command that scores the model on a **hand-curated
50-prompt forced-choice set** in the Twin-2K-500 style (arXiv 2505.17479):
each prompt has N≥2 discrete options A/B/C/D and a single ground-truth choice
(Seth's actual answer). The adapter's prediction is the option with the
highest sequence log-probability under the conditional `p(option | prompt)`;
accuracy is the fraction of items where `argmax` matches `seth_answer`.

**Scoring math (deterministic, MMLU-style):**

```
for item in fixture:
    prompt = item["question"]
    options = item["options"]            # ["A: ...", "B: ...", ...]
    truth  = item["seth_answer"]         # "A" | "B" | "C" | "D"
    # Per-option score: mean log-prob over the option tokens, conditioned on prompt.
    # Length-normalised so longer wording isn't penalised (matches Twin-2K-500
    # protocol §4.2 and US-11.1 length normalisation we already ship).
    scores = { letter: nll_compute(prompt, opt_text) / n_tokens
               for letter, opt_text in options.items() }
    pred = argmax(scores)                # lowest length-normalised NLL wins
    correct += (pred == truth)
accuracy = correct / n_questions
stderr   = sqrt(accuracy * (1 - accuracy) / n_questions)  # binomial SE
```

We run this twice — once with the base model and once with the adapter
loaded — and emit `delta_accuracy = adapter_accuracy - base_accuracy`. The
**same `hu_ml_nll_compute_fn_t` seam** that US-11.6 introduces is reused
verbatim: forced-choice is just N evaluator calls per item, then an argmax.
No new ML wiring.

**Confidence weighting is explicitly out of scope.** AC-11.10.2 specifies
plain binomial accuracy (4/5 → 0.80). Twin-2K-500 §5 reports both plain and
log-prob-weighted accuracy; the literature does not establish that weighting
materially changes ranking. Plain accuracy is the contract; keep it.

**Curating the 50 prompts** (the actual hard part): the fixture
`tests/fixtures/twin2k_seth_50q.jsonl` must be authored manually by Seth in
the Twin-2K-500 schema (`{question, options:{A,B,C,D}, seth_answer}`). Each
prompt should be a **behavioural** question (decision under tradeoff, planning,
strategic choice) — NOT a stylistic/lexical question, since that's what the
YNTP NLL evaluator already measures. The PR for US-11.10 ships the loader,
validator, and scorer; **the fixture itself is gated on Seth's labelling
time** (see Risk #1 and Open Question #1). The story can land with a 10-prompt
demo fixture if 50 is not ready, but the headline metric needs n=50 for the
stderr (~0.07 at p=0.5) to be tight enough to claim a real delta.

Why this design and not alternatives:

- **Why reuse `--protocol` switch instead of a new command?** The two
  protocols share 90% of plumbing (model load, adapter load, fixture
  iteration, JSON-out). A second command would duplicate it. US-11.6's
  design already anticipates protocol dispatch.
- **Why length-normalised log-prob and not raw sum?** Twin-2K options vary
  from 4 to 30 tokens; raw sum biases toward shorter options. This is the
  same length-normalisation US-11.1 ships for the NLL evaluator; reuse it.
- **Why binomial stderr and not bootstrap?** Forced-choice with N=50 is a
  Bernoulli sample; closed-form binomial SE is exact, deterministic, and
  requires zero extra code. Bootstrap is overkill at this scale.
- **Why no per-option logit caching?** N=50 questions × 4 options × 2
  models = 400 NLL calls. With mock seam in tests this is sub-second; on
  real inference (which only runs outside `HU_IS_TEST`) it's still <5 min
  on M-series. Premature optimisation.

## Test plan

- **Determinism:** all 4 tests use the mock NLL seam with hardcoded log-probs;
  re-running produces byte-identical output. Verified by running the suite
  twice in CI and `diff`ing JSON output.
- **Per-choice logprob comparison:** `test_twin2k_accuracy_computation`
  injects per-option log-probs such that the argmax behaviour is exercised
  for every option position (A wins, B wins, C wins, D wins, tie-break).
- **Fixture validation:** `test_twin2k_fixture_validation` walks
  `twin2k_malformed.jsonl` (4 deliberately broken lines) and asserts each
  yields a distinct `HU_ERR_INVALID_ARG` with line number in the error message.
- **No real inference under test:** `test_twin2k_no_real_inference_when_test_guard`
  installs a sentinel weight-loader that aborts if invoked; verifies the
  whole `--protocol twin2k` path runs the mock seam only.
- **Stderr arithmetic:** with synthetic 5-question fixture at adapter
  accuracy 0.80, expected `stderr = sqrt(0.8*0.2/5) ≈ 0.1789` — asserted to
  4 decimal places.

**Suite invocation:** `./build/human_tests --filter=twin_eval_twin2k`
(per AC-11.10's specified command).

## Risk analysis

1. **Fixture curation gates the headline metric** — *MEDIUM probability,
   LARGE impact.* 50 behavioural questions requires Seth's manual labelling
   time. Each question needs a real-life tradeoff plus 3-4 plausible
   distractors plus Seth's genuine choice. Realistic budget: 2-3 hours of
   focused work, NOT a 15-minute task. If Seth doesn't commit time before
   Wave 3 starts, the metric ships with a 10-question demo fixture and
   `stderr ≈ 0.16` swamps any plausible `delta_accuracy`, making the result
   uninformative. **Mitigation:** Open Question #1 must be answered BEFORE
   the implementer is dispatched; if "no time", we ship code + 10-q demo
   fixture and defer the 50-q labelling to Sprint 12, flagging this in the
   sprint retro. Do not block US-11.6 / US-11.7 on this.

2. **MMLU-style scoring may not capture nuance** — *MEDIUM probability,
   MEDIUM impact.* Forced-choice multiple-choice over length-normalised
   log-prob is a known-noisy signal: small wording changes in options can
   flip the argmax (Hendrycks et al. 2021; Robinson et al. 2023 on
   "permutation sensitivity"). At n=50 with binomial stderr ≈ 0.07, a real
   adapter improvement of <0.10 may not clear the noise floor.
   **Mitigation:** (a) accept this as a known limitation of the secondary
   metric — the primary (YNTP NLL from US-11.6) is the headline; (b) the
   AC requires *reporting* delta accuracy, not *passing a threshold*, so
   the noisy signal is documented but not weaponised; (c) optional
   follow-up in Sprint 12: add the Twin-2K-500 "option-letter shuffle"
   robustness check (average over 4 shuffles).

3. **Depends on US-11.6** — *LOW probability of US-11.6 slipping at this
   point in the sprint, MEDIUM impact if it does.* US-11.6 is P1 Wave 1
   and provides both the `twin-eval` CLI surface and the
   `hu_ml_nll_compute_fn_t` seam. If US-11.6 lands without the
   `--protocol` switch (i.e. hardcodes YNTP), we have to retrofit it
   in this story (+30 LOC, +1 day). **Mitigation:** the US-11.6 design
   doc (sibling design under `sprints/sprint-11/designs/US-11.6.md`)
   must explicitly call out the `--protocol` enum and the seam being
   reused here. Coordinate at design-review time.
