**Sprint:** sprint-11-sota-twin
**Story:** US-11.6 — `human ml twin-eval --protocol yntp`
**Risk tier:** HIGH (primary sprint metric; user-derived fixture; new C CLI subcommand + Python NLL backend; gates publishable claim)
**Author:** tech-lead
**Status:** READY FOR IMPLEMENTATION
**Builds on:** Sprint 7 US-7.6 (dormant `hu_ml_nll_compute_fn_t` seam in `src/ml/fidelity.c`)

## 1. Approach

### 1.1 What the story actually is

Sprint 8's "+0.019 lexical delta with 40% pad-leakage" smoke run proved that
the lexical-fingerprint metric in US-7.6 baseline is gameable: a broken adapter
that emits pad tokens scored *higher* than a coherent one. US-11.6 replaces
that synthetic metric with **mean per-token negative log-likelihood of real
held-out user continuations**, in the YNTP-100 protocol (arXiv 2510.14398) +
TwinVoice (arXiv 2510.25536) shape, scoped to n=1 user (Seth) with N=30
conversations from `~/.human/memory.db` (verified: 1050 messages).

This is the **ungameable** metric: a model that emits pad tokens or
random characters gets a high NLL on a real continuation regardless of how
"persona-like" its surface stats look. It is the load-bearing artifact for
the sprint's publishable claim (`sprints/sprint-11/stories.md` Sprint success
metric).

### 1.2 Design choice: extend the dormant US-7.6 seam, do not invent a new one

US-7.6 already shipped the `hu_ml_nll_compute_fn_t` seam dormant
(`include/human/ml/fidelity.h` lines 88–95, `src/ml/fidelity.c` lines 125–131).
The seam is a process-wide function pointer with a `HU_ERR_NOT_SUPPORTED`
default. Sprint 11 wakes it up — it does not rewrite it. The same setter,
same signature, same `HU_IS_TEST` mock pattern, same JSONL holdout shape
(`{prompt, continuation}` rows). What changes:

1. A **new CLI subcommand** `human ml twin-eval` (separate from
   `human ml fidelity-status --judgment` to avoid widening US-7.6's API)
   that emits the YNTP schema: `{base_nll, adapter_nll, delta_nll,
   n_prompts, pad_rate}` instead of US-7.6's `{judgment_ppl,
   judgment_ppl_status, ...}`.
2. A **new Python NLL backend** (`scripts/yntp_nll_backend.py`) registered
   via a subprocess+JSON-lines protocol over stdin/stdout, called by the C
   evaluator one row at a time. C stays C; Python does the MLX work. The C
   side never links against MLX or Python.
3. A **new fixture-derivation script** (`scripts/derive_yntp_holdout.py`)
   that reads `~/.human/memory.db`, PII-redacts via `hu_pii_redact`, and
   emits a deterministic 30-row JSONL by message-id-modular sampling
   (frozen seed). Run-once; output committed to repo as
   `tests/fixtures/yntp_holdout_30.jsonl`.
4. A **two-adapter comparison loop**: the evaluator runs the registered
   NLL fn twice — once with `adapter_path == ""` (base) and once with the
   real adapter — and emits the delta. The backend handles
   load/unload of the adapter between calls.

### 1.3 Why this seam, not a direct MLX C binding

The MLX-LM library is Python and Swift; no public C ABI. We could:

- **A.** Bind to `mlx_lm.generate`'s logprobs output via Python C-API in
  process. Ties human's C build to a Python runtime. Rejected: violates
  KISS + h-uman's zero-mandatory-deps stance.
- **B.** Spawn `python3 scripts/yntp_nll_backend.py` as a subprocess, talk
  JSONL over pipes. One process for the whole evaluation (not per row),
  loads the model once, services N rows. Loose coupling, easy to mock,
  easy to swap to llama.cpp/MLX/Swift later. **Chosen.**
- **C.** Wire to `src/ml/gpt.c` reference HUML GPT (the US-7.6 follow-on
  path). Works in CI but doesn't match the *real* Gemma-4 model the user
  chats with — defeats the point of an ungameable metric.

Option B keeps the C surface clean: the C evaluator only knows about
`hu_ml_nll_compute_fn_t`. A new file `src/ml/nll_backend_subprocess.c`
provides one concrete implementation of that fn type that fork+exec's the
Python backend in non-`HU_IS_TEST` builds. In `HU_IS_TEST` builds the
default fn remains `HU_ERR_NOT_SUPPORTED` and tests register their own
mocks (US-7.6's D3 dormancy pattern, preserved).

### 1.4 NLL computation mechanism (Python side)

`mlx_lm.generate` does not expose per-token logprobs cleanly across all
versions (acknowledged risk; see §4 Risk 1). The robust approach is
**teacher-forced scoring**, not generation:

```
# pseudo-API; see backend file for actual MLX calls
tokens = tokenizer.encode(prompt + continuation)
prompt_len = len(tokenizer.encode(prompt))
logits = model(tokens[:-1])           # forward pass, one shot
log_probs = nn.log_softmax(logits, axis=-1)
# index out the log-prob of each true continuation token
target_tokens = tokens[prompt_len:]
log_probs_of_target = log_probs[prompt_len-1:-1, target_tokens]  # gather
nll_per_token = -log_probs_of_target.mean().item()
```

Teacher-forced scoring is the standard NLL-evaluation pattern (e.g. the
`lm-eval-harness` `loglikelihood` task type). It is deterministic, has
no sampling-temperature dependency, and works identically on base and
adapted models — eliminating Risk 1's exposure to the `generate` API
instability. The MLX-LM library exposes `model(tokens)` as a regular
forward pass; this is stable API.

`pad_rate` is computed separately: for each row, also run free generation
(temperature 0, max_tokens 64) and count rows whose output contains the
pad-token string. This is the Sprint 8 broken-adapter regression guard
(AC-11.6.3). Two passes per row (score + generate) is acceptable at N=30.

### 1.5 The four design questions in the brief, answered

1. **Where do held-out prompts come from?** `~/.human/memory.db` →
   `derive_yntp_holdout.py` with a **frozen seed**. Sampling strategy:
   pick every k-th user message where `k = floor(n_user_messages / 30)`,
   starting at `message_id % k == 0`. Deterministic, no random.choice.
   The prompt is the last 4 messages before the held-out one (conversation
   context); the continuation is the held-out user message. Once
   committed, `tests/fixtures/yntp_holdout_30.jsonl` is frozen — no
   re-derivation per run.
2. **Privacy.** `hu_pii_redact` (existing in `src/security/`) is called on
   every prompt and continuation **before** serialization to JSONL.
   No phone numbers, emails, addresses, URLs, or contact names land in
   the committed fixture. The fixture itself is reviewed by Seth before
   commit (manual gate). The derivation script never writes raw text.
3. **NLL computation.** Teacher-forced scoring via direct forward pass on
   `mlx_lm` (not via `mlx_lm.generate`). See §1.4. Per-token NLL averaged
   over continuation tokens only.
4. **Comparison baseline.** Two NLL passes per holdout row: (a) base
   Gemma-4-E2B with the persona system prompt prepended (the M3-aligned
   baseline — the cloud-provider-equivalent of "personalization via prompt
   only"); (b) base + DPOP+DoRA adapter loaded, same persona system
   prompt. `delta_nll = base_nll - adapter_nll`. Positive = adapter wins.
   The persona-system-prompt baseline is honest: it's what M3's "no
   fine-tuning, just prompt" cloud-provider path delivers today.

### 3.2 Test seam discipline

- **Same pattern as US-7.6 D3.** Production default for the NLL fn is
  `HU_ERR_NOT_SUPPORTED`. The subprocess backend is only initialized when
  `hu_ml_nll_subprocess_init` is explicitly called by the CLI in non-test
  builds. In `HU_IS_TEST`, that function returns immediately without
  spawning anything (compile-out via `#ifdef HU_IS_TEST`).
- **No network, no filesystem outside `tests/fixtures/`, no real model
  weights** in any test. All NLL values are mock outputs.
- **All tests deterministic** — given the same fixture and same mocks,
  the output JSON is byte-identical run to run. The inference order is
  the fixture's natural order (no shuffling).

### 3.3 Determinism contract (the headline test)

`test_deterministic_same_adapter_same_holdout_same_result`: run the full
inference twice in the same process with the same mock NLL fn registered
twice, on the same loaded holdout. Assert the two output JSON strings
are byte-identical (not just numerically equal — same string ordering,
same float formatting, same key order). This is the "ungameable"
property's flip side: deterministic means trustable.

## 4. Risk analysis (top 3)

### Risk 1 — Per-token logprob extraction from MLX is API-fragile (PROBABILITY MEDIUM, IMPACT HIGH)

**What could go wrong:** `mlx_lm.generate` does not consistently expose
per-token log-probabilities across versions. The library's primary surface
is generation (sampling), not scoring. If we depend on internal logits
access that the maintainers refactor between mlx-lm versions, the backend
breaks silently and we can't reproduce the headline number.

**Mitigation:**
- **§1.4 design pins teacher-forced scoring via the raw `model(tokens)`
  forward pass**, not `generate`. The `model.__call__` API is the
  stable, low-level interface. Inspect logits, log_softmax, gather —
  all standard MLX array ops, not mlx-lm internals.
- The backend pins `mlx-lm` version in `pyproject.toml` /
  `requirements-ml.txt` (recommended pin: `mlx-lm==0.21.*` per Sprint 8
  smoke-run lineage).
- The Python backend has a self-test mode: `python3 scripts/yntp_nll_backend.py --self-test`
  runs a fixed-prompt-fixed-continuation pair and asserts the NLL is
  within 1e-3 of a hand-recorded golden number. Run in CI's nightly ML
  lane (when ML lane lands; until then, manually on Seth's machine
  before each adapter run).
- **Fallback if scoring API breaks:** the subprocess protocol is
  JSON-lines, so swapping the backend to `llama-cpp-python` (which has a
  documented `Llama.eval_logits` + `Llama.scores` API) is a one-file
  replacement. The C side does not change.

### Risk 2 — Base-vs-adapter comparability (PROBABILITY MEDIUM, IMPACT HIGH)

**What could go wrong:** if base and adapter inference use different
tokenizers, different system prompts, different precision (fp16 vs bf16),
different KV-cache state, or different chat templates, the delta is
measuring those differences instead of the adapter's effect. We could
report a publishable improvement that is actually a tokenization artifact.

**Mitigation:**
- **Same Python process, same loaded model object.** The adapter is
  loaded/unloaded between passes via `model.load_weights(adapter_path)`
  rather than spawning two separate processes. Tokenizer, system prompt,
  dtype, sampling config: all identical by construction.
- The system prompt is read once from `~/.human/persona/current.json` and
  used verbatim for both passes. The JSON output records the
  system-prompt SHA256 hash so reviewers can verify identical inputs.
- **Per-row sanity check baked into the test plan:** for at least one row
  in `yntp_holdout_30.jsonl`, the test asserts that with `adapter_path
  == ""` (no adapter loaded), the prompt token count is identical to
  the run with the adapter loaded (only the model weights differ). This
  catches the "tokenizer changed" failure mode.
- The output JSON also records `n_prompt_tokens` and
  `n_continuation_tokens` per row in a `--verbose` mode (off by default).
  When the headline claim is published, the verbose dump must be in
  `sprints/sprint-11/evidence/US-11.6/`.

### Risk 3 — Holdout PII handling and consent (PROBABILITY MEDIUM, IMPACT HIGH)

**What could go wrong:** `~/.human/memory.db` contains Seth's real
messages, possibly with contact names, phone numbers, addresses,
financial info. `hu_pii_redact` is a regex-based redactor — it
misses things (free-text first names, slang, code-words, unusual
formats). If even one row leaks PII, the fixture cannot be committed
to the repo, and the publishable claim cannot cite the fixture.

**Mitigation:**
- **The derivation script never auto-commits.** It writes
  `tests/fixtures/yntp_holdout_30.jsonl.candidate`, prints a count of
  rows with potential residual PII (using a stricter secondary regex
  list than `hu_pii_redact` uses), and **stops**. Seth manually reviews
  the candidate file, fixes any leaks by hand, and renames it to drop
  the `.candidate` suffix. The fixture-validity test
  (AC-11.6.6) blocks commit if the disallowed-names list is matched.
- The fixture is gated by a `.gitattributes` filter or a pre-commit
  hook that runs `tests/test_yntp_holdout_fixture` on the staged file.
  (Implementation note: if the project does not already have a
  pre-commit pattern for fixture validation, a CI-only check is
  acceptable for Sprint 11; pre-commit can be a follow-up.)
- **Consent.** This is Seth's own data, on Seth's own machine,
  for Seth's own product. The fixture is committed to a public repo
  only after Seth's explicit review. **Open question §6.1 requests this
  explicit decision.** If the answer is "do not commit real-data
  fixture", the fallback is a synthetic 30-row fixture in the YNTP
  format with explicit `synthetic: true` per row; the headline claim
  then cites "computed on Seth's local chat.db, fixture not published
  for privacy reasons; methodology published, raw data withheld."
- All test code that reads the fixture works identically with the
  synthetic-fallback fixture. The choice does not affect the implementer's
  work; only the evidence captured at sprint close.

## 6. Open questions for Seth

### 6.1 Privacy / consent: commit the chat.db-derived fixture, or synthetic-only?

`tests/fixtures/yntp_holdout_30.jsonl` is the headline artifact. Two
options:

- **(A) Commit the redacted real-data fixture** to `sprint-11-sota-twin`
  (and eventually to `main`). Pros: the publishable claim cites the
  actual fixture; reviewers can audit; reproducibility. Cons: even after
  `hu_pii_redact` + manual review, some risk of leaking style markers
  ("the way Seth phrases things" is itself identifying).
- **(B) Synthetic-only public fixture**, real fixture stays in
  `~/.human/yntp_holdout_30.private.jsonl` on Seth's machine. Pros:
  zero privacy risk. Cons: claim becomes "computed on real data,
  methodology published, fixture withheld" — weaker but defensible.
- **(C) Hybrid:** commit a synthetic fixture for CI + an `.example`-form
  redacted real fixture (10 rows) for reviewer audit; the headline
  number is computed on the full 30-row private fixture and recorded
  in evidence/.

**Recommendation: (C)**. It satisfies the CI + repro need without
publishing 30 rows of real conversation. The implementer agent should
proceed with (C) unless overridden.

### 6.2 What is the publishable comparison?

The brief says "base Gemma-4 with persona system prompt vs base+adapter".
The sprint stories.md Sprint success metric agrees ("base+system-prompt
persona baseline"). Confirm: should the evaluator ALSO emit a
"raw base, no persona prompt" number as a third column, to quantify how
much of the lift comes from the system prompt vs the adapter?

**Recommendation: yes** — extend the JSON schema (additive, not
breaking) to include `raw_base_nll` alongside `base_nll` (which is
"base + persona system prompt"). Three-way comparison is more
informative and costs one extra inference pass.

### 6.3 Pad-token detection: which token id?

The "pad rate" metric requires knowing what counts as a pad token in
Gemma-4-E2B's tokenizer. Sprint 8's `<pad>` detection assumed a
specific token id; this may differ in mlx-lm's Gemma vocab. Confirm
whether to detect by:
- (i) tokenizer's `pad_token_id` (whatever the model declares),
- (ii) literal substring `<pad>` in decoded text,
- (iii) both (OR).

**Recommendation: (iii) both.** Defensive: tokenizers sometimes
decode the pad-id to empty string, in which case substring search
misses it; sometimes they decode to literal `<pad>`, in which case
the id check misses it (because the actual emitted id is something
else like the eos id followed by `<pad>` tokens encoded as bytes).
