# Design for US-11.7: 4-stage Pareto gate cascade

**Sprint:** 11
**Branch:** `sprint-11-sota-twin`
**Depends on:** US-11.6 (held-out NLL evaluator → Stage 1 input), US-11.1 (pad masking — so Stage 2 tests the right failure mode)
**Risk tier:** HIGH (gates adapter promotion)
**Estimate:** L

---

## 1. Approach

The cascade is a **fail-fast pipeline** that orders four checks by ascending cost and descending determinism. Each stage is a pure function of `(adapter_path, fixture_path) -> StageResult`; the orchestrator composes them and short-circuits on the first REJECT. This composition is the design — not the individual stages, which are mostly thin wrappers over work that already exists or will exist (US-11.6) or is honestly dormant (Stage 3, per Sprint 7 D3).

```
                            ┌──────────────┐
adapter_path, fixtures ───► │ Stage 1: PPL │── REJECT? ──► exit 2
                            │  floor       │
                            │ (US-11.6 NLL │
                            │  evaluator)  │
                            └──────┬───────┘ PASS
                                   ▼
                            ┌──────────────┐
                            │ Stage 2:     │── REJECT? ──► exit 2
                            │ Coherence    │
                            │ (local Gemma │
                            │  G-Eval)     │
                            └──────┬───────┘ PASS
                                   ▼
                            ┌──────────────┐
                            │ Stage 3:     │── DORMANT (D3 pattern):
                            │ Persona PRM  │── emits SKIP line,
                            │ (DORMANT —   │   produces NEUTRAL score,
                            │  Sprint 7 D3)│   never gates positive
                            └──────┬───────┘
                                   ▼
                            ┌──────────────┐
                            │ Stage 4:     │── verdict ──► PROMOTE/DEFER/REJECT
                            │ Pareto       │
                            │ ensemble     │
                            │ (min-agg)    │
                            └──────────────┘
```

**Why this and not alternatives.** A monolithic `cascade.py` that owns all four stages would be hard to mock and would tangle the dormancy seam with live logic. Instead we keep:
- the **existing `pareto_picker.py`** as the Stage 4 engine, extended with a `--stage-scores` JSON input so it can ensemble multiple judges, not just (delta, pad_rate);
- a new thin **`stage_cascade.py`** orchestrator that drives stages 1→4, emits a single per-stage JSON, and owns fail-fast control flow;
- **shell entry point unchanged** — `check-lora-ab.sh` gains a `--cascade` flag that invokes the orchestrator and respects the same dormancy SKIP convention `--judgment` already established.

**Fail-fast semantics.** Stages 1, 2 can REJECT and short-circuit. Stage 3 (dormant) can only ABSTAIN — it never rejects and never promotes; it contributes a neutral score and a visible SKIP line. Stage 4 always runs and produces the final verdict from whichever stage scores reached it. The cron treats SKIP-only outputs as DEFER, never PROMOTE — a deliberate copy of D3's "inactive gate cannot silently advance the cron".

**Cascade order is load-bearing.** Stage 1 (PPL floor) is the only stage that catches the Sprint 8 iter-200 `<pad>` failure deterministically and for free. Putting Stage 2 ahead of Stage 1 would either (a) require Stage 2 to also detect pad-token gibberish (it shouldn't — that's not its job), or (b) burn the coherence judge's model load time on adapters Stage 1 would reject for ¢0. The order is the design.

## 3. Test plan

Each AC has one test. Three named scenarios cover the cross-cutting cases the PO called out:

| Scenario | Fixture | Stage 1 | Stage 2 | Stage 3 | Stage 4 | Final verdict | Exit |
|---|---|---|---|---|---|---|---|
| Sprint 8 iter-200 (broken adapter) | `sprint8_iter200.json` | REJECT (PPL=4×) | (skipped) | (skipped) | (skipped) | REJECT | 2 |
| iter-60 best-of-Pareto (current) | `iter60_dirty.json` | PASS (1.2×) | PASS (0.75) | SKIP (dormant) | DEFER (pad_rate=0.40 > 0.10) | DEFER | 1 |
| iter-60 with hypothetical US-11.1 pad-masking fix | `iter60_padfix.json` | PASS (1.05×) | PASS (0.82) | SKIP (dormant) | PROMOTE | PROMOTE | 0 |

Additional AC-specific tests:
- `test_ppl_floor_rejects_high_ppl` (AC-11.7.1) — fixture with `adapter_ppl = 4 × base_ppl`; asserts exit 2 at Stage 1, Stage 2 never invoked (assert via mock-call counter).
- `test_coherence_judge_rejects_pad_outputs` (AC-11.7.2) — fixture passes PPL but has 50%+ `<pad>` rate in mocked Stage 2 generations; asserts exit 2 at Stage 2.
- `test_sprint8_iter200_rejected_by_gate` (AC-11.7.3, regression guard) — the named scenario above; this is the test that would have caught the Sprint 8 catastrophe.
- `test_stage3_stub_configurable` (AC-11.7.4) — invoking with `--stage3-stub 0.5` returns 0.5 for Stage 3; default (no flag) returns SKIP; ensures Stage 3 NEVER promotes-on-its-own.
- `test_ensemble_min_aggregation` (AC-11.7.5) — three scores `{lexical: PROMOTE, coherence: PROMOTE, nll: DEFER}` → final = DEFER (min, not majority).
- `test_check_lora_ab_staged.sh` (AC-11.7.6) — invokes shell with `--cascade`, asserts presence of a `cascade_stages` JSON block with one entry per stage.

**Determinism contract.** Every stage that calls a model is mockable via env var:
- Stage 1: `HU_CASCADE_STAGE1_MOCK_PPL=<float>` (already supported in spirit by US-11.6's `HU_IS_TEST` path).
- Stage 2: `HU_CASCADE_STAGE2_MOCK=<json>` — array of per-prompt coherence scores.
- Stage 3: `--stage3-stub <float>` CLI flag (per AC-11.7.4).

No test invokes a real Gemma-4-E2B; the coherence judge is mocked in 100% of test paths. A separate manual-smoke script (`scripts/cascade_smoke.sh`, not part of US-11.7 AC) exercises the real judge against `tests/fixtures/yntp_holdout_30.jsonl` once we have evidence we want.

## 4. Risk analysis

### Risk 1 — Cascade order is wrong and changes verdicts (probability: MED, impact: LARGE)

If Stage 2 runs before Stage 1, a pad-poisoned adapter might score high enough on a coherence judge that hasn't itself been adversarial-tested against `<pad>` tokens to be REJECTED — but it would never get to a Stage 1 that would have rejected it deterministically. Worse: if anyone later "optimizes" the cascade by re-ordering, the Sprint 8 failure can return silently.

**Mitigation:**
1. Test AC-11.7.3 asserts the rejection happens **at Stage 1 specifically** (assert via per-stage JSON), not "somewhere in the cascade". A re-ordering will fail that AC.
2. `stage_cascade.py` defines stages as a single ordered tuple `STAGES = (stage1, stage2, stage3, stage4)`. Reordering requires editing the tuple, which lights up the AC test immediately.
3. Code comment at the tuple cites this risk by name.

### Risk 2 — Stage 2 coherence judge is itself a model and can fail (probability: MED, impact: MED)

The coherence judge is a Gemma-4-E2B that we load locally. Three failure modes:
- **Model file missing** — first run on a fresh machine has no model.
- **Inference crashes** — OOM, missing CoreML, version skew.
- **Judge returns NaN / out-of-range score** — silent corruption.

Any of these, treated as "PASS by default", would allow a broken adapter through Stage 2. Treated as "REJECT by default" would block every adapter.

**Mitigation:**
1. Stage 2 has THREE distinct return states: `PASS`, `REJECT`, `ABSTAIN`. ABSTAIN is for "judge itself failed". Cascade treats ABSTAIN like Stage 3 dormancy: emits a visible `STAGE2: ABSTAIN (reason=...)` line; Stage 4 receives no coherence score; the final verdict can be at most DEFER. **The judge never silently passes nor silently rejects.**
2. Health check: orchestrator calls `stage2.healthcheck()` once before the run; if it fails, emits a single ABSTAIN at the top and continues. No retries (deterministic).
3. The judge is the only Stage that is mocked in CI; production smoke runs of the real judge are a separate script.

### Risk 3 — Stage 3 dormancy is invisible (probability: LOW-MED if we follow D3, HIGH if we don't, impact: LARGE)

Stage 3 ships dormant. The Sprint 7 retro is explicit: a silently-skipped gate is the same as no gate. Operators reading `cron.log` must be able to tell that Stage 3 did not actually run.

**Mitigation (direct lift from D3):**
1. Stage 3 always emits a single visible line: `[cascade] stage3: SKIP (PRM not trained — Sprint 12)`.
2. Stage 3's contribution to the Stage 4 ensemble is `null`, not 0.0 and not 1.0 — the ensemble explicitly excludes null scores from min-aggregation. A null score CANNOT pull a verdict up OR down.
3. The cron consumer (US-11.8) must treat a run where Stage 3 status == "skip" as eligible for PROMOTE only if the OTHER stages all PASS — which is exactly what the dormant path produces. Documented in `pareto_picker.py` docstring and asserted in `test_stage3_skip_does_not_promote_alone`.

## 5. Sequencing (for implementer)

The order below is "smallest reversible change first". Each step ends with a green test; do not advance until it does.

1. **Skeleton package (no behavior).** Create `scripts/cascade_stages/__init__.py`, four stage files each containing only a `def run(adapter_path, fixture_path) -> dict: raise NotImplementedError`, and `scripts/stage_cascade.py` that imports and calls them in order, catching `NotImplementedError` and emitting `STAGE_n: NOT_IMPLEMENTED`. Run: `python3 scripts/stage_cascade.py --help` — must succeed.

2. **Pareto picker `--stage-scores` mode.** Extend `pareto_picker.py` to accept `--stage-scores <json>`. Existing positional CLI untouched. Add `test_ensemble_min_aggregation` (AC-11.7.5) — passes BEFORE wiring the orchestrator into it, because it tests the pure ensemble function.

3. **Stage 3 dormant stub.** Implement first because it's the smallest. Returns `{"status": "skip", ...}` always (unless `--stage3-stub <f>` injects). Add `test_stage3_stub_configurable` (AC-11.7.4) and `test_stage3_skip_does_not_promote_alone`.

4. **Stage 1 (PPL floor).** Wraps `human ml twin-eval --protocol yntp` from US-11.6. Reads JSON output, applies 3× floor. Mockable via env var. Add `test_ppl_floor_rejects_high_ppl` (AC-11.7.1).

5. **Stage 2 (coherence judge), mocked path only.** Implement the orchestration; the real Gemma call is hidden behind a `_call_judge()` function that consults `HU_CASCADE_STAGE2_MOCK` first. Add `test_coherence_judge_rejects_pad_outputs` (AC-11.7.2) and `test_stage2_abstain_on_judge_failure`.

6. **End-to-end orchestrator.** Wire `stage_cascade.py` to call stages in order with fail-fast. Add the three named-scenario tests, especially `test_sprint8_iter200_rejected_by_gate` (AC-11.7.3) — this is the regression guard.

7. **Shell flag.** Extend `check-lora-ab.sh` with `--cascade`. Add `test_check_lora_ab_staged.sh` (AC-11.7.6).

8. **Real Gemma backend (deferred to follow-on).** The real model load lives behind the mock seam. A follow-on story (US-11.7.1) lights it up after we have evidence the orchestration is right. This is the *exact* D3 pattern — orchestration ships green, the live model is a separate, named, deferrable step.

9. **`/verify` on the full sprint-11 test suite.** Required before TaskUpdate close.

## 6. Open questions for PO

1. **AC-11.7.6 naming.** AC text says `--staged-gate`; this design uses `--cascade` for the implementer-facing flag because "staged gate" is ambiguous (could mean "this gate is in staging" vs "a gated cascade"). Either works; please confirm. The AC test filename `tests/test_check_lora_ab_staged.sh` is preserved either way.
2. **Stage 1 PPL source.** AC-11.7.1 says "held-out PPL > 3× base". The US-11.6 evaluator reports NLL on YNTP; `PPL = exp(NLL/n_tokens)`. Stage 1 will derive PPL from NLL. Confirm this is the intended pipe rather than a separate PPL evaluator.
3. **Stage 4 min-aggregation policy on missing scores.** AC-11.7.5 says "no better than the worst individual judge". When Stage 3 contributes `null` (dormant), is the min taken over the non-null subset (this design) or treated as REJECT (would block every adapter until Sprint 12)? This design assumes the former; please confirm.
4. **Coherence threshold (0.7).** Research doc cites 0.7; AC-11.7.2 says ">= 50% pad outputs → reject". The 0.7 threshold is on the judge's coherence score, not pad rate. They're different. The implementation applies BOTH: pad_rate >= 0.5 → REJECT, OR mean_coherence < 0.7 → REJECT. Confirm.
