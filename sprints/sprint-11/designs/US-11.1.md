# Design for US-11.1: Pad-token masking + length normalization in DPO loss

**Story:** US-11.1 (P0, Wave 0)
**Risk tier:** LOW (per story header) — scripts + vendored Python only; no C changes
**Sprint:** sprint-11-sota-twin
**Author:** tech-lead
**Date:** 2026-05-16

---

## 1. Approach

### 1a. Where the bug actually lives

After reading `mlx_lm_lora/trainer/dpo_trainer.py` end-to-end, the issue is **not** "pad tokens leak into the loss" — they don't, on a per-token basis. `get_token_scores()` (line 47) already multiplies `cross_entropy(...)` by `mask[:, :-1]`, and `iterate_dpo_batches()` constructs `chosen_masks`/`rejected_masks` correctly (1.0 on real tokens, 0.0 on pad).

The actual bug is in **`compute_score()` at lines 50–52**:

```python
def compute_score(scores, mask, loss_type):
    token_count = mask.sum(-1)
    return scores.sum(-1) / token_count if loss_type == "ipo" else scores.sum(-1)
```

For `loss_type == "sigmoid"` (Sprint 8's configuration — `--dpo-cpo-loss-type sigmoid`), the per-token (pad-masked) log-probabilities are **summed without dividing by non-pad count**. The DPO margin therefore compares **total log-probability over the sequence**, which is monotonically more negative for longer non-pad sequences. The optimizer's cheapest move is to make rejected sequences "effectively shorter" by pushing real tokens to near-zero and letting the pad mask zero them — which it learns by emitting EOS/pad early at generation time. This is the textbook length-bias-into-pad-collapse pathway that Meng et al. (SimPO §3) and the DPO research synthesis (`sota-dpo.md` §4) flag as mandatory to fix.

So "pad masking + length normalization" actually decomposes into:
- **Pad masking** (already present in upstream): keep, add a regression test that asserts it still works under our patch
- **Length normalization** (missing for sigmoid/hinge/dpop in upstream): the new behavior we need

### 1b. Patch surface decision: vendor + patch, not upstream PR

Options evaluated:

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| Upstream PR to `Goekdeniz-Guelmez/mlx-lm-lora` | Future-proof | Multi-week merge timeline; Sprint 11 cannot block on it | NO |
| YAML config (`-c`) only | Zero code change | `compute_score()` has no length-norm switch in upstream code; YAML cannot inject behavior | NO |
| Wrapper subprocess (post-process the loss) | No vendor copy | We don't control the loss tensor — it's inside `mx.compile` graph | NO |
| **Vendor a thin subtree + monkey-patch at import time** | Minimal LOC; targeted; reversible | Diverges from upstream; must track upstream | **YES** |
| Fork the full repo into `vendor/mlx_lm_lora/` | Full control | Heavy; ~25 Python files; ownership burden | Overkill |

**Chosen approach: monkey-patch.** Create `scripts/mlx_lora_patch.py` that imports `mlx_lm_lora.trainer.dpo_trainer` and overwrites `compute_score` with a length-normalizing variant before `mlx_lm_lora.train` is invoked. `finetune-gemma.py` imports this patch module before constructing the training subprocess, AND we change the invocation from `python3 -m mlx_lm_lora.train` to `python3 -m scripts.mlx_lora_entry` (a thin wrapper that does `import mlx_lora_patch; from mlx_lm_lora.train import main; main()`).

This keeps the diff to **two new files (~120 LOC total)**, no edits to vendored 3rd-party source, and an obvious unwind path: delete the two files and the patch is gone.

### 1c. The semantic change

New behavior for `compute_score`: when `length_normalize=True` (driven by a new `--length-normalize` CLI flag in `finetune-gemma.py`, default ON for sigmoid/hinge/dpop, no-op for ipo which already normalizes):

```
score = (token_scores * mask).sum(-1) / mx.maximum(mask.sum(-1), 1.0)
```

The `mx.maximum(..., 1.0)` floor prevents divide-by-zero on degenerate empty sequences. With this, the DPO margin in the sigmoid path becomes a margin over **average per-token log-probability**, which is the SimPO/LN-DPO formulation (Meng et al. §3, eq. 4) minus the target-margin γ term (γ stays 0 here; it's a separate story if we want SimPO proper).

The patched `compute_score` is pure tensor math on small `mx.array`s — no model loading, no weights, no network. Tests assert `os.environ.get("HU_IS_TEST") == "1"` and that no `mlx_lm.load(...)` call is reached (mock `mlx_lm.load` to raise; test fails on any invocation).

## 4. Risks

### Risk 1 — Upstream fork divergence (probability MEDIUM, impact MEDIUM)

**What:** `mlx-lm-lora` is a single-maintainer fork at `Goekdeniz-Guelmez/mlx-lm-lora`. A future bump (2.2.0+) may rename `compute_score`, change its signature, or add a `length_normalize` flag natively — at which point our monkey-patch breaks silently or duplicates upstream.

**Mitigation:**
- Version assertion in `apply_length_norm_patch()` fails fast if `__version__ != "2.1.0"`.
- Pin `mlx-lm-lora==2.1.0` (drop the `<3` upper bound) in `scripts/finetune-gemma.py` install hint and any `requirements*.txt` we ship.
- Quarterly tech-debt task: re-evaluate whether upstream has merged length normalization. If yes, delete `scripts/mlx_lora_patch.py` and revert `finetune-gemma.py` to use `python3 -m mlx_lm_lora.train` directly.
- The two files are isolated to `scripts/`, so unwind is a 5-minute diff.

### Risk 2 — Length normalization changes loss magnitude → β needs re-tuning (probability HIGH, impact SMALL)

**What:** Switching from summed log-prob to mean log-prob shrinks `|logits|` by ~50× (sequences are ~50 tokens, so mean is ~50× smaller). With the same `beta=0.1`, the sigmoid saturates differently and learning may be too slow or too fast.

**Mitigation:**
- This is in-scope for US-11.4 (DPOP) and US-11.6 (eval) tuning, not US-11.1.
- US-11.1 ships with the default β unchanged but emits a clear warning in `finetune-gemma.py` stdout: "length normalization is active; if convergence is slow, try beta in [1.0, 5.0] (≈50× the prior value)". This warning satisfies the observability requirement.
- The SimPO paper (Meng et al. 2024 §5) reports β=2.0 as their default with length normalization, providing empirical anchor.

### Risk 3 — Pad masking + length norm changes do not fix the 40% leakage on their own (probability MEDIUM, impact MEDIUM)

**What:** Sprint 8 smoke-run-3 finding 4 noted that iter-60's 40% pad rate is the *empirical floor* under vanilla DPO with the current data. The research synthesis (`sota-dpo.md` §4) presents pad masking + length norm as **necessary but not sufficient** — DPOP (US-11.4) and ORPO (US-11.5) provide the **structural** prevention of DCR. So US-11.1 alone may not drive pad_rate below 50% on the Sprint 8 fixture.

**Mitigation:**
- AC-11.1.3 is written conservatively: it asserts "strictly less than 40%", not "≤ 10%". The PROMOTE bar requires US-11.4 + US-11.1 together; US-11.1 alone targets DEFER.
- The Sprint 11 success metric §1 (`twin-eval delta_nll > 0 with pad_rate == 0`) is the *combined* gate of Waves 0+1, not US-11.1 alone.
- If AC-11.1.3 fails empirically (pad_rate is still ≥ 40% after the patch), that is a Sprint 8 data-quality finding, not a US-11.1 implementation bug. Surface to product-owner and proceed to US-11.4 as planned.

### Risks NOT material here

- **Backward compatibility:** `--no-length-normalize` flag preserves prior behavior for any caller (CI, scripts/check-lora-baseline.sh) that depends on the old loss numerics. Default flip to `True` is intentional and matches sprint mandate.
- **Concurrency:** training is single-process; no race surface.
- **Data integrity:** training does not write to user data DB; only to adapter `.safetensors` files in an isolated path.
- **Performance:** `mask.sum(-1)` + division adds < 0.1% wall-clock per step (already-resident tensors).

Run in order. Each step has an explicit verification command. **No step is "done" until the verification passes.**

1. **Create the patch module skeleton** with the version assertion and `compute_score` replacement, but **do not yet wire it into `finetune-gemma.py`**.
   - Verify: `python3 -c "from scripts.mlx_lora_patch import apply_length_norm_patch; apply_length_norm_patch()"` exits 0.

2. **Write the 5 unit tests in `tests/test_dpo_pad_masking.py`** (all 5 will fail initially — that's the TDD signal).

   - Verify: `python3 -c "import json; d=json.load(open('tests/fixtures/sprint8_sweep.json')); assert len(d['checkpoints']) == 4 and d['checkpoints'][3]['pad_rate'] == 0.7"`.

7. **Run the full pytest suite plus the verifier agent**.
   - Verify: `/verify` returns `RESULT_verifier=PASS`. Manually run `cmake --build --preset dev && ./build/human_tests --suite=JSON` to ensure no C-side regression (none expected; we touched only Python).

## 7. Open questions

1. **Should the new `compute_score` length-normalize *both* `sigmoid` and `dpop` paths, or only `sigmoid`?**
   Recommendation: both, plus `hinge`. DPOP's positive-clipping penalty (US-11.4) is added *after* `compute_score`, so length-normalizing the inputs is independent of the penalty term — and the same length-bias issue exists for all summed-log-prob variants. Awaiting product-owner confirmation; if "only sigmoid" is preferred, the test fixture is the same, just one extra `loss_type` parameter.

2. **`train_config.json` schema bump**: adding the `length_normalize` field is a non-breaking additive change, but Sprint 8 `train_config.json` files do not have it. Should `human ml lora-ab` treat missing-field-old-files as `length_normalize=false` (the Sprint 8 default) for the historical-comparison view? Recommendation: yes, document as a JSON field default in `docs/ml-adapter-config.md` (out of scope for this story; flag to product-owner).

3. **Should we ship `--length-normalize` as a config-file-only setting (via the existing `-c` YAML config that US-8.6 fixed) rather than a CLI flag?** Recommendation: keep it CLI-first (defaults are visible in `--help`) with YAML override available through the existing config mechanism. No additional code path required.

None of these block implementation; all have a recommended default.
