# Design for US-11.4: DPOP loss head (Smaug positive-clipping)

> Sprint 11 / Wave 1 / P0. Author: tech-lead. Date: 2026-05-16.
> Branch: `sprint-11-sota-twin`. Depends on US-11.1 (pad masking).

## 1. Approach

### 1.1 Upstream support — confirmed

`mlx_lm_lora` (vendored at `~/Library/Python/3.14/lib/python/site-packages/mlx_lm_lora`)
**already implements DPOP natively.** Verified in this design pass:

- `trainer/dpo_trainer.py:78–83`:

      elif loss_type == "dpop":
          penalty = mx.maximum(
              mx.zeros_like(policy_chosen_score),
              reference_chosen_score - policy_chosen_score,
          )
          losses = -(nn.log_sigmoid(beta * logits) - delta * penalty)

- `train.py:376–383` exposes the flags we need:
  - `--dpo-cpo-loss-type {sigmoid,hinge,ipo,dpop}`
  - `--delta <float>` (default `50.0` upstream — see Risk 2)

**Implication:** No fork patch, no custom loss wrapper, no monkey-patch.
US-11.4 is a CLI-shape + config-plumbing + numerical-golden-test story. We do
**not** re-implement DPOP in Python — we drive the upstream-vendored
implementation, and we pin it with our own golden test so any silent
upstream change is caught.

This is the cheapest defensible design, and the AC are written to allow it:
AC-11.4.1 asserts the subprocess argv contains `--variant dpop` / `--dpop-lambda`
(our CLI surface) which we translate to upstream `--dpo-cpo-loss-type dpop` /
`--delta` (the upstream flag spelling).

### 1.2 CLI surface (ours) vs. mlx_lm_lora flags (theirs)

We keep our **user-facing** flag spelling consistent with the story
(`--variant dpop`, `--dpop-lambda`) and translate at the subprocess boundary
in `run_dpo()` — exactly the layering Sprint 7/8 already established for
`--dpo-cpo-loss-type sigmoid` (see `scripts/finetune-gemma.py:513`).

| Ours (user-facing)        | Upstream (mlx_lm_lora)            | Notes                          |
|---------------------------|-----------------------------------|--------------------------------|
| `--variant {dpo,dpop}`    | `--dpo-cpo-loss-type {sigmoid,dpop}` | `dpo` → sigmoid (back-compat) |
| `--dpop-lambda <float>`   | `--delta <float>`                 | Default 0.1 (NOT upstream's 50)|
| `--beta 0.1` (unchanged)  | `--beta 0.1`                      | DPO temperature, untouched     |

The name `--dpop-lambda` matches the research doc and AC text. Upstream calls
it `delta`, but the literature (Pal et al. Eq. 8) uses λ; we present λ to
operators and translate internally. A comment at the translation site spells
this out so the next reader is not confused.

### 1.3 What `--variant dpo` keeps doing (back-compat)

`--variant dpo` (the current implicit default) continues to pass
`--dpo-cpo-loss-type sigmoid` — bit-identical to current behavior. AC-11.4.5
is satisfied by *not* changing that codepath. The existing
`tests/test_finetune_gemma_dpo.py` suite must keep passing untouched.

### 1.4 Why no custom Python loss

A custom Python loss wrapper was considered. It is rejected because:

1. The upstream `dpop` branch is exactly the formula in the AC (verified
   line-by-line against Pal et al. 2024 §3 / Eq. 8).
2. Wrapping it would require re-implementing the batched MLX
   forward/backward, doubling the surface area, and creating a divergence
   risk with upstream when mlx_lm_lora updates.
3. The numerical golden test (§3) catches any silent upstream regression
   without us owning the loss code.

If a future story needs a loss term that upstream does **not** support
(e.g., Cal-DPO, BPO), that's the moment to build the wrapper — not now.

## 3. Test plan

### 3.1 Pattern: SimPO-golden-style numerical fixture

We mirror the load-bearing pattern from US-7.10's
`tests/test_rl_trainer_simpo.c::test_simpo_loss_golden`:

1. Hardcode logprob inputs as floats.
2. Compute expected loss in pure Python (numpy, double precision) — show the
   derivation in the fixture file's `_comment` and in a comment block in the
   test.
3. Call the implementation under test with the same inputs.
4. Assert `|loss - expected| < 1e-4` (matches US-7.10's tolerance).

For US-11.4, "the implementation under test" is upstream
`mlx_lm_lora.trainer.dpo_trainer.dpo_loss(..., loss_type="dpop")`. We
import it directly in the test — no subprocess, no model forward, no
filesystem I/O. Pure mlx-array math on injected logprobs.

### 3.2 The three numerical tests

**AC-11.4.2 — `test_dpop_penalty_fires_on_dcr_condition`:**

    # Inputs designed so log_pi_ref(chosen) > log_pi(chosen)
    policy_chosen   = -12.0   # current model gave chosen a low score
    ref_chosen      =  -8.0   # ref model gave chosen a higher score
    policy_rejected = -15.0
    ref_rejected    = -15.0
    beta = 0.1
    delta = 0.1

    # Sigmoid (vanilla DPO):
    logits = (policy_chosen - policy_rejected) - (ref_chosen - ref_rejected)
           = (-12 - -15) - (-8 - -15) = 3 - 7 = -4
    sigmoid_loss = -log_sigmoid(0.1 * -4) = -log_sigmoid(-0.4)
                 = 0.91301525...

    # DPOP penalty:
    penalty = max(0, ref_chosen - policy_chosen) = max(0, 4) = 4
    dpop_loss = sigmoid_loss + delta * penalty
              = 0.91301525... + 0.1 * 4 = 1.31301525...

    assert abs(dpop_loss - 1.31301525) < 1e-4
    assert dpop_loss > sigmoid_loss  # strict greater (AC text)

**AC-11.4.3 — `test_dpop_penalty_zero_on_healthy_chosen`:**

    policy_chosen = -8.0   # model now scores chosen higher than ref
    ref_chosen    = -10.0
    # penalty = max(0, -10 - -8) = max(0, -2) = 0
    # → DPOP loss == sigmoid loss (exact equality, not approx)
    assert abs(dpop_loss - sigmoid_loss) < 1e-9

**AC-11.4.4 (regression guard) — `test_sprint8_iter80_dcr_prevented_by_dpop`:**

This is the most subtle test. We do NOT run real training — that's slow,
nondeterministic, and not what the AC asks for ("fixture simulation").
Instead we replay the Sprint 8 gradient direction analytically:

    # Sprint 8 iter-80 observation: vanilla DPO drove chosen_r to -8.867.
    # chosen_r is defined upstream as beta * (policy_chosen - ref_chosen).
    # So policy_chosen - ref_chosen = -88.67 (with beta=0.1).
    #
    # Inject a sequence of (policy_chosen, ref_chosen) pairs that walk in
    # the DCR direction (policy < ref by increasing margin). At each step:
    #   - Vanilla DPO: the loss penalizes the *gap to rejected*, NOT the
    #     decrease in chosen — so dL/d(policy_chosen) can be ~0 once the
    #     margin is wide enough, allowing chosen to drift down.
    #   - DPOP: the penalty term contributes -delta * 1 to
    #     dL/d(policy_chosen) the moment policy < ref, pulling it back up.
    #
    # We do NOT need to actually run an optimizer. The AC says
    # "must NOT drop below 0 at any sampled checkpoint". We simulate by:
    #   1. start: chosen_r = +2.0
    #   2. compute the DPOP loss gradient w.r.t. policy_chosen (analytically)
    #   3. step: policy_chosen -= lr * grad
    #   4. recompute chosen_r = beta * (policy_chosen - ref_chosen)
    #   5. assert chosen_r >= 0 at every step
    #
    # The DPOP gradient w.r.t. policy_chosen has a -delta term active
    # whenever policy_chosen < ref_chosen, so the simulation provably
    # cannot cross zero from above. This is a *property* test of the
    # loss shape, not a model-training test.

Determinism: all inputs are hardcoded floats; no RNG; the test is a single
function call with a deterministic for-loop. Runtime budget: <1s.

## 4. Risks

### Risk 1 — Upstream `--delta` default is 50.0, not 0.1 (HIGH / LARGE)

**What could go wrong.** `mlx_lm_lora/train.py:383` defaults `--delta` to
**50.0**. The Smaug paper and our research doc recommend **0.1–0.5**. If an
operator omits `--dpop-lambda` and our argparse default is unset, we'd
inherit a 500× larger penalty — likely catastrophic for training stability
(the DPOP penalty would dominate the sigmoid term, training collapses to
"only match ref on chosen").

**Probability.** High (this is exactly the kind of unit-mismatch bug that
ships).
**Impact.** Large (silent training-collapse on the only loss variant Sprint 11
is shipping).
**Mitigation.**
1. Our argparse `--dpop-lambda` default = `0.1` — explicit, never falls
   through to upstream.
2. We **always** pass `--delta <args.dpop_lambda>` to upstream when
   `--variant dpop`; never rely on upstream default.
3. Unit test asserts the default path emits `--delta 0.1`, not just "some
   --delta". One line in `test_dpop_flag_propagated`.
4. The translation site comment explicitly calls out: "Upstream default
   is 50.0; we override to 0.1 per Smaug / our research doc."

### Risk 2 — Interaction with US-11.1 pad masking (MEDIUM / MEDIUM)

**What could go wrong.** DPOP's penalty term uses
`policy_chosen_score - reference_chosen_score`. Both scores are sums over
the chosen token sequence. If US-11.1's pad masking is not active, pad
tokens contribute to both scores — and because policy and reference
tokenize/mask identically, the pad contribution **cancels** in the
*difference* used by sigmoid loss, but it does **NOT** cancel in the
DPOP penalty when there's any asymmetry in pad treatment between policy
and reference paths. This is exactly the failure US-11.1 is designed to
fix at the loss level; DPOP makes the dependency tighter.

**Probability.** Medium (US-11.1 is in the same wave and may not land
before US-11.4 starts).
**Impact.** Medium (the DPOP regression test could pass while real training
silently still has pad noise — a false positive on AC-11.4.4).
**Mitigation.**
1. US-11.4 is sequenced AFTER US-11.1 (story explicitly says so; the
   dependency graph in `sprints/sprint-11/stories.md:783` codifies it).
2. The implementer MUST verify US-11.1 has merged before opening the
   US-11.4 PR. Sequencing check is in the implementer's task list (§5).
3. The numerical golden test (§3.2) operates on `chosen_masks` directly
   (the upstream `dpo_loss` signature takes masks as inputs) — we set the
   mask explicitly in the test, so pad masking is correct *in the test*
   regardless of training-time bugs. The regression-guard test in §3.2
   does NOT prove production correctness; it proves the loss-formula
   correctness. Smoke-run with real data is needed to close the loop
   (handled by US-11.7 / DCR-eval, not this story).

### Risk 3 — Lambda hyperparameter choice (MEDIUM / SMALL-to-MEDIUM)

**What could go wrong.** Smaug paper sweeps λ ∈ {5, 10, 25, 50}. Our
research doc (`sota-dpo.md:57`) recommends **0.1**. That's a 50–500×
difference. If 0.1 is too small, DPOP becomes ~vanilla DPO and the DCR
fix is illusory; AC-11.4.4 still passes (because it's an analytical
property test, not a real training test), but real training would
regress.

**Probability.** Medium.
**Impact.** Small for this story (AC pass on shipped code), Medium for the
overall sprint (next story US-11.7 / Sprint-8-replay may fail).
**Mitigation.**
1. CLI accepts `--dpop-lambda` so an operator can sweep without code
   changes — no recompile, no PR.
2. Default 0.1 is documented in `--help` text as "starting point per
   Smaug-low / persona research; sweep 0.1 → 1.0 if DCR persists."
3. Add a "tuning notes" section to `sprints/sprint-11/designs/US-11.4.md`
   (this doc, §6) for the next operator.
4. The Sprint-8 smoke-replay (`scripts/ab_eval_30.py` exists already,
   per worktree state) is the empirical gate, NOT this design.

## 6. Open questions

1. **Should `--variant dpop` become the default in Sprint 12?** The story
   is silent. Recommendation: NO for Sprint 11 (preserve back-compat for
   any external scripts; AC-11.4.5 requires the dpo path to be
   bit-identical). Revisit after US-11.7 DCR-eval lands.

2. **`--delta` vs `--dpop-lambda` naming.** Confirmed above: we expose
   `--dpop-lambda` to match the research doc and AC text; translate to
   upstream `--delta`. The implementer should NOT rename it.

3. **Mask plumbing in the golden test.** Upstream `dpo_loss` takes
   `chosen_masks` / `rejected_masks` as MLX arrays. The fixture must
   create these as `mx.ones(...)` of explicit shape — there's no model,
   no tokenizer, so masks are trivially all-ones for the injected
   logprob sums. Document this in the fixture comment so the next
   reader doesn't think "but real masks aren't all-ones."

4. **Should the C-layer DPOP factory be a stub now?** The story's
   "Out of scope" line says Sprint 12. Recommendation: do NOT stub —
   stubs become drift. Add it in Sprint 12 with real tests when needed.

5. **Tuning notes for the operator** (§4 Risk 3 promise):
   - Start: `--dpop-lambda 0.1`.
   - If `chosen_r` still trends negative in the first 50 iters → bump to
     0.3, then 1.0. Above 1.0, the penalty likely dominates the
     preference signal — drop iters/LR before going higher.
   - Above 5.0 you're in Smaug-paper territory (their default was 50);
     that regime is for adversarial low-edit-distance pairs and may be
     correct for our use case eventually — track in US-11.7 eval.
