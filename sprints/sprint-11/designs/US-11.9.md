# Design for US-11.9 (P2 stretch): POPI summarizer baseline

> Cloud-provider-compatible personalization via a ≤100-token preference
> summary injected into the system prompt. Plan B for the M3 frontier-model
> bridge when on-device LoRA degrades on a cloud provider.

## 1. Approach

POPI's full paper (arXiv 2510.17881) trains an RL inference model that
compresses heterogeneous user signals into a short natural-language
preference summary. **That is explicitly out of scope** (story §Out of scope).
What is in scope is a **zero-shot baseline**: take the last N correction
pairs from `dpo_pairs.db`, run them through a deterministic template-based
extractor, and emit a ≤100-token plain-text summary. The summary is then
injected as a system-prompt suffix and benchmarked against base on the
US-11.6 YNTP NLL evaluator.

**Why template-based, not LLM-call:** AC-11.9.3 requires that under
`HU_IS_TEST` no real LLM call is made. Rather than gate the LLM path behind
two implementations (one for tests, one for prod) we pick the cheapest
option that satisfies the AC: **rule-based extraction is the default
implementation; a `--use-llm` flag (off by default) wires in the optional
cloud call for users who want it after the baseline lands.** Two reasons:
(a) we already have rule-based fact extraction in `personal_model.c`
(heuristic "i like" / "i never" patterns) — the same pattern works for
correction pairs and is already proven deterministic; (b) the comparison
we care about for the Pareto gate (US-11.7) is "does any cheap POPI variant
beat base?". If the rule-based variant wins, an LLM-based one will too;
if it loses, the LLM variant may still be worth a follow-up but is not
required to answer the sprint question.

**Compression strategy** (rule-based, deterministic):

1. Read up to `--max-pairs` (default 50) most-recent rows from
   `dpo_pairs.db` (`SELECT prompt, rejected, chosen FROM pairs ORDER BY
   created_at DESC LIMIT ?`).
2. For each pair, compute a delta signal — extract edit-distance-minimal
   replacements (rejected → chosen). These are the style preferences.
3. Bucket the edits into categories using regex/keyword rules:
   - **length**: chosen shorter/longer than rejected by ≥30%
   - **formality**: presence of contractions, slang words, "tbh", "lol"
   - **directness**: removed hedges ("maybe", "I think", "perhaps")
   - **emoji**: added/removed emoji codepoints
   - **markdown**: added/removed bullet lists, headings, code fences
4. Rank categories by frequency (most-evidenced first). Take the top 3-5.
5. Emit a fixed-form template: `User style: prefers <X>; avoids <Y>;
   tends to <Z>.` — whitespace-token-count budgeted to ≤100. If a
   category exceeds budget, truncate by line.

**Token counting:** AC-11.9.1 specifies *whitespace-split tokens*, not BPE.
This is intentional and simplifying — `len(summary.split()) <= 100` is the
test, and we enforce it at emission time.

**A/B harness:** US-11.6 already emits `base_nll` and `adapter_nll`. For
US-11.9 we extend the twin-eval CLI with a `--baseline popi
--popi-summary-file <path>` flag. When set, the harness runs a third
evaluation pass where the holdout prompts are wrapped with the POPI
summary prepended to the system prompt (existing persona block stays).
Output gains a third field `popi_nll`. No re-architecture of US-11.6 —
this is one extra call to the same mocked NLL seam.

## 3. Test plan

**Python unit tests (pytest):**

1. `test_summary_under_token_limit` — load fixture 50 pairs, run extractor,
   assert `len(summary.split()) <= 100`. Repeat 10× — must be byte-identical
   each time (determinism guard).
2. `test_summary_captures_three_distinct_preferences` — fixture is hand-
   crafted to evidence length, formality, and emoji preferences; assert
   summary text contains tokens from all 3 categories.
3. `test_empty_corrections_returns_empty` — empty DB → empty-string output,
   exit code 0 (AC-11.9.4).
4. `test_no_network_under_hu_is_test` — monkeypatch `urllib`, `httpx`,
   `requests` to raise on any call; run summarizer; assert no exception
   (AC-11.9.3).
5. `test_extract_edit_categories` — unit-tests for the 5 category
   classifiers in `popi_extract.py` with hand-built rejected/chosen pairs.

**Twin-eval integration (mocked NLL seam):**

6. `test_popi_baseline_in_yntp_output` — invoke `twin-eval --protocol
   yntp --baseline popi --popi-summary-file <fixture>` with mocked NLL
   returning 3 distinct values for base / adapter / popi prompts; assert
   JSON contains all 3 fields (AC-11.9.2).
7. `test_popi_summary_prepended_to_system_prompt` — capture the prompt
   passed to the mock NLL seam; assert it contains both the existing
   persona block AND the POPI summary.

**Determinism:** same `dpo_pairs.db` + same seed → byte-identical summary.
No randomness in the rule-based extractor (no `set()` ordering, no
`dict()` iteration before Python 3.7 — we target 3.11+ already).

**Command:** `python3 -m pytest tests/test_popi_summarize.py
tests/test_twin_eval_popi.py -v` (matches the story's test seam line).

## 4. Risk analysis (top 3)

### Risk 1: 100-token budget is too tight to capture meaningful preferences
- **Probability:** MEDIUM
- **Impact:** MEDIUM — could make POPI lose to base unfairly, masking
  whether the *approach* is viable.
- **Failure mode:** template emits 3 generic-sounding categories ("prefers
  shorter; avoids hedges; uses emoji") that don't change NLL meaningfully.
- **Mitigation:** template is parameter-driven (`--max-tokens 100` default
  per AC-11.9.1, but configurable up to 200 for exploration). If 100 wins,
  ship; if 100 loses by < 0.005 NLL, run a follow-up at 150/200 before
  declaring POPI dead. Don't bake "100" into anything that's not the CLI
  default. Honest reporting in design eval doc, not a verdict.

### Risk 2: Story requires LLM-call summarizer to be meaningful at all
- **Probability:** LOW (we explicitly de-scoped the LLM variant in §1)
- **Impact:** SMALL — if the rule-based loses badly, the question "would
  an LLM-summarized POPI win" is still open, but US-11.7 Pareto gate can
  still decide LoRA-vs-base without POPI.
- **Mitigation:** state explicitly in the JSON output and in the eval
  evidence file: `"popi_variant": "rule_based_v1"`. Future story
  US-11.9-followup can add `"popi_variant": "llm_zeroshot"`. The story's
  Out-of-Scope section already covers the deferral; we're not promising
  more than the AC ask for.

### Risk 3: US-11.6 ships late or with breaking JSON-schema changes
- **Probability:** MEDIUM — US-11.6 is P1 Wave 2; this story is P2 Wave 3
  (stretch). If US-11.6 lands different fields than expected, our
  three-way comparison test breaks.
- **Impact:** MEDIUM — we can't run AC-11.9.2 at all without US-11.6.
- **Mitigation:** (a) test against the **fixture JSON shape** documented
  in US-11.6 AC-11.6.1 (`base_nll`, `adapter_nll`, `delta_nll`,
  `n_prompts`, `pad_rate`) — if US-11.6 changes that schema, both
  stories' tests fail together and the breakage is obvious; (b) implement
  the `--baseline popi` flag as **additive** to twin-eval (does not alter
  existing fields); (c) gate this story's start on US-11.6 actually merging
  to the sprint branch, not just being "in progress".

## 5. Sequencing

1. **Pre-flight gate.** Verify US-11.6 has merged to `sprint-11-sota-twin`
   and `scripts/twin_eval.py` exists with the expected output schema.
   If not, this story stays parked. Do not stub the dependency.
2. **Fixtures first.** Write `tests/fixtures/popi_corrections_50.jsonl`
   with hand-crafted pairs exercising all 5 edit categories. Write the
   empty-DB fixture. Commit fixtures alone — no logic yet.
3. **Pure extractor.** Build `scripts/popi_extract.py` (pure functions:
   edit-delta classification, category ranking, template emission).
   Tests #5 (unit tests of classifiers) pass.
4. **CLI wrapper.** Build `scripts/popi_summarize.py` that reads the DB,
   calls the extractor, writes a file. Tests #1, #2, #3, #4 pass.
5. **C dispatch.** Wire `human ml popi-summarize` in `src/cli/cli.c`.
   Test #8 (CLI dispatch) passes.
6. **Twin-eval extension.** Add `--baseline popi --popi-summary-file`
   to `scripts/twin_eval.py`. Tests #6, #7 pass.
7. **Eval run.** Run the actual three-way comparison on the YNTP-30
   fixture from US-11.6 with the rule-based summary. Capture
   `popi_nll` vs `base_nll` to `sprints/sprint-11/evidence/US-11.9-popi.json`.
   Report honestly in the sprint evidence — POPI winning is not required
   for the story to complete; *measuring* it is.
8. **`/verify` gate.** Run full pytest + the C test suite. Confirm
   `RESULT_verifier=PASS`.

Each step is reversible; nothing after step 1 touches existing files in
a breaking way.

## 6. Open questions

1. **Should the optional `--use-llm` flag (deferred, not in this story)
   support both local and cloud summarizers?** The research note says
   POPI was validated to transfer zero-shot to GPT-4o and Claude. For our
   M3-bridge use case the answer is "yes both" — but for the v1 baseline
   we only need rule-based. Question for product-owner: is a follow-up
   story for the LLM-summarizer variant on the Sprint 12 backlog, and
   if so should it default to Gemini 3.1 (our standard) or be
   provider-agnostic?
2. **Whitespace-tokens vs BPE-tokens for the budget.** AC-11.9.1 says
   whitespace, which is the cheap test. But the *real* token count seen
   by the cloud provider will be BPE and will be larger (typically 1.3-
   1.5× for English prose). Should the v1 also enforce a BPE upper bound
   to be honest about "≤100 tokens" claims in evidence reports?
3. **Personal-model overlap.** `hu_personal_model_build_prompt` already
   injects a learned style summary into every system prompt. Does the
   POPI summary go *in addition to* or *in place of* the personal-model
   block during the A/B? Recommendation: **in addition** — POPI is the
   correction-pair signal, personal-model is the chat-history signal; they
   are complementary inputs. But this needs the product-owner's call
   because it changes what we're really measuring.
