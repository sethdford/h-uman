## Approach

The cheapest design that satisfies the ACs is a **thin, single-purpose adapter** that converts an existing `hu_mcp_client_t` (connected, with tools already discovered) into a `hu_tool_t[]` array suitable for handing to `hu_hula_exec_run`. The adapter does not own the MCP client, does not start MCP servers, does not modify either `src/mcp/*` or `src/agent/hula.c`. It is purely a vtable shim that:

1. Maps each MCP tool descriptor to a `hu_tool_t` whose `name()` returns the namespaced string `"mcp__<server>__<tool>"` (the same convention permission/audit code already uses — see `.claude/rules/tests-that-pin-bugs.md` mention of the `mcp__evil__file_write` form).
2. Implements `execute()` by parsing the `mcp__<server>__<tool>` prefix off the name, then delegating to `hu_mcp_client_call_tool` with the original `<tool>` and the CALL node's args JSON.
3. Propagates any non-`HU_OK` from `hu_mcp_client_call_tool` into the executor result as `ok == false` with the error code surfaced in the trace — never silently returns `HU_OK` on an MCP-side failure.

**Why this and not alternatives:**

- _Alt 1: Modify `hu_hula_exec_run` to know about MCP._ Rejected — couples two subsystems, violates AC-10.5.5 ("No existing `src/mcp/` or `src/agent/hula.c` files are modified").
- _Alt 2: Build a generic "tool source" abstraction with pluggable backends._ Rejected — YAGNI. One backend (MCP) is in scope; an abstraction earns its keep when it has ≥2 callers.
- _Alt 3: Spawn the MCP server inside the bridge._ Rejected — out of scope, and `hu_mcp_client_t` already owns connection lifecycle. The bridge takes a connected client by borrowed pointer.

Test seam is a stub `hu_mcp_client_t`-compatible echo server provided as a test fixture. We do **not** spawn a real subprocess in tests (`HU_IS_TEST` discipline). If `src/mcp/` already exposes a stub/loopback transport, we reuse it; otherwise we add `tests/fixtures/stub_mcp_server.{c,h}` that satisfies the same calling conventions via in-process function-pointer hooks. This is decided by Implementation Step 1 (a 10-minute spike) — if no in-process MCP test seam exists, US-10.5 estimate stays at M because the stub is small (~80 LOC).

## Public API (header sketch — design level only, no implementation)

```c
/* include/human/hula_mcp_bridge.h */
#ifndef HU_HULA_MCP_BRIDGE_H
#define HU_HULA_MCP_BRIDGE_H

#include "human/mcp.h"
#include "human/agent/hula.h"

/*
 * Build a hu_tool_t array from the tools currently exposed by `client`.
 * Each tool's name() returns "mcp__<server>__<tool>" where <server> is
 * client->config.server_name and <tool> is the MCP-side tool name.
 *
 * Ownership: caller owns the returned array; free with
 * hu_hula_mcp_bridge_tool_list_free. The bridge holds a BORROWED pointer
 * to `client` — the caller must keep `client` alive for the lifetime of
 * any hu_hula_exec_run that uses these tools.
 *
 * Returns HU_OK on success; on failure *out_tools == NULL, *out_count == 0.
 */
hu_error_t hu_hula_mcp_bridge_tool_list(hu_mcp_client_t *client,
                                        hu_allocator_t *alloc,
                                        hu_tool_t **out_tools,
                                        size_t *out_count);

void hu_hula_mcp_bridge_tool_list_free(hu_allocator_t *alloc,
                                       hu_tool_t *tools,
                                       size_t count);

#endif
```

The internal `execute` thunk has the contract:

- Strip the `mcp__<server>__` prefix from the tool name. If the prefix is malformed → return `HU_ERR_INVALID_ARG`, do NOT call the MCP client.
- Pass `args_json` (the CALL node's input) verbatim to `hu_mcp_client_call_tool`.
- If `hu_mcp_client_call_tool` returns non-OK → the bridge translates to the executor's failure protocol: result `ok = false`, error code carried in the trace via the existing `hu_hula_exec_t` error-surfacing convention used by other tools. Specifically, the bridge MUST NOT translate an MCP error to `HU_OK`.

## Risks

- **External-process timeout (MEDIUM / MEDIUM):** if the bridge is wired to a real MCP server (not the stub) and that server hangs on `tools/call`, the bridge will block indefinitely. **Mitigation:** the bridge does NOT manage the transport — `hu_mcp_client_t` owns timeouts. The bridge contract requires the caller to configure `hu_mcp_client_config_t` with sane timeouts; this is documented in the header. Add a test that simulates a slow stub returning an error after a delay → bridge still propagates the error, doesn't deadlock. (We do not test "true hang" — that's a property of the transport, not the bridge.)
- **Tests-that-pin-bugs anti-pattern (MEDIUM / LARGE) — explicit guard:** test `bridge_propagates_mcp_error_does_not_succeed` is adversarial. Its assertions MUST be phrased so a regression (bridge silently swallows error and returns `HU_OK`) fails the test. Specifically:
  - `HU_ASSERT_EQ(result.ok, false);`
  - `HU_ASSERT_NE(node_trace.error_code, HU_OK);`
  - **NOT** `HU_ASSERT_EQ(rc, HU_OK)` — that would pin the bug. The test name is a claim; the assertions must enforce the claim. See `.claude/rules/tests-that-pin-bugs.md`.
- **Memory ownership ambiguity (MEDIUM / MEDIUM):** the bridge allocates per-tool context structs holding a borrowed client pointer. **Mitigation:** explicit doc-comment on `hu_hula_mcp_bridge_tool_list` stating client must outlive the array; `..._free` releases everything the bridge allocated and nothing else. ASan run in CI confirms.
- **Args JSON pass-through validation (LOW / SMALL):** the bridge does not validate args JSON — it forwards verbatim. The MCP server validates per its tool schema. Bridge surfaces the resulting error if validation fails server-side. No mitigation needed; this is by design (we are not a JSON validator).
- **Concurrency (LOW / SMALL):** a `hu_hula_exec_t` runs single-threaded; the bridge's `execute` thunk is called from that thread. The `hu_mcp_client_t` underneath may have its own thread model; we trust its contract.
- **Backward compat (LOW / SMALL):** new file + new public header + 1-line include. No existing symbol changes. `hula_sdk.h` SDK version bump (`HU_HULA_SDK_VERSION_STRING`) → bump minor (additive).
- **Observability (LOW / SMALL):** each invocation should emit one trace event with the namespaced tool name and outcome — the executor's existing trace facility handles this; bridge only needs to populate the outcome correctly.

## Test strategy

- **Unit tests in `tests/test_hula_mcp_bridge.c`:** the four tests in Step 4 above. Production-symbol references: `hu_hula_mcp_bridge_tool_list`, `hu_hula_mcp_bridge_tool_list_free`, `hu_hula_exec_run`. Satisfies `.claude/rules/test-references-production-symbol.md` (test file → implied module `src/agent/hula_mcp_bridge.c`).
- **No integration tests across real network/process** — `HU_IS_TEST` discipline. The stub server is in-process.
- **ASan run** under preset `dev` confirms zero leaks for create/exec/free cycle.
- **Python smoke example** is exercised in CI by US-10.6's `bindings` job.

## Convergence story (MCP red-team Option A)

This story is Option A of the red team's MCP convergence ask: deliver the bridge as **shipped code with a public header and tested seam**, not just an ADR. The header `hula_mcp_bridge.h` becomes part of the SDK surface (`hula_sdk.h` includes it) — external developers can build MCP-backed HuLa programs from day one of v0.2.0. ADR follow-up documenting the long-term plan (HTTP transport, MCP server mode, auto-discovery) is filed as a P3 doc-only task in a future sprint; nothing on the bridge's public API needs to change to support those — they are additive transports under the existing `hu_mcp_client_t` and additive tool-list sources alongside the bridge.
