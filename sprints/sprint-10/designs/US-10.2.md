# Design for US-10.2: Python ctypes bindings (`bindings/python/`)

**Sprint:** 10 — HuLa Platform
**Priority / Estimate:** P0 / M
**Depends on:** US-10.1 (context handle + `hu_hula_error_string`)
**Risk tier:** LOW (additive; no C source changes beyond what US-10.1 already lands)
**Wave:** 1 (cannot start until US-10.1 lands AND the shared library target produces `libhuman_hula.{so,dylib}`)

---

## Approach

The cheapest binding that satisfies the AC is **`ctypes` over a shared library** — no extension build, no native compile step on the Python side, no `pybind11` / `cffi` dependency. `pip install -e .` is a pure-Python install; the C side is built once by CMake and discovered at runtime. This matches the AC literal ("Python ctypes bindings") and keeps the install path deterministic for CI.

The Python surface is intentionally thin: one `HulaContext` class that owns a `hu_hula_ctx_t` handle, exposes `run_json()` and a `version()` accessor, and follows the context-manager protocol. Errors from the C layer become a `HulaError` exception carrying `.code` (the `hu_error_t` integer) and `.message` (whatever `hu_hula_error_string` returns). The ctypes plumbing lives in one file (`_lib.py`) so the public `__init__.py` re-exports only `HulaContext`, `HulaError`, and `__version__`.

Two design decisions worth flagging:

1. **Shared library is a precondition, not part of this story.** The current `CMakeLists.txt` builds `human_core` as STATIC only (verified — `grep add_library CMakeLists.txt` returns two STATIC targets). US-10.1 owns adding the `human_hula` SHARED target (otherwise the Python AC-10.2.1 cannot pass). This design assumes US-10.1 lands that target. If it does not, US-10.2 is **BLOCKED** — see Risks.
2. **`find_library` first, env override second.** `ctypes.util.find_library("human_hula")` works for system-installed libraries; for in-tree development we honor `HUMAN_HULA_LIB` (absolute path) and fall back to walking `../../build/libhuman_hula.{so,dylib}` relative to the package. This is the same pattern Python projects like `cryptography` use and avoids forcing a `LD_LIBRARY_PATH` dance.

Stub tool registration (referenced by AC-10.2.2) is **out of scope for the binding layer** — the test fixture builds a no-op `hu_tool_t` via a small C helper that US-10.1 will already have to expose if its own tests are to validate `run_json`. If US-10.1 does not expose a way to register a tool from outside the agent, AC-10.2.2 is provably untestable from Python and must bounce back to product-owner (see Risks). For this design we assume `hu_hula_ctx_t` either carries an in-memory tool registry or `run_json` accepts a tools array — confirmation needed before implementation.

## Public Python surface (the contract the implementer locks in)

```python
# human_hula/__init__.py
from .context import HulaContext
from .errors import HulaError
__version__ = "0.2.0"  # tracks SDK version from US-10.1

# human_hula/errors.py
class HulaError(Exception):
    code: int       # raw hu_error_t value
    name: str       # e.g. "HU_ERR_INVALID_ARGUMENT" (resolved via error_string)
    message: str    # same as .name in v0.2.0; reserved for future expansion

# human_hula/context.py
class HulaContext:
    def __init__(self, lib_path: str | None = None) -> None: ...
    def __enter__(self) -> "HulaContext": ...
    def __exit__(self, exc_type, exc, tb) -> None: ...
    def close(self) -> None: ...                                   # idempotent
    def run_json(self, program_json: str) -> str | None: ...       # returns root output; None if no output
    @staticmethod
    def sdk_version() -> str: ...                                  # reads HU_HULA_SDK_VERSION_STRING
```

The ctypes glue in `_lib.py` declares exactly four C entry points:

| C function | argtypes | restype |
|---|---|---|
| `hu_hula_ctx_create` | `(c_void_p,)` (allocator ptr; pass `None` → default) | `c_void_p` (ctx handle) |
| `hu_hula_ctx_destroy` | `(c_void_p,)` | `None` |
| `hu_hula_error_string` | `(c_int,)` | `c_char_p` |
| `hu_hula_sdk_run_json` | `(c_void_p, c_char_p, c_size_t, c_void_p, c_size_t, c_void_p, c_void_p, POINTER(c_char_p), POINTER(c_size_t))` | `c_int` |

Note: the v0.2.0 header is expected to ship a context-aware wrapper (`hu_hula_ctx_run_json` or similar) that hides the tools / policy / observer arguments. If it does not, the binding will pass `NULL` for `tools`, `tools_count=0`, `policy=NULL`, `observer=NULL` — which is allowed by the current header (`hu_hula_sdk_run_json` accepts zero tools and skips registry validation). **This is the call shape used until US-10.1 provides a ctx wrapper.**

## Implementation steps (for the implementer agent)

1. **Verify the precondition.** `ls build/libhuman_hula.{so,dylib}` after `cmake --preset dev && cmake --build --preset dev`. If absent, stop and surface to lead — US-10.1 has not finished its work.
2. **Skeleton package.** Create `bindings/python/pyproject.toml`, empty `human_hula/__init__.py`, empty `tests/test_bindings.py`. Confirm `pip install -e bindings/python/` exits 0 (AC-10.2.1 skeleton check).
3. **Library loader in `_lib.py`.** Three-step probe: `$HUMAN_HULA_LIB` → repo-relative `build/libhuman_hula.*` → `ctypes.util.find_library("human_hula")`. Raise `HulaError(code=-1, name="HU_ERR_LIB_NOT_FOUND", message="…helpful…")` on miss.
4. **Declare argtypes/restype** for the four C entry points listed above. Add `_check_err(code: int) -> None` that consults `hu_hula_error_string`, raising `HulaError` for any nonzero code.
5. **Write the failing tests first** (AC-10.2.3 set):
   - `test_context_create_and_destroy` (ctx round-trip)
   - `test_run_json_single_call_returns_string`
   - `test_run_json_seq_returns_string`
   - `test_run_json_malformed_raises_hula_error` ← AC-10.2.5, MUST assert exception IS raised; see anti-pattern note below
   - `test_error_string_returns_non_empty_for_invalid_argument`
   - `test_context_manager_closes_on_exit`
6. **Implement `HulaContext` and `HulaError`** until all six tests pass.
7. **Write `examples/hello_hula.py`**; run it manually; confirm non-empty stdout and exit 0 (AC-10.2.4).
8. **Verify gates:** `pip install -e bindings/python/`, `pytest bindings/python/tests/ -v`, `python bindings/python/examples/hello_hula.py`. Then re-run the full C suite (`./build/human_tests`) to confirm AC-10.2.6 — the binding must be fully additive.
9. **Run `/verify`** with the full AC matrix to capture evidence.

## Risks

| Risk | Probability | Impact | Mitigation |
|---|---|---|---|
| **Shared library not built.** Current `CMakeLists.txt` only builds STATIC targets. If US-10.1 does not add `add_library(human_hula SHARED …)`, AC-10.2.1 / .2 / .4 are all unsatisfiable. | **HIGH** | **LARGE** | Precondition check in step 1. Coordinate with US-10.1 implementer to confirm SHARED target lands. If it does not, **BLOCK** US-10.2 and bounce to scrum-master. |
| **Tool registration not exposed from C.** AC-10.2.2 calls a `tool: "echo"`. If `hu_hula_sdk_run_json` cannot accept tools registered from Python (no public API to build a `hu_tool_t` from outside the agent), this AC cannot pass via ctypes alone. | **MEDIUM** | **MEDIUM** | Option A (preferred): drop the tool from the AC-10.2.2 example to a no-tool program (`emit` only — opcode does not need a registry). Option B: US-10.1 exposes a stub-tool helper `hu_hula_sdk_register_echo_tool(ctx)` for binding tests. Decision needed from product-owner before implementation. |
| **Symbol visibility on the shared lib.** Static-inline helpers in `hula_sdk.h` will not be exported as ELF/Mach-O symbols. Only the v0.2.0 *non-inline* entry points (`hu_hula_ctx_create`, `hu_hula_ctx_destroy`, `hu_hula_error_string`, and ideally `hu_hula_ctx_run_json`) will be callable from ctypes. | MEDIUM | MEDIUM | Confirm US-10.1 lands these as non-inline functions in a `.c` file, not just `static inline` in the header. If they remain `static inline`, the shared lib cannot expose them. |
| **Library path on macOS (`@rpath`, code-signed Python).** macOS Python (especially Homebrew / system) restricts `DYLD_LIBRARY_PATH`. `find_library` may return None even when the lib exists. | MEDIUM | SMALL | Explicit `HUMAN_HULA_LIB` env override documented in README. Repo-relative fallback walks up from `__file__` to find `build/libhuman_hula.dylib`. |
| **Test pins a bug (anti-pattern).** AC-10.2.5 demands "malformed JSON raises `HulaError`". A test that asserts `result is None` or `ctx.run_json(bad) == ""` would pin the bug instead of catching it. | LOW | LARGE | `test_run_json_malformed_raises_hula_error` MUST use `with pytest.raises(HulaError) as exc_info:` and assert `exc_info.value.code != 0`. See `.claude/rules/tests-that-pin-bugs.md`. Reviewed as part of implementer's per-task gate. |
| **Memory leak in `result_out`.** `hu_hula_sdk_run_json` returns an `alloc->alloc`'d buffer the caller must free. ctypes will not auto-free. | MEDIUM | SMALL | `_lib.py` copies the C buffer to a Python `bytes`/`str` and immediately calls `alloc->free` via a small exported `hu_hula_sdk_free_result` helper (request US-10.1 add it) **or** uses `ctypes.c_char_p` + manual `free` via `libc.free` (less portable). Prefer the SDK helper. |
| **Concurrency.** `HulaContext` is not thread-safe in v0.2.0. | LOW | SMALL | Document "one context per thread" in README. No `threading.Lock` — adds cost for a guarantee we do not promise. |
| **Backward compat.** No existing Python callers (new package). | n/a | n/a | n/a |
| **Observability.** ctypes errors at load time are notoriously cryptic. | LOW | SMALL | Loader emits the candidate paths it tried in the exception message; example script prints `__version__` and the resolved lib path before running. |

### Risks requiring resolution before implementation starts

1. **Shared library target lands in US-10.1** (HIGH probability of blocking).
2. **Tool-registry exposure** for AC-10.2.2 — choose Option A (drop tool) or Option B (helper). Recommend Option A: rewrite the AC-10.2.2 example to use an `emit` opcode, which needs no tool registry. This is cleaner and keeps the binding decoupled from agent internals.
3. **`hu_hula_sdk_free_result` helper** — needs to be added in US-10.1 or the binding leaks per-call.

If items 2 or 3 are not acceptable, this story bounces to product-owner with `NEEDS_AC_REFINEMENT`.

## Test strategy

**Unit + integration tests in `bindings/python/tests/test_bindings.py`** (six tests, listed in step 5). Tests skip cleanly if `libhuman_hula` is not discoverable (the precondition check in `conftest.py`) so CI can give a clear "missing precondition" signal rather than an opaque ImportError.

**No mocking of the C library.** The whole point of the binding is to call real C; a mocked test would assert nothing useful. The skip-if-missing pattern is the only acceptable bypass.

**Full C suite re-run** is required (AC-10.2.6) — the binding is additive, but the implementer must prove it. Add `./build/human_tests` to the `/verify` evidence bundle.

**No fuzz target** for the binding in this story (`bindings/python/` is not in the fuzz harness scope; the C layer is already fuzzed via `fuzz/`).

This is a P2 cosmetic issue; not blocking.

## What this design explicitly does NOT include

- Tool registration from Python (out of scope; see Risks)
- Async / threading support (out of scope per story)
- PyPI publish wheels (out of scope per story)
- `Program` builder class (AC-10.2.2 imports it but never uses it; treat as a future iteration — implementer may add an empty `Program` placeholder solely to satisfy the import, or bounce the AC)
- numpy / pandas integration (out of scope per story)
- Type stubs (.pyi) — recommended but not required by any AC; defer to follow-up unless P0
