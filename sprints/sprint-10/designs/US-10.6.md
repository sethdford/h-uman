# Design for US-10.6: Bindings CI integration

## Approach

Add a single new job `bindings` to `.github/workflows/ci.yml` rather than introducing
a separate workflow file. Rationale: bindings are tightly coupled to the C SDK
(`include/human/hula_sdk.h` + shared library output from the main CMake build), so
co-locating them in `ci.yml` keeps the dependency graph honest — when the SDK
header changes, the same workflow that compiles C also exercises the bindings.
A separate workflow file would split that signal across two CI runs and double
the maintenance surface for runner setup.

The job is a matrix over `ubuntu-latest` and `macos-latest` (mirroring
`build-and-test`). Each runner: (1) builds the shared library via the existing
`setup-build` composite action with the same flags as the main matrix, (2) runs
the Python binding test sequence (`pip install -e bindings/python/` then
`pytest bindings/python/tests/`), (3) runs the TypeScript binding test sequence
(`npm --prefix bindings/typescript install` then `npm --prefix bindings/typescript test`).
Sequence — not parallel — because AC-10.6.1 specifies sequential execution and
because both bindings link against the same just-built shared library; parallel
runs would gain nothing and complicate cache scoping.

Path filtering (AC-10.6.4) is enforced at the job level via a `paths` filter
on the workflow trigger. Caching uses the first-party `actions/setup-python@v5`
(`cache: pip`) and `actions/setup-node@v4` (`cache: npm`) — both are
keyed off lockfiles and require no manual cache-key arithmetic. Failure semantics
are **default GitHub Actions**: no `continue-on-error`, no `if: always()` —
a non-zero exit from `pytest` or `npm test` reds the job, which reds the
workflow, which blocks merge (AC-10.6.2).

## Path-filter approach (decision)

GitHub Actions does not support per-job `paths` filters natively when the
workflow trigger already fires on `push:` / `pull_request:` globally. Two
options:

1. **`dorny/paths-filter@v3`** as a preflight job that outputs `bindings-changed`,
   gated on `if: needs.changes.outputs.bindings == 'true'`.
2. **A second workflow file** `bindings.yml` with `on.pull_request.paths`.

**Pick option 1.** It keeps the workflow surface area in one file (matches
existing CI pattern), uses a well-known action, and the preflight job runs in
~5 seconds. Option 2 is what we explicitly rejected in the Approach section.

## Implementation steps (for the implementer agent)

1. **Add `changes` preflight job** to `ci.yml` using `dorny/paths-filter@v3` with
   filter outputs for `bindings: bindings/**` and `sdk: include/human/hula_sdk.h`.
   Output a single combined boolean `bindings_or_sdk`.
2. **Add `bindings` job** with `needs: changes` and
   `if: needs.changes.outputs.bindings_or_sdk == 'true'`.
3. **Matrix:** `os: [ubuntu-latest, macos-latest]`.
4. **Steps in order:**
   - `actions/checkout@v6`
   - `actions/setup-python@v5` with `python-version: '3.11'` and `cache: pip`
   - `actions/setup-node@v4` with `node-version: '20'` and `cache: npm` plus
     `cache-dependency-path: bindings/typescript/package-lock.json`
   - `./.github/actions/setup-build` (reuse existing composite) with the same
     flags as `build-and-test` so the shared library lands in `build/`
   - Step: `pip install -e bindings/python/`
   - Step: `pytest bindings/python/tests/ -v` (working dir = repo root)
   - Step: `npm --prefix bindings/typescript ci` (use `ci` not `install` for
     deterministic CI installs from lockfile)
   - Step: `npm --prefix bindings/typescript test`
5. **No `continue-on-error: true` anywhere** in the new job.
6. **Verify path filter** by pushing a no-op commit touching only `README.md` —
   the `bindings` job should be skipped (visible as "Skipped" in the Actions UI).
7. **Verify failure mode** by temporarily deleting a symbol used by a Python
   test from `include/human/hula_sdk.h` on a scratch branch — the job MUST fail.
   Revert before merge. (AC-10.6.2 falsifiability check.)
8. **Run `gh workflow list`** locally on the branch after push to confirm the
   workflow parses (jobs list shows `bindings`).

## Test seam

The workflow file IS the test seam. There is no unit-testable function here.
Verification is operational:

| Check | How |
|---|---|
| Workflow YAML parses | `actionlint .github/workflows/ci.yml` (already in repo tooling) |
| Job visible | `gh workflow view ci.yml --yaml \| grep '^  bindings:'` |
| Job runs on branch | Push to `sprint-10-hula-platform`; check `gh run list` |
| Job goes red on broken binding | Falsifiability test in step 7 above |
| Path filter works | Pure-docs commit shows `bindings` as skipped |

## Risks

- **Backward compat (LOW/SMALL).** New job is additive. Existing jobs are
  untouched. The new `changes` preflight job adds ~5s to every CI run but does
  not gate any existing job. **Mitigation:** the `changes` job has no
  dependencies of its own; if `dorny/paths-filter` ever breaks, fail-open by
  defaulting outputs to `'true'`.

- **Dependency on US-10.2 / US-10.3 (MED/MEDIUM).** This job cannot land until
  `bindings/python/` and `bindings/typescript/` exist with passing tests. **Mitigation:**
  Wave 2 sequencing — implementer must verify both directory trees exist with
  green local test runs before opening the PR for US-10.6. If US-10.2/US-10.3
  slip, US-10.6 slips with them; no partial landing.

- **Cache miss does not skip tests (LOW/SMALL).** Risk from
  `~/.claude/rules/quality-gates.md`: caches must accelerate, not gate.
  **Mitigation:** `actions/setup-python` and `actions/setup-node` caches are
  read-through — a cache miss still runs `pip install` / `npm ci`, which then
  runs the test step unconditionally. Verify by inspecting workflow run logs:
  `pytest` and `npm test` steps must appear in the step list on both cache-hit
  and cache-miss runs.

- **Cross-platform binding portability (MED/MEDIUM).** Python ctypes and
  TypeScript ffi-napi resolve the shared library extension differently on
  Linux (`.so`) vs macOS (`.dylib`). AC-10.6.3 demands both pass. **Mitigation:**
  this is a US-10.2 / US-10.3 implementation concern, NOT a CI concern. If the
  bindings have a hard-coded extension, the matrix will catch it — which is
  exactly what AC-10.6.3 wants. No CI-side mitigation needed; flag to the
  bindings implementer.

- **Shared library path discovery (MED/SMALL).** Bindings need to know where
  `build/libhuman.{so,dylib}` lives. Hardcoding `build/` couples to the C build
  step ordering. **Mitigation:** Export `HU_SHARED_LIB_PATH=$GITHUB_WORKSPACE/build`
  in a step before the bindings tests; require US-10.2 / US-10.3 to honor that env
  var. Document in the design hand-off.

- **`pytest`/`vitest` not installed (LOW/SMALL).** Tests need their own
  dev-dependencies declared. **Mitigation:** `pip install -e bindings/python/[test]`
  with an extras_require, and `npm ci` reads `devDependencies` from
  `bindings/typescript/package.json`. Verify with US-10.2 / US-10.3 implementers
  that those files declare test deps; otherwise the install step itself fails
  loudly (acceptable — the failure is honest).

- **CI flake from npm registry / PyPI (LOW/SMALL).** Network failures during
  install. **Mitigation:** `npm ci` is deterministic from lockfile; pip cache
  reduces PyPI calls. Re-run policy is the project default; do NOT add
  `continue-on-error`.

- **Observability (LOW).** Per CLAUDE.md monitoring: how do we know the job
  is working? **Mitigation:** the `gh workflow list` + `gh run list` pair
  shows the job status. No dashboard needed for a CI job.

## Test strategy

Operational verification, not unit tests:

1. **YAML lint:** `actionlint .github/workflows/ci.yml` exits 0.
2. **Workflow enumeration:** `gh workflow view ci.yml` shows the new job.
3. **Green on branch (AC-10.6.5):** push to `sprint-10-hula-platform`, observe
   `bindings (ubuntu-latest)` and `bindings (macos-latest)` both green.
4. **Falsifiability (AC-10.6.2):** scratch branch where one symbol is removed
   from `hula_sdk.h`; observe red job; revert before merge. Document the run
   ID in the PR description as evidence.
5. **Path filter (AC-10.6.4):** scratch commit touching only `README.md`;
   observe `bindings` shown as "Skipped" in the Actions UI.

## Acceptance criteria mapping

| AC | How satisfied |
|---|---|
| AC-10.6.1 (job runs both binding test commands sequentially, both must exit 0) | Implementation step 4; no `continue-on-error` |
| AC-10.6.2 (broken binding fails CI) | Falsifiability check in step 7; documented in Test strategy item 4 |
| AC-10.6.3 (both ubuntu-latest and macos-latest pass) | Matrix in step 3; green-on-branch check |
| AC-10.6.4 (path filter on `bindings/**` and `hula_sdk.h`) | `changes` preflight job + `if:` guard (steps 1–2); verified by Test strategy item 5 |
| AC-10.6.5 (green on sprint-10-hula-platform before merge) | Implementer pushes branch, confirms green run, attaches run URL to PR |

## Anti-patterns explicitly avoided

- ❌ `continue-on-error: true` on the bindings job — would silently let a broken
  binding through. **Not used.**
- ❌ `if: always()` after a test step — would mask failures. **Not used.**
- ❌ Caching that gates test execution — the cache steps in this design are
  read-through; tests run on cache-miss too. **Verified.**
- ❌ Splitting the workflow file — would fragment CI signal. **Single ci.yml job.**
- ❌ Speculative Windows runner — out of scope per story line 184. **Not added.**

## Hand-off notes for the implementer

- The shared library output path from `setup-build` composite is `build/` —
  confirm by reading `.github/actions/setup-build/action.yml` before writing
  the env-var export.
- Use `npm ci`, not `npm install`, in CI — deterministic, fails on lockfile
  drift.
- Use `pytest -v` so AC-10.6.1's per-test pass/fail is visible in logs.
- Do not run `bindings` on `schedule:` or `workflow_dispatch:` triggers unless
  explicitly asked — keep it tied to push/PR with the path filter.
- After the workflow lands, update `sprints/sprint-10/stories.md` US-10.6 DoD
  with the green run URL.
