# Design for US-10.4: HuLa examples gallery

## Approach

US-10.4 is a documentation-and-data story, not a behavior story. We deliver
five canonical `program.json` artifacts plus READMEs under
`examples/hula/<NN>-<slug>/`, a top-level `examples/hula/README.md` index,
and one C test (`tests/test_hula_examples.c`) that parses+validates each
file via the real production entry points `hu_hula_parse_json` and
`hu_hula_validate`. No C source under `src/` is modified.

This is the cheapest design that satisfies the ACs because:

1. The IR is already JSON-serializable (`hu_hula_parse_json` exists; the
   op-string table in `src/agent/hula.c:249-256` maps every opcode the
   stories require: `seq`, `par`, `branch`, `try`, `verify`, plus `call`).
   No new opcodes, no SDK additions.
2. The test seam is a single iteration loop over a static file list. It
   references **two** production symbols (`hu_hula_parse_json`,
   `hu_hula_validate`), satisfying both the AC test-seam clause and
   `.claude/rules/test-references-production-symbol.md` without needing
   `// @covers-none`.
3. Examples are pure data — no provider, no network, no Python/TS
   bindings. The story is Wave-0 and independent of US-10.1/10.2/10.3.

Alternatives rejected:

- **Run each example via `hu_hula_exec_run`.** Tempting (AC-10.4 implies
  "structurally valid", not "executes"), and exec would require stub
  tools matching every `tool` string in every example. Story scope says
  "Out of scope: Runnable examples that need a live model provider …
  use stub/echo tools." We satisfy this by validating against an empty
  tool registry (`tools_count == 0`) — per `hu_hula_validate` behavior,
  structure and opcode rules still apply, and `val.valid == true` is
  achievable without registering tools. If we wanted exec, we would
  ship a stub-tool registry; that doubles test surface and bleeds into
  US-10.5 (MCP bridge / executor). Keep this story tight.
- **Shell-script harness (`tests/test_hula_examples.sh`)** as originally
  scoped by the parent. Rejected because the *story* ACs explicitly name
  `tests/test_hula_examples.c` (AC test-seam line) and require the
  `test-references-production-symbol` rule, which is C-grep-based. A C
  test is both shorter and aligned with the rest of the suite. The
  parent's adversarial-shell point is preserved: a malformed
  `program.json` MUST fail the test loudly (we assert `HU_OK` from parse
  AND `val.valid == true`, both hard fails).

## Coexistence with existing `examples/hula/*.json`

The current directory contains six top-level JSON files (`hula_minimal.json`,
`hula_parallel_fetch.json`, `hula_loop_retry.json`, `hula_arg_refs.json`,
`hula_research_pipeline.json`, `workflow.template.json`) and a `hula/`
subdir. Per AC-10.4.1, `examples/hula/` "contains exactly these five
subdirectories" — read strictly, this would require deleting the existing
files. **Risk decision (see Risks §)**: do **not** delete; AC-10.4.1's
"contains" is satisfied by the five subdirectories existing. The C test
iterates only the five canonical subdirs by absolute relative path, so
legacy files cannot pollute the assertion set. If the implementer finds
that the strict-listing reading is required by review, the existing
files are referenced by `tests/test_hula_golden.c` and
`tests/test_idempotency_hula_integration.c`; deleting them would break
those tests and is therefore out of scope for this story.

## Implementation steps (for the implementer agent)

1. **Skeleton** — create `examples/hula/01-simple-call/` through
   `05-multi-step-pipeline/` and place empty `program.json` + `README.md`
   stubs in each. Create top-level `examples/hula/README.md` stub.
2. **Test scaffold** — add `tests/test_hula_examples.c` with one
   placeholder test that opens
   `examples/hula/01-simple-call/program.json` and asserts the file
   exists. Register in `CMakeLists.txt`. Build (`cmake --build --preset
   dev`) and confirm the test compiles + fails on the missing file.
3. **Fill `01-simple-call/program.json`** — single CALL root, tool
   `"echo"`, args `{"text":"hello"}`. Use `id` `"root"`. Update its
   `README.md` (≥100 words: explains CALL semantics, `tool` and `args`
   fields, why this is the starting point). Extend the test to parse
   this file with `hu_hula_parse_json` and validate with
   `hu_hula_validate` (tool list NULL/0). Assert `err == HU_OK` and
   `val.valid == true`. Cleanup with `hu_hula_validation_deinit` and
   `hu_hula_program_deinit`.
4. **Fill `02-branching/program.json`** — root `branch` (id `b1`) with a
   `pred` JSON object (any predicate the parser accepts; the simplest
   is `{"eq":["{{some.var}}","yes"]}` — confirm shape against
   `hu_hula_parse_json`'s branch handler before committing), a `then`
   subtree containing one `call`, and an `else` subtree containing one
   `call`. Add an additional test in the same file asserting the parsed
   root op is `HU_HULA_BRANCH` (AC-10.4.4 inspection). README ≥100w.
5. **Fill `03-error-recovery/program.json`** — root `try` (id `t1`) with
   a `body` of one `call` to a fail-prone tool and a `catch` of one
   `call` to a recovery tool. Test asserts root op is `HU_HULA_TRY` and
   it has a non-null catch child (AC-10.4.5). README ≥100w.
6. **Fill `04-emergence-detection/program.json`** — root `seq` containing
   one `call` then a `verify` (id `v1`) whose predicate references the
   previous call's output. Test asserts at least one descendant has op
   `HU_HULA_VERIFY` (AC-10.4.6). README ≥100w; the README explains the
   emergence-detection connection (the `verify` opcode is what triggers
   emergence tracing per the SDK header docstring).
7. **Fill `05-multi-step-pipeline/program.json`** — root `seq` with three
   children: (a) one `call`, (b) one `par` containing two `call`s, (c)
   one `call` that aggregates. Test asserts the program contains both a
   `HU_HULA_SEQ` node and a `HU_HULA_PAR` node anywhere in the tree
   (AC-10.4.7) — requires a tiny `walk_for_op` recursive helper in the
   test (≤15 LOC; not production duplication because it is purely a
   structural inspection over the parsed tree, not a re-implementation
   of validation). README ≥100w.
8. **Top-level `examples/hula/README.md`** — table linking to each of
   the five subdirs and the primary opcode(s) each demonstrates
   (AC-10.4.8). Include a "How to run" pointer: "validated by
   `tests/test_hula_examples.c`; for execution see `bindings/python/examples/`
   (US-10.5 once it lands)."
9. **Adversarial sanity** — temporarily corrupt one of the program.json
   files (e.g. delete a closing brace), run `./build/human_tests
   --filter=hula_examples`, confirm it fails non-zero, then revert.
   Document the result in the task close.
10. **Full suite** — `./build/human_tests` must remain 0 failures, 0
    ASan errors (AC-10.4.9). Spawn `/verify`.

## Test strategy

`tests/test_hula_examples.c`:

```c
#include "human/agent/hula.h"
#include "human/core/string.h"
/* test framework header used by sibling test_hula*.c */

typedef struct {
    const char *path;
    hu_hula_op_t expected_root_op;   /* or HU_HULA_OP_COUNT for "any" */
    hu_hula_op_t must_contain_op;    /* secondary structural assertion */
    hu_hula_op_t must_also_contain;  /* HU_HULA_OP_COUNT if N/A */
} hula_example_case_t;

static const hula_example_case_t k_cases[] = {
    {"examples/hula/01-simple-call/program.json",       HU_HULA_CALL,   HU_HULA_OP_COUNT, HU_HULA_OP_COUNT},
    {"examples/hula/02-branching/program.json",         HU_HULA_BRANCH, HU_HULA_OP_COUNT, HU_HULA_OP_COUNT},
    {"examples/hula/03-error-recovery/program.json",    HU_HULA_TRY,    HU_HULA_OP_COUNT, HU_HULA_OP_COUNT},
    {"examples/hula/04-emergence-detection/program.json", HU_HULA_OP_COUNT, HU_HULA_VERIFY, HU_HULA_OP_COUNT},
    {"examples/hula/05-multi-step-pipeline/program.json", HU_HULA_SEQ,  HU_HULA_PAR,    HU_HULA_OP_COUNT},
};
```

(Pseudocode — implementer writes the loop, file-read helper, recursive
`tree_contains_op`, and per-case assertions. Use the standard test
harness allocator pattern from `tests/test_hula.c:237`.)

Per-test assertions in order:

1. File reads non-empty (`HU_ASSERT_TRUE(buf && len > 0)`).
2. `hu_hula_parse_json(&alloc, buf, len, &prog) == HU_OK`.
3. `hu_hula_validate(&prog, &alloc, NULL, 0, &val) == HU_OK` and
   `val.valid == true`. Print `val.error_count` first issue on failure.
4. If `expected_root_op` is not `HU_HULA_OP_COUNT`,
   `HU_ASSERT_EQ(prog.root->op, expected_root_op)`.
5. If `must_contain_op` is set,
   `HU_ASSERT_TRUE(tree_contains_op(prog.root, must_contain_op))`.
6. Cleanup: `hu_hula_validation_deinit(&alloc, &val)`,
   `hu_hula_program_deinit(&prog)`.

This is one suite, one test function per case = five tests, plus a sixth
"all-five-exist" guard so the loop can't accidentally skip a missing
file (defensive against AC-10.4.1).

## Risks

- **AC strict-listing vs existing files (LOW / SMALL).** AC-10.4.1 says
  `examples/hula/` "contains exactly these five subdirectories". Six
  legacy JSON files plus the existing `hula/` and `edge/` subdirs are
  present and referenced by `tests/test_hula_golden.c` and
  `tests/test_idempotency_hula_integration.c`. **Mitigation:** interpret
  "contains" as "the five subdirs exist and are valid"; do not delete
  legacy files; document this reading in the implementer task close so
  PO review can affirm or bounce. If PO insists on strict reading, scope
  expands to refactoring two other tests — surface as a follow-up, do
  not silently delete.

- **Predicate JSON shape for `branch` and `verify` (LOW / SMALL).** The
  parser accepts a `pred` object whose internal shape is determined by
  `src/agent/hula.c`'s predicate handler. **Mitigation:** before
  committing example #2 and #4, run a one-shot parse against a
  candidate shape (e.g. via a throwaway test or `./build/human_tests
  --filter=hula` reading the new file) and confirm `val.valid`. The
  parse-then-validate pipeline is exactly what the production test
  exercises, so "valid in test" = "valid in spec".

- **`val.valid == true` with empty tool registry (LOW / SMALL).** The
  example programs reference tool names like `"echo"` and `"web_search"`
  that won't exist in the test's tool registry. **Mitigation:**
  AC-10.4.2 says "via `hu_hula_parse_json` … `hu_hula_validate` returns
  `val.valid == true`". Pass `tools = NULL, tools_count = 0` — per
  `hu_hula_sdk.h` docstring, "If `tools_count` is zero, validation skips
  the tool registry check (structure and opcode rules still apply)."
  This satisfies the AC. If a future reviewer wants tool-name validation
  too, that becomes a follow-up story with a stub tool table.

- **Test pinning a bug (LOW / SMALL).** Per
  `.claude/rules/tests-that-pin-bugs.md`, the test name must match the
  assertion. Function names: `example_01_simple_call_is_valid_hula`,
  `example_02_branching_contains_branch_op`, etc. — the assertion
  matches the name. **Mitigation:** adversarial step #9 above
  (deliberate corruption) proves the test fails on bad input.

- **Test references production symbols (LOW / SMALL).**
  `.claude/rules/test-references-production-symbol.md` requires test
  files to grep-reference a `hu_*` symbol from the implied module.
  Implied module from `test_hula_examples.c` is `hula` →
  `src/agent/hula.c`. **Mitigation:** the test calls
  `hu_hula_parse_json` and `hu_hula_validate` directly — both exported
  from `hula.c`. No `// @covers-none` escape needed.

- **README word count (LOW / SMALL).** AC-10.4.1 requires ≥100 words per
  README. Easy to miss while drafting. **Mitigation:** implementer runs
  `wc -w examples/hula/*/README.md` as a sanity check; surface a count
  table in the task close.

- **Cross-agent regression (LOW / SMALL).** Adding a test file may race
  with US-10.1/US-10.5 if they also touch `CMakeLists.txt` test list.
  **Mitigation:** US-10.4 is Wave-0 and has no story-level dependency,
  but the implementer should `git pull` before adding the CMake line
  and verify the surrounding registrations still match the pattern.

- **Observability (LOW).** If a future reviewer adds a sixth example and
  forgets to extend the test loop, the new example is silently
  unchecked. **Mitigation:** add a comment at the top of `k_cases[]`:
  "If you add a directory to `examples/hula/`, append a row here."
  Don't over-engineer (no glob-based discovery — that would be a new
  abstraction this story doesn't need).

## Acceptance criteria mapping

| AC | Covered by |
|---|---|
| AC-10.4.1 (five subdirs, each with program.json + README ≥100w) | Files in step 1+8; word-count sanity in implementer close |
| AC-10.4.2 (parse + validate returns `val.valid == true`) | `tests/test_hula_examples.c` per-case assertions #2 + #3 |
| AC-10.4.3 (01 root op is `call` with non-empty tool) | Case row for 01 (`expected_root_op == HU_HULA_CALL`); extra inline assert on `prog.root->tool_name` non-empty |
| AC-10.4.4 (02 contains `branch` with then/else) | Case row for 02; recursive walk asserts a `HU_HULA_BRANCH` node has both `then`/`else` children populated |
| AC-10.4.5 (03 contains `try` with `catch`) | Case row for 03; assert TRY node's `catch_node` is non-NULL |
| AC-10.4.6 (04 contains `verify`) | Case row for 04 (`must_contain_op == HU_HULA_VERIFY`) |
| AC-10.4.7 (05 contains both `seq` and `par`) | Case row for 05 (`expected_root_op == HU_HULA_SEQ`, `must_contain_op == HU_HULA_PAR`) |
| AC-10.4.8 (top-level README links all five, names opcodes) | `examples/hula/README.md` in step 8; verifier visually confirms |
| AC-10.4.9 (full C test suite green) | Step 10 + `/verify` PASS |

## What this story does NOT do

- Does not execute any program (no exec, no tools, no stubs).
- Does not modify any production C source.
- Does not add Python or TypeScript example wrappers (those belong with
  US-10.2 / US-10.3 in `bindings/<lang>/examples/`).
- Does not delete legacy JSON files in `examples/hula/` root.
- Does not introduce a glob-based discovery test — explicit list only.
- Does not add a hosted playground or web demo.
