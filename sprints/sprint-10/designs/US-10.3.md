# Design for US-10.3: TypeScript/Node bindings (`bindings/typescript/`)

## Approach

Use **`ffi-napi`** (plus `ref-napi` for pointer/string handling) to bind the
already-built `libhuman` shared library at runtime. This mirrors the Python
bindings' ctypes strategy from US-10.2: no C compilation at `npm install`
time, no native addon to rebuild per Node ABI version, and the binding code
stays at the SDK boundary (`hu_hula_ctx_create`, `hu_hula_sdk_run_json`,
`hu_hula_error_string`) — exactly the three entry points US-10.1 stabilizes.

A native N-API addon was considered and **rejected for v0.2.0**: it would
require `node-gyp`, a C toolchain on every developer's machine, and a
prebuilds matrix for distribution. The ACs do not demand throughput or
zero-copy buffers; they demand `import` works, `tsc --strict` passes, a
trivial round-trip program runs, and errors surface as a typed `HulaError`.
`ffi-napi` clears that bar with the smallest surface area. We document the
supported Node version range and revisit N-API in a later sprint only if
benchmark data justifies it.

The TS surface intentionally mirrors the Python `HulaContext` class shape
(constructor with an opaque handle, `runJson(programJson: string): Promise<string>`,
`close()` / disposable). Symmetry makes the docs single-source and reduces
review surface when both bindings change together.

## Implementation steps (for the implementer agent)

1. **Skeleton with no FFI** — write `package.json`, `tsconfig.json`,
   `src/index.ts` exporting a `HulaContext` class whose methods throw
   `new Error("not implemented")`, plus `HulaError`. Confirm
   `npm install` and `tsc --noEmit --strict` both exit 0 with no FFI
   yet wired up. This pins AC-10.3.1 and AC-10.3.6 before any native
   code is touched.
2. **Add library loader (`src/ffi.ts`)** — resolve the shared library
   path: prefer `process.env.HULA_LIB_PATH`, fall back to
   `path.resolve(__dirname, '../../../build/libhuman.dylib')` on darwin
   and `libhuman.so` elsewhere. Declare the three SDK functions with
   `ffi.Library(...)` using `ref` types. No exported behavior yet —
   just confirm the dlopen succeeds when invoked from a smoke test.
3. **Write the 5 vitest cases first (all should fail)** — mirror the
   Python contract: (a) ctx round-trip success, (b) malformed JSON
   rejects with `HulaError`, (c) `error.code` is a `hu_error_t` name
   string, (d) version-string accessor matches `0.1.0`, (e) ctx can
   be closed and re-used pattern (or disposable semantics).
4. **Implement `HulaContext.runJson`** — call `hu_hula_sdk_run_json`
   via FFI; if returned `hu_error_t` is non-zero, capture the int,
   look up its name via `hu_hula_error_string`, and reject the
   promise with a `HulaError(message, { code })`. On success,
   convert the returned `char *` to a JS string and free it via the
   allocator the binding owns. Pattern: wrap synchronous FFI in
   `Promise.resolve()` for AC-10.3.2's `await` signature (no worker
   thread needed for v0.2.0 — document the synchronous-under-the-hood
   note in README).
5. **Wire the example** — `examples/hello_hula.ts` instantiates a
   context, runs a trivial single-CALL program JSON, prints the
   result, exits 0. Matches AC-10.3.4.
6. **Self-check with `/verify`** — verifier runs
   `npm install && npm test && npx tsc --noEmit --strict && npx tsx examples/hello_hula.ts`
   in the worktree and reports PASS.

## Risks

- **Backward compat (LOW/SMALL)** — package does not exist yet; no
  callers. The TS surface is brand new. Mitigation: none needed; pin
  package version `0.2.0` matching the sprint.
- **`ffi-napi` Node runtime compatibility (MEDIUM/MEDIUM)** —
  `ffi-napi` historically lags Node major releases by 3–6 months and
  has known issues on Node ≥ 22 in certain configurations.
  **Mitigation:** declare `"engines": { "node": ">=18.18 <23" }` in
  `package.json`, document the supported range in README, run CI on
  Node 18 and 20 LTS only. If the implementer hits a load failure on
  the local Node version, fall back to Node 20.
- **Shared library path resolution (MEDIUM/SMALL)** — the dylib is
  built into `build/` by CMake; tests and examples may be run from
  arbitrary cwd. **Mitigation:** resolve relative to `__dirname`,
  not `process.cwd()`; allow `HULA_LIB_PATH` override; throw a clear
  `HulaError` with `.code = 'HU_ERR_LIBRARY_NOT_FOUND'` if dlopen
  fails, naming the path attempted.
- **Memory ownership across the FFI boundary (MEDIUM/MEDIUM)** —
  `hu_hula_sdk_run_json` allocates `result_out` via the caller's
  allocator and the caller must free it. In JS we receive a pointer;
  if we forget to free, every `runJson` leaks. **Mitigation:** the
  binding must always free in a `try/finally` immediately after
  copying the bytes to a JS string. Pin this with a vitest case that
  runs `runJson` in a loop ≥ 1000 times and asserts `process.memoryUsage().rss`
  stays bounded; gate on a sane delta, not an absolute number.
- **Error-shape regression — tests that pin a bug (LOW/MEDIUM)** —
  AC-10.3.5 requires `instanceof HulaError`. A weak test would
  assert `result === undefined` or `await ... .catch(() => true)`,
  silently passing if the rejection never fires. **Mitigation:**
  use vitest `expect(...).rejects.toThrow(HulaError)` and also
  assert `err.code` matches a known `hu_error_t` name regex. See
  `.claude/rules/tests-that-pin-bugs.md`.
- **Observability (LOW/SMALL)** — `HulaError.message` should include
  the `hu_error_t` name from `hu_hula_error_string`, not just a
  generic "runJson failed". Otherwise users debugging in production
  cannot tell `HU_ERR_INVALID_ARGUMENT` from `HU_ERR_OUT_OF_MEMORY`.

## Test strategy

vitest. Five+ cases, named to assert contracts (not labels):

- `runJson_returns_nonempty_string_for_valid_program`
- `runJson_rejects_with_HulaError_on_malformed_json`
- `HulaError_code_is_known_hu_error_t_name`
- `version_string_matches_sdk_constant`
- `context_can_be_disposed_and_recreated`
- (memory guard) `runJson_does_not_leak_over_1000_iterations`

No mocking of the library under test. All cases load the real
`libhuman` shared library built by CMake; if the library is missing,
the suite fails with a clear "build first" message — not skipped
silently.

## Dependencies

US-10.1 (Wave 0) must be merged first — the binding consumes
`hu_hula_ctx_create`, `hu_hula_sdk_run_json`, and `hu_hula_error_string`
as a stable surface. US-10.3 is Wave 1, parallel-safe with US-10.2
(Python bindings) and US-10.4 (examples gallery).

## Out of scope (explicit)

- WASM/browser bundle
- npm publish (sprint produces a publishable package; the publish
  step is a separate operational task)
- Deno or Bun support
- ESM/CJS dual-build beyond what `package.json` `exports` already
  provides
- Async tool execution running on a worker thread
- Streaming output
