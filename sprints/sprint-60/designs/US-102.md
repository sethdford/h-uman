# Design for US-102: Production Outcomes Table & DPO Pair Mining

## Approach

**Goal:** Automatically insert outbound messages into `production_outcomes` table and mine DPO pairs from implicit signals (reply latency, tapback polarity, user-edit status).

**Why this design:** The `production_outcomes` table already exists (verified at `src/ml/dpo.c:86`); all insertion functions (`hu_dpo_record_outbound`, `hu_dpo_record_outcome`, `hu_dpo_record_inbound_arrival`) are already wired. This design adds the ONE missing piece: **mining DPO pairs from resolved outcomes** via a new function `hu_dpo_collector_mine_pairs_from_outcomes()` called in the nightly LoRA job BEFORE training.

**Schema**: Table exists with all required columns. No ALTER needed; verify at runtime that columns are present.

**Insertion points (AC-102.2)**: Already wired at `src/daemon.c:11056` (outbound record) and `src/agent/reaction_handler.c:393` (outcome update). No new insertion logic needed.

**Mining logic (AC-102.6)**: New function queries `production_outcomes` WHERE `outcome_resolved_at IS NOT NULL AND processed_into_dpo = 0`, materializes DPO pairs deterministically (reply within 5min + sentiment > 0.6 = chosen; no reply after 24h = rejected), and inserts into `dpo_pairs` table.

**Integration (AC-102.7)**: Wire mining into existing nightly job at `src/daemon.c:4210` BEFORE training subprocess invocation.

**Test strategy**: Fixture-based in `tests/test_dpo_collector.c` — 5 synthetic `production_outcomes` rows (2 replied, 2 silent, 1 edited) → verify 2 pairs mined, all rows marked processed=1, pairs have correct source + contents.

## Implementation steps (for implementer agent)

1. **Create skeleton function** in `src/ml/dpo.c`:
   - Signature: `hu_error_t hu_dpo_collector_mine_pairs_from_outcomes(sqlite3 *db, int output_limit, int *pairs_written)`
   - Stub body returns `HU_OK` with `*pairs_written = 0`
   - Wire into header `include/human/ml/dpo.h`

2. **Implement mining query** (determinism-first):
   - SELECT `id, prompt, chosen, reply_length, reply_sentiment, tapback_polarity, outcome_resolved_at` FROM `production_outcomes` WHERE `outcome_resolved_at IS NOT NULL AND processed_into_dpo = 0` ORDER BY `id ASC` LIMIT output_limit
   - Iterate rows; for each contact, pair: **chosen** = (reply within 5min AND reply_sentiment > 0.6); **rejected** = (no reply AND outcome_resolved_at > send_timestamp + 86400)

3. **Insert pairs into dpo_pairs**:
   - Reuse `hu_dpo_record_pair()` with `source = "implicit_feedback"` for each pair
   - OR inline prepared statement: `INSERT INTO dpo_pairs(prompt, chosen, rejected, margin, timestamp, source) VALUES(?, ?, ?, 0.0, ?, 'implicit_feedback')`

4. **Mark rows processed** in same transaction:
   - `UPDATE production_outcomes SET processed_into_dpo = 1 WHERE id IN (SELECT id FROM production_outcomes WHERE outcome_resolved_at IS NOT NULL AND processed_into_dpo = 0) [LIMIT matched count]`

5. **Add test fixture** in `tests/test_dpo_collector.c`:
   - Create in-memory SQLite DB with DPO collector
   - Insert 5 `production_outcomes` rows with known timestamps, reply signals
   - Call mining function; assert 2 pairs, all rows marked processed=1

6. **Wire into nightly job** at `src/daemon.c:4210`:
   - Before `hu_lora_nightly_run()`, call: `hu_dpo_collector_mine_pairs_from_outcomes(db, INT_MAX, &pairs_mined)`
   - Log: `"mined {pairs_mined} pairs from production outcomes"`

7. **Run /verify** to confirm all tests pass + no ASan errors.

## Risks

### Risk 1: Sentiment classifier unavailable (MEDIUM/SMALL)
**What could go wrong**: AC-102.4 calls `hu_sentiment_classify()` or similar. If that function doesn't exist, outcome UPDATEs will set `reply_sentiment = 0.5` (stub). Mining pairs on `reply_sentiment > 0.6` will fail to materialize.

**Probability**: MEDIUM (sentiment classifier may not exist yet).

**Impact**: SMALL (test fixture just stubs sentiment to 0.7 or 0.3 as needed; real sentiment classification is follow-on work).

**Mitigation**: Define sentiment in mining predicate as `reply_sentiment IS NOT NULL AND reply_sentiment > 0.6`, defaulting to NULL when classifier unavailable. Mining still works with incomplete signals.

### Risk 2: Race condition on `processed_into_dpo` mark (LOW/MEDIUM)
**What could go wrong**: Between SELECT and UPDATE, another nightly job could insert/process rows. SQLite serialization handles it, but mark-and-insert is not atomic.

**Probability**: LOW (nightly runs at fixed 4 AM; daemon is single-threaded; unlikely collision).

**Impact**: MEDIUM (worst case: a pair is mined twice, dpo_pairs gets duplicates).

**Mitigation**: Wrap SELECT + INSERT + UPDATE in a transaction (BEGIN; ... COMMIT;). Determinism contract already requires this.

### Risk 3: DPO pair materialization misses contact context (LOW/MEDIUM)
**What could go wrong**: Mining logic pairs replies per **row**, not per **contact**. A contact with 3 unresolved outbounds + 1 reply will pair the reply with ALL 3 outbounds.

**Probability**: LOW (contacts send 1 message at a time in most cases; multi-send is rare).

**Impact**: MEDIUM (creates false (prompt, rejected) pairs).

**Mitigation**: Pair within contact by (`channel`, `target`): SELECT latest unresolved outbound per contact, pair its outcome with that row only. Query becomes: `WHERE outcome_resolved_at IS NOT NULL AND processed_into_dpo = 0 ORDER BY target, id ASC` → group by (channel, target) in application code.

## Test strategy

**Unit test** in `tests/test_dpo_collector.c`:
- Setup: 5 synthetic rows
  - Row 1: channel=imessage, target=alice, sent 100s ago, reply arrived 180s after (3min), reply_sentiment=0.8 → **CHOSEN**
  - Row 2: channel=imessage, target=alice, sent 200s ago, no reply → **REJECTED**
  - Row 3: channel=imessage, target=bob, sent 300s ago, no reply → **REJECTED**
  - Row 4: channel=imessage, target=bob, sent 400s ago, reply arrived 120s after (2min), reply_sentiment=0.75 → **CHOSEN**
  - Row 5: channel=imessage, target=charlie, sent 500s ago, user_edited=1 → skip (edited; not a clean pair)

- Call: `hu_dpo_collector_mine_pairs_from_outcomes(db, INT_MAX, &pairs_mined)`

- Assert:
  - `pairs_mined == 2`
  - 2 rows in `dpo_pairs` with `source = 'implicit_feedback'`
  - All 5 rows have `processed_into_dpo = 1`
  - Pair 1: prompt=row1.prompt, chosen=row1.chosen, rejected=row2.chosen (contact alice)
  - Pair 2: prompt=row3.prompt, chosen=row4.chosen, rejected=row3.chosen (contact bob)

**Integration**: nightly job gate (AC-102.7) wired; next nightly cycle mines and exports pairs.

## Out of scope

- **Sentiment classifier**: AC-102.4 mentions `hu_sentiment_classify()` but this function may not exist. If missing, stub to NULL and mining treats NULL as "no reply signal" (conservative).
- **Edit-before-send tracking**: AC-102.5 requires detecting user edits pre-send. Insertion point is `src/agent/agent_turn.c` or a pre-send validator. Out of scope for mining; ACs 102.3–102.6 assume the table is pre-populated.
- **Per-contact pairing logic**: Current spec pairs within outcomes per row. Per-contact grouping is a refinement.

## Determinism notes

Mining is **deterministic by design**:
- No floating-point arithmetic (only integer comparisons and timestamps).
- No randomness in pair selection (FIFO by ID, deterministic timestamp comparison).
- SQLite serialization ensures consistent reads.
- Same `production_outcomes` state → same DPO pairs every time.
- Transaction-wrapped UPDATEs ensure all-or-nothing outcome marking.
