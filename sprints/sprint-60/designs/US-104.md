# Design for US-104: Implicit Proactive Outcome Signals

## Approach

**Goal:** Track proactive message sends in a new `proactive_sends` table and feed implicit outcome signals (reply, ignored, blocked) to a Thompson-sampling contextual bandit for per-contact engagement prediction.

**Why this design:** The proactive/follow-up subsystem exists (`src/daemon_follow_up_watcher.c`, `src/follow_up.c`); AC-104 adds signal-ingestion and bandit integration. The `production_outcomes` table tracks outbound messages generally; `proactive_sends` is a **specialized subset** for proactivity learning, with additional columns (`outcome_type`, `processed`) to decouple proactive signal processing from general DPO mining.

**Schema**: New `proactive_sends` table with columns: `id`, `contact`, `message_ref`, `sent_timestamp`, `outcome_type` (NULL | HU_BANDIT_REPLY | HU_BANDIT_IGNORED | HU_BANDIT_BLOCKED), `outcome_timestamp`, `processed` (0 | 1).

**Insertion point (AC-104.1)**: When `hu_daemon_follow_up_watcher()` (or `hu_follow_up_send()`) sends a proactive, insert row into `proactive_sends` with channel + contact + message_ref + sent_timestamp.

**Signal ingestion (AC-104.2–104.4)**: 
- When reply arrives, UPDATE `proactive_sends` SET `outcome_type = HU_BANDIT_REPLY` (call to US-103 bandit API for outcome type enums).
- Async timer loop: if no reply after 24h, UPDATE `proactive_sends` SET `outcome_type = HU_BANDIT_IGNORED`.
- Block signal: if contact blocked, UPDATE with `HU_BANDIT_BLOCKED`.

**Async update loop (AC-104.5)**: New daemon tick or background worker queries `proactive_sends` WHERE `outcome_type IS NOT NULL AND processed = 0`, calls `hu_contextual_bandit_update(bandit, contact, outcome_type)` per row, marks `processed = 1`. Rate-limit: once per 60s.

**Test strategy**: Fixture-based in `tests/test_proactive_outcomes.c` — 3 rows (reply, ignored, blocked) → verify async processor calls bandit correctly and marks processed=1.

## Risks

### Risk 1: Outcome type enum mismatch (MEDIUM/MEDIUM)
**What could go wrong**: US-104 AC specifies `HU_BANDIT_REPLY`, `HU_BANDIT_IGNORED`, `HU_BANDIT_BLOCKED` as enum values. US-103 (contextual bandit) will define these. If the enum values don't match (e.g., US-103 uses `REPLY=10, IGNORED=20, BLOCKED=30` but AC-104 assumes `REPLY=1, IGNORED=2, BLOCKED=3`), the signal will be misrouted.

**Probability**: MEDIUM (two separate features define the enum; easy to drift).

**Impact**: MEDIUM (bandit receives wrong outcome type; learns incorrectly).

**Mitigation**: 
- Define enum at **one source of truth** (likely in a shared header like `include/human/daemon/contextual_bandit.h`).
- Both US-103 (bandit) and US-104 (signals) import the same header.
- Pin the enum values in the design doc (this design uses `HU_BANDIT_REPLY=1, IGNORED=2, BLOCKED=3` provisionally; US-103 must confirm).

### Risk 2: Double-update on outcome (LOW/MEDIUM)
**What could go wrong**: If a reply arrives at the same time the 24h timeout fires, the row could be updated twice (once to REPLY, once to IGNORED). The second UPDATE overwrites the first.

**Probability**: LOW (reply path is synchronous; 24h timeout is async; collision window is tiny).

**Impact**: MEDIUM (outcome changes from REPLY to IGNORED; bandit gets wrong signal).

**Mitigation**: UPDATE with condition `WHERE outcome_type IS NULL` so the second update fails if outcome_type is already set. Both UPDATE functions should use this guard.

### Risk 3: Config gate not logged (LOW/SMALL)
**What could go wrong**: AC-104 subsystem is config-gated (likely `cfg.proactive_bandit_enabled` or similar). If disabled silently, operator won't know why proactivity learning isn't happening.

**Probability**: LOW (implementer may forget to add the log).

**Impact**: SMALL (operator can inspect config; not a correctness bug).

**Mitigation**: Add one-shot log in the async processor tick: `hu_log_info_once(&warned, ..., "proactive outcome processor disabled by config; set proactive_bandit_enabled=true")` when gate is off.

## Test strategy

**Unit test** in `tests/test_proactive_outcomes.c`:
- Setup: 3 synthetic `proactive_sends` rows
  - Row 1: channel=imessage, contact=alice, sent 1000s ago, outcome_type=NULL (not yet resolved)
  - Row 2: channel=imessage, contact=bob, sent 1000s ago, outcome_type=HU_BANDIT_REPLY, processed=0
  - Row 3: channel=imessage, contact=charlie, sent 90000s ago (>24h), outcome_type=HU_BANDIT_IGNORED, processed=0

- Call: `hu_daemon_tick_proactive_outcomes(db, &mock_bandit)`

- Assert:
  - Row 1 unchanged (no outcome yet)
  - Row 2: bandit.update called with (alice, HU_BANDIT_REPLY), row marked processed=1
  - Row 3: bandit.update called with (charlie, HU_BANDIT_IGNORED), row marked processed=1
  - bandit.update call count == 2

**Fixture predicates**:
- Mock bandit: simple struct with `int call_count`, `int last_outcome_type`, `char last_contact[64]`
- Mock tracking allows test assertions without a real Thompson sampler

**Integration**: Next session, wire into live daemon tick loop; observe bandit state changes in production.

## Acceptance criteria mapping

- **AC-104.1** (Outbound tracking): `proactive_sends` table created; `hu_dpo_collector_insert_proactive_send()` called at send point.
- **AC-104.2** (Reply outcome): `hu_dpo_collector_update_proactive_outcome(outcome_type=HU_BANDIT_REPLY)` called when reply detected.
- **AC-104.3** (Ignored outcome): Background check marks rows where `sent_timestamp < (now - 86400)` as IGNORED.
- **AC-104.4** (Blocked outcome): When block signal received, call `hu_dpo_collector_update_proactive_outcome(outcome_type=HU_BANDIT_BLOCKED)`.
- **AC-104.5** (Async update loop): `hu_daemon_tick_proactive_outcomes()` runs at most once per 60s, calls bandit.update, marks processed=1.
- **AC-104.6** (Fixture test): 3 rows, all outcomes processed correctly.
- **AC-104.7** (Determinism): Outcome inference deterministic; no randomness in signal processing.

## Out of scope

- **Contextual bandit implementation** (US-103): This design assumes `hu_contextual_bandit_update(bandit, contact, outcome_type)` exists and returns HU_OK on success.
- **Contact blocking / muting detection**: AC-104.4 assumes a signal arrives when contact blocks. Finding that signal source is out of scope (may be iMessage reaction handler, daemon block watcher, etc.).
- **Thompson sampler tuning**: Bandit hyperparameters (α, β priors) are US-103's responsibility.

## Determinism notes

Outcome inference is **deterministic by design**:
- Reply detection: message_ref match is exact (no fuzzy matching).
- Ignored timeout: integer timestamp comparison (now > sent_timestamp + 86400).
- No floating-point arithmetic; no randomness.
- Same `proactive_sends` state → same bandit updates every time.
- Transaction-wrapped UPDATEs ensure all-or-nothing marking.
