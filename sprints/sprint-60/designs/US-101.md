# Design for US-101: Bradley-Terry Reward Model — HUML Toy Backbone

## Approach

US-101 implements Phase 3 Task 2: a **deterministic, gradient-checkable reward model** using a frozen HUML toy-GPT backbone with a trainable value head. The reward model scores (prompt, response) pairs via a single scalar for use in RL training (GRPO, KTO, DPO). Bradley-Terry loss (`-log σ(r_w - r_l)`) applies only to the value-head weights; the backbone is frozen per Christiano 2017 §2.2.

**Key design choices:**

1. **HUML backbone is last-position logits.** The toy GPT forward pass returns shape `[vocab_size]` at the final token position. This vector feeds directly to `hu_value_head_forward`, which projects to a scalar score. The hidden_dim equals vocab_size — no extra bottleneck, all logits are used.

2. **Value head is the ONLY learnable component.** Weights `W[hidden_dim]` and bias `b` are updated via SGD with Bradley-Terry gradients. The backbone (`hu_gpt_t`) stays frozen.

3. **String-based tokenization for testing & determinism.** Prompts and responses are space-separated decimal token IDs (mirrors KTO Task 4's reward_source rendering). No external tokenizer; tokens are parsed as `int` from the string. This ensures cross-platform determinism and makes gradient checks reproducible.

4. **Two separate source files for clarity:**
   - `src/ml/reward_model_huml.c` — factory, scoring, value-head wiring
   - `src/ml/reward_model_train.c` — Bradley-Terry loop, SGD, gradient step
   
   Both share `src/ml/reward_model_priv.h` for the private opaque context (private header is internal only, never installed).

5. **Gradient-checkable loss computation.** Bradley-Terry forward uses exact arithmetic (`double` accumulators internally) with no approximations or pooling. The analytical gradients match finite-difference gradients to 3 significant figures (rel. error < 0.001).

6. **Test seams: finite-difference gradient check, preference ranking, KTO handling.** Three test contracts: (a) backprop gradient matches FD to 1e-3 relative error on 3 batch sizes; (b) after training on 10 synthetic pairs with margin > 0.1, held-out pairs rank correctly 5/5 times across random seeds; (c) one-sided pairs (chosen_len=0 OR rejected_len=0) produce NaN outputs and are skipped in training with a stderr warning.

## Implementation steps (for the implementer agent)

1. **Create private header `src/ml/reward_model_priv.h`:**
   - Define `reward_model_huml_ctx_t` with: `hu_allocator_t`, `hu_gpt_t *gpt` (frozen), `hu_value_head_t vh` (trained)
   - Opaque to callers; used internally by train + score functions

2. **Scaffold `src/ml/reward_model_huml.c`:**
   - Implement `hu_reward_model_create_huml()`: allocate gpt via `hu_gpt_create()`, allocate value head via `hu_value_head_create()`, wrap in vtable
   - Implement `score()`: tokenize prompt/response as space-separated ints, call `gpt->forward()`, extract last-pos logits, call `hu_value_head_forward()`
   - Implement `score_batch()`: same as score() for chosen, rejected; handle one-sided pairs (set to NaN if either len==0)
   - Implement vtable stubs: `name()` returns "huml", `deinit()` calls `hu_gpt_deinit()` + `hu_value_head_deinit()`
   - Test assertion: `hu_reward_model_create_huml()` with `backend != HU_REWARD_MODEL_BACKEND_HUML` → `HU_ERR_INVALID_ARGUMENT`

3. **Scaffold `src/ml/reward_model_train.c`:**
   - Implement Bradley-Terry forward: for each pair, compute `r_w = score(prompt, chosen)`, `r_l = score(prompt, rejected)`, `delta = r_w - r_l`, loss = `-log σ(delta)` (where σ = sigmoid = 1 / (1 + exp(-delta)))
   - Implement gradient: `dL/dr_w = σ(delta) - 1`, `dL/dr_l = 1 - σ(delta)`
   - Implement SGD step: for each pair, call `hu_value_head_backward()` to get dW and db, apply SGD: `W -= lr * dW`, `b -= lr * db`
   - Implement `hu_reward_model_train()`: iterate `max_iters` times over the batch, track initial loss (before iter 0), final loss (after last step), skip one-sided pairs and log once per run
   - Test assertion: loss is monotonically nonincreasing (or nearly so) across iterations

4. **Wire test framework (`tests/test_reward_model_huml.c`):**
   - Test 1: `test_score_deterministic()` — create model, score same pair 2x, assert bit-exact match

## Bradley-Terry Math (Concrete)

For a preference pair `(prompt, chosen, rejected)`:

```
r_w = score(prompt, chosen)       [double, via value_head_forward]
r_l = score(prompt, rejected)     [double]
delta = r_w - r_l

sigmoid(x) = 1.0 / (1.0 + exp(-x))  [use std exp() + 1.0 / denom for numeric stability]
Loss = -log(sigmoid(delta))
     = -log(1.0 / (1.0 + exp(-delta)))
     = log(1.0 + exp(-delta))

Gradients (w.r.t. the scalar scores):
dL/dr_w = sigmoid(delta) - 1.0          [chain rule: dL/d_delta * d_delta/dr_w = (sigma-1) * 1]
dL/dr_l = 1.0 - sigmoid(delta)          [chain rule: dL/d_delta * d_delta/dr_l = (sigma-1) * (-1)]

Each gradient is passed to hu_value_head_backward():
  hu_value_head_backward(vh, h, dL/dr_w, &dW, &db, NULL)
  hu_value_head_backward(vh, h, dL/dr_l, &dW, &db, NULL)
  (dW and db accumulate; the output gradients sum across the pair)
```

One SGD step (learning_rate η):
```
for each pair in batch:
  compute loss and gradients as above
  accumulate dW and db (all losses sum)
W -= η * (sum_dW / batch_size)
b -= η * (sum_db / batch_size)
```

**Exact arithmetic requirement:** No approximate pooling; use `double` for all loss + gradient accumulators. This ensures the finite-difference check (perturb by ε=1e-3, recompute analytically and numerically) can verify gradients to 3 significant figures.

## Batch Scoring Design

`score_batch()` processes `n` preference pairs in one call:

```c
hu_error_t hu_reward_model_score_batch(
    void *ctx,
    hu_allocator_t *alloc,
    const hu_preference_pair_t *pairs,  /* [n] */
    size_t n,
    double *out_chosen_scores,          /* [n], pre-allocated by caller */
    double *out_rejected_scores         /* [n] */)
{
    for (size_t i = 0; i < n; i++) {
        /* If chosen_len == 0, set to NaN and score rejected only */
        if (pairs[i].chosen_len > 0) {
            score(ctx, alloc, pairs[i].prompt, pairs[i].prompt_len,
                  pairs[i].chosen, pairs[i].chosen_len,
                  &out_chosen_scores[i]);
        } else {
            out_chosen_scores[i] = NAN;
        }
        
        /* If rejected_len == 0, set to NaN and score chosen only */
        if (pairs[i].rejected_len > 0) {
            score(ctx, alloc, pairs[i].prompt, pairs[i].prompt_len,
                  pairs[i].rejected, pairs[i].rejected_len,
                  &out_rejected_scores[i]);
        } else {
            out_rejected_scores[i] = NAN;
        }
    }
    return HU_OK;
}
```

**Latency target:** <100ms for n=100 on a dev machine (single-threaded). Toy GPT forward is ~O(seq_len * hidden^2) and small (typically 12K-24K params); 100 pairs × 2 forwards = 200 forward passes ≈ 2-5ms on CPU. Should easily meet the budget.

## One-Sided KTO Pair Handling

When training, KTO pairs may have `chosen_len == 0` (rejection-only) or `rejected_len == 0` (positive-only). Bradley-Terry requires BOTH sides, so:

1. **In `hu_reward_model_train()`:**
   - Skip the pair: do not compute loss or gradient
   - Increment `metrics.skipped_count`
   - Emit ONE `fprintf(stderr, "WARNING: skipped %zu one-sided KTO pairs during training\n", skipped_count);` at the end (per training run, not per pair)

2. **In `score_batch()`:**
   - For the missing side, set the corresponding output slot to `NAN` (from `<math.h>`)
   - Score the available side normally
   - Caller (GRPO/KTO task) must filter out NaN before calling `hu_reward_model_train()`

## Risk analysis

### Risk 1: Floating-point non-determinism (MEDIUM / MEDIUM)
**What could go wrong:** Reordering of addition in loss accumulation, platform-specific exp() implementations, or misaligned gradients could cause loss to differ between runs or systems.

**Probability:** MEDIUM — floating-point is inherently tricky; AC-101.2 and AC-101.4 explicitly demand bit-exact reproducibility.

**Impact:** MEDIUM — gradient check fails, training metrics are unreproducible, tests flake across CI runs.

**Mitigation:** 
- Use `double` accumulators (not `float`) for all loss + gradient computation
- Accumulate loss and gradients in a fixed order (no reordering): for each pair in order, compute and accumulate
- Avoid approximate pooling; use exact arithmetic
- Gradient check test (AC-101.4) runs at least 3 batch sizes and verifies to 1e-3 relative error, which catches systematic drift
- Allocator RNG seeding (AC-101.8): use `alloc->rng_seed` if in test mode; in prod, seed from /dev/urandom once

### Risk 2: Gradient check tolerance mismatch (LOW / MEDIUM)
**What could go wrong:** ε=1e-3 for finite-difference may be too large or too small; analytical gradient might differ from FD by >1e-3 relative error due to second-order effects or accumulation errors.

**Probability:** LOW — standard practice uses ε=1e-3 to 1e-5; relative tolerance 1e-3 is loose.

**Impact:** MEDIUM — test fails, blocking the task; requires rederiving the analytical gradient or adjusting tolerance.

**Mitigation:**
- Start with ε=1e-3, rel. tol. 1e-3 per AC-101.4
- If test fails, fall back to ε=1e-4, rel. tol. 1e-2 (looser tolerance to account for higher-order perturbation effects)
- Hand-verify 1-2 gradient computations by pen-and-paper before claiming the code is correct
- Gradient check test logs the relative error for each weight so debugging is easy if it fails

### Risk 3: Value-head initialization (LOW / SMALL)
**What could go wrong:** Xavier initialization variance too large or too small, leading to poor gradient flow or extreme initial loss.

**Probability:** LOW — `hu_value_head_create()` already uses Xavier-Glorot (stddev = sqrt(2 / hidden_dim)), which is the standard.

**Impact:** SMALL — if initial loss is extreme, early SGD steps waste iterations; AC-101.5 (preference ranking) might take more than 10 iterations to converge.

**Mitigation:**
- Reuse `hu_value_head_create()` as-is; it's already proven (Task 1)
- Log initial loss in metrics; if it's >10, investigate the pair distribution
- AC-101.5 test trains for at least 20 iterations if needed (flexible, not hard-capped)

## Summary

**Key deliverable:** A gradient-checkable, deterministic Bradley-Terry reward model backed by a frozen HUML toy GPT + trainable value head. The vtable-based design composes cleanly with Phase 4's reward sources (GRPO, KTO, DPO). Finite-difference gradient checks validate correctness to 1e-3 relative error; preference ranking test shows learning works. Implementation splits scoring logic (reward_model_huml.c) and training logic (reward_model_train.c) for clarity. All state is managed through the allocator; no globals. Tests are deterministic and run in <500ms (3 batch sizes × 3 seed runs).
