# Design for US-107: End-to-End Learning Loop Integration Test

## Approach

E2E test simulates the full closed loop: Turn 1 generates response + records `production_outcome` row → mine DPO pair (Turn 1 response = chosen, synthetic alternate = rejected) → train LoRA (subprocess mocked to succeed, writes synthetic adapter) → swap adapter (mocked HTTP POST) → Turn 3 generates response using new adapter → verify Turn 3 output differs from Turn 1. All external dependencies (subprocess, MLX server, actual model inference) are mocked deterministically via `HU_IS_TEST` guards so the test is fully repeatable. Determinism is enforced by seeding the mock model's signature with a fixed value that changes only when the adapter changes.

## Implementation steps

1. **Fixture DB setup**: create in-memory SQLite DB (`sqlite3_open(":memory:", &db)`), create schema (persona, config, messages, production_outcomes, dpo_pairs). Insert persona fixture (neutral baseline).
2. **Turn 1 agent invocation** (via mock provider): call `hu_agent_turn()` with prompt "Hi, how are you?" → capture response (e.g., "I'm doing well, thanks for asking.").
3. **Outcome insertion**: call mining/outcome recording to insert a `production_outcomes` row: channel=test, target=user_contact_id, prompt="Hi, how are you?", chosen=Turn1_response, send_timestamp=now.
4. **Mining**: call `hu_dpo_mine_corrections(alloc, db, &opts, &stats)` → verify pairs_recorded >= 1 → verify DPO pair has chosen=Turn1_response, rejected=(alternate or default).
5. **Training mock**: call `hu_daemon_nightly_lora_run()` which (under `HU_IS_TEST`) invokes mock subprocess → subprocess writes synthetic adapter checkpoint → return success.
6. **Adapter swap mock**: call `hu_mlx_admin_swap_adapter()` (under `HU_IS_TEST`, mocked) → verify resolved_path matches new adapter → telemetry logged.
7. **Turn 2 (skipped)** per AC-107.1: the spec says "Turn 2: Mine DPO pair" but that's just describing the mining step (step 4 above). No separate Turn 2 agent call needed.
8. **Turn 3 agent invocation**: call `hu_agent_turn()` again with same prompt → capture response. Under mock model, response includes adapter signature in format `"e2e_sig_<hex>"` where hex changes when adapter changes.
9. **Verification**:
   - `production_outcomes` row has channel, target, prompt, chosen, send_timestamp (AC-107.2).
   - DPO pair mined: has chosen=Turn1_response, rejected=alternate (AC-107.2).
   - Training checkpoint file created at `~/.human/adapters/lora-persona-<timestamp>.bin` (AC-107.2).
   - Adapter swap logged (AC-107.2).
   - Turn 3 output signature differs from Turn 1 signature (AC-107.2). This is the proof the persona evolved.
10. **Determinism test**: run scenario 3 times with same seed → verify identical outcomes, pairs, weights, Turn 3 signature (AC-107.3).
11. **Timing test**: add `clock_gettime()` calls before/after each phase → log durations → verify total < 30s (AC-107.4).
12. **Fallback error case**: re-run with subprocess mock returning `HU_ERR_IO` → verify system logs error + continues → Turn 3 still generates (uses old persona) (AC-107.5).

## Mocking architecture

All three external dependencies are mocked under `HU_IS_TEST`:

1. **Model inference (agent turn)**: mock provider returns output in format `"e2e_sig_<signature>"` where signature = sum of all adapter-weight tensors. When adapter swaps, signature changes → output changes → test detects the change.
2. **Subprocess (training)**: under `HU_IS_TEST`, `hu_daemon_nightly_lora_run()` calls a mock training function that writes a synthetic adapter file to the expected checkpoint path and returns success.
3. **MLX swap (HTTP)**: under `HU_IS_TEST`, `hu_mlx_admin_swap_adapter()` mocks the HTTP response (status 200, tensors_loaded=N, resolved_path) and returns `HU_OK`.

These mocks are the same as used in US-105 and US-106 tests; the e2e test composes them.

## Checkpoints (AC-107.2)

The test asserts the following at each step:

1. **production_outcomes row exists**: query DB, verify row with channel, target, prompt, chosen, send_timestamp.
2. **DPO pair mined**: query `dpo_pairs`, verify chosen=Turn1_response, rejected is set, source="implicit" or similar.
3. **Checkpoint file created**: `stat(~/.human/adapters/lora-persona-<timestamp>.bin)` succeeds.
4. **Adapter swap logged**: grep `~/.human/logs/service.log` (or wherever swap logs) for `[adapter_swap]` line with old/new paths.
5. **Turn 3 output differs**: compare signature string from Turn 1 vs Turn 3.

## Timing (AC-107.4)

Pseudocode:
```c
int64_t t0 = current_time_ns();
// ... mining ...
int64_t t_mine = current_time_ns();
// ... training mock ...
int64_t t_train = current_time_ns();
// ... swap mock ...
int64_t t_swap = current_time_ns();
// ... Turn 3 ...
int64_t t_end = current_time_ns();

HU_TEST_ASSERT((t_end - t0) < 30_seconds_in_ns, "loop too slow");
```

## Determinism (AC-107.3)

Run the test 3 times; each time:
1. Seed the mock model with a fixed value (e.g., seed=12345).
2. Capture Turn 1 signature, DPO pair hash, trained-adapter-weight checksum, Turn 3 signature.
3. Verify all three are identical across runs (within floating-point tolerance, e.g., ulp < 1).

## Error fallback (AC-107.5)

Create a variant test `test_e2e_learning_loop_fallback_on_training_error`:
1. Same setup as main test.
2. Before calling training, set a mock flag `mock_training_returns_error = true`.
3. Call training → returns `HU_ERR_IO`.
4. Verify system logs error message.
5. Call Turn 3 with old adapter (no swap happened).
6. Verify Turn 3 output uses OLD signature (same as Turn 1, because no persona change).
7. Verify no crash.

## Risks

- **Mock determinism across runs (LOW/SMALL)**: mock model signature depends on floating-point sums, which can vary by compiler/platform. Mitigation: use fixed-integer mock signature (e.g., counter that increments per adapter load) instead of floating-point sum. AC-107.3 specifies "differences due to floating-point are acceptable (< 1 ulp per value)" — so use integer counter, no ulp concern.
- **Test isolation (MEDIUM/SMALL)**: if mocks are global state, running tests in parallel can race. Mitigation: reset all mock state at test start via dedicated `hu_test_reset_mocks()` helper (part of test framework).
- **Timing flakiness (LOW/MEDIUM)**: if test system is slow, timing assertion can fail. Mitigation: use generous timeout (30s) and log actual duration so operator can diagnose slowness. Also acceptable to skip AC-107.4 timing assertion in CI, keep it for local profiling only.

## Test strategy

- **Main flow**: AC-107.1 + AC-107.2 + AC-107.3 in one test `test_e2e_learning_loop_full_spine`.
- **Timing**: separate test `test_e2e_learning_loop_timing_acceptable` (or skip in CI).
- **Error fallback**: separate test `test_e2e_learning_loop_fallback_on_training_error`.

## Acceptance criteria mapping

- AC-107.1 → full scenario in `test_e2e_learning_loop_full_spine`
- AC-107.2 → checkpoints verified in same test
- AC-107.3 → covered by `test_e2e_learning_loop_deterministic_across_runs` (run 3 times)
- AC-107.4 → optional/local profiling, can skip in CI
- AC-107.5 → covered by `test_e2e_learning_loop_fallback_on_training_error`

## Out of scope

- Actual Python training (mocked).
- Actual MLX server (mocked).
- Actual model weights (mocked via fixed-signature output).
- Multi-turn context from prior conversations (simplified: each turn is independent).
- Concurrent daemon operation (single-threaded fixture test).

## Single biggest e2e-testability risk

**Turn 3 output must be verifiably different from Turn 1 output despite using the same prompt and same model code.** If the mock adapter swap doesn't change the model's signature, the test cannot prove the loop closed. Mitigation: mock model output is deterministically derived from a `current_adapter_id` variable that changes only after a successful swap. Turn 1 uses adapter_0, Turn 3 uses adapter_1 → outputs differ deterministically. This is testable without a real model.
