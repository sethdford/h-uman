# Design for US-48-3: Wire follow-up watcher + daemon flush into iMessage proactive path

## Approach

US-48-3 introduces a daemon background subsystem that periodically polls iMessage chat.db for "read but unreplied" messages from seth's contacts, computes circadian-aware follow-up delays via `hu_followup_compute_send_time()`, stores them in a `follow_up_scheduled` SQLite table, and flushes them when the contact enters their active hours—throttled to max 1 per contact per day.

The design is modular: the read-receipt watcher is a pure predicate at the iMessage channel layer (queries chat.db), the follow-up delay computation is already extracted (`hu_followup_compute_send_time`), and the daemon tick orchestrates polling + scheduling + throttle gates. The dangerous case (sending at 2 AM to a LARK contact) is prevented by a pure predicate extracted per `.claude/rules/security-predicate-extraction.md`.

## Implementation steps (for the implementer agent)

1. **Define config schema** — Add `follow_up_watcher` and `proactive_throttle.per_contact_daily_max` to config struct + schema defaults.
2. **Extract the send-now predicate** — `hu_follow_up_should_send_now(contact_handle, now_ms, last_msg_ts, chronotype, throttle_state)` with full truth-table tests (9 tests covering active-hour snap boundaries, throttle-gated, idempotent).
3. **Extend throttle struct** — Add per-contact daily ring + contact-scoped query fn `hu_proactive_throttle_did_send_today()`. Persist to SQLite `proactive_send_log` table.
4. **Add chat.db unresponded query** — `hu_follow_up_watcher_detect_unresponded(contact_handle, chat_db)` returning list of `{msg_id, read_at_ms, chat_id}`. Validate query shape against real chat.db schema (test with fixture DB).
5. **Wire daemon tick** — Add tick fn to `src/daemon.c` main loop, register in tick vector, add one-shot log on disable (per `.claude/rules/silent-config-gated-subsystems.md`).
6. **Implement flush path** — `hu_daemon_follow_up_flush_for_contact()` calls autoresponder + iMessage send. Reuse M2 per-contact context.
7. **Add integration test** — `test_follow_up_daemon_integration.c::test_scheduled_flush_honors_chronotype_active_hours` — midnight read, LARK chronotype, verify send fires during 06:00–22:00 window, not at 02:00.
8. **Run full suite** — Must pass all 10,600+ tests. Check no ASan leaks. Verify predicate tests cover all AC-3 scenarios.

## Risks

- **chat.db is_read semantics (HIGH/LARGE)** — Real iMessage chat.db only sets `is_read` on INBOUND messages; outbound `is_read` is unused/always 0. Querying for `is_from_me=1 AND is_read=1` returns 0 rows. **Mitigation**: Verify schema against a real chat.db dump. The correct query is: "messages from seth (`is_from_me=1`) that have at least one read receipt from a contact (`read_receipts.read_status=1`)." Confirm with iMessage channel owner or a real DB inspection before implementation. **TEST**: fixture DB must have real chat structure (messages + read_receipts join).

- **Chronotype default for contacts without overlay (MEDIUM/MEDIUM)** — If a contact has no per-contact overlay, which chronotype do we use? M2 per-contact model may not include chronotype. **Design pick**: Default to persona's global chronotype (from `hu_persona_t`), fall back to `HU_CHRONO_INTERMEDIATE` (9am–11pm). **AC-3.5 test must pin this** by asserting the default fires for a contact with zero overlay.

- **Throttle persistence across daemon restart (MEDIUM/MEDIUM)** — In-memory throttle ring is lost on restart, risking duplicate follow-ups. **Mitigation**: Persist `proactive_send_log` table to SQLite on every send; reload into ring on daemon startup. The reload is a one-time scan at boot; adds <10 ms. **TEST**: `test_proactive_throttle_persists_across_restart`.

- **Predicate-extraction discipline (LOW/LOW if applied now, HIGH/HIGH if skipped)** — The send-now decision must be a pure predicate, testable without spawning the daemon. **Mitigation**: Extract `hu_follow_up_should_send_now()` BEFORE wiring into daemon tick. The truth table is: `(contact_handle, now_ms, last_msg_ts, chronotype, throttle_state) → bool`. Tests must cover all 9 quadrants of the snapping matrix. **Don't proceed past step 2 without this predicate isolated and tested.**

- **Idempotency + dedup (MEDIUM/SMALL)** — The watcher runs every 5 min; the same message could schedule a follow-up multiple times. Existing `hu_followup_dedup` ring (32 slots) may not be enough if daemon is slow. **Mitigation**: Use `follow_up_scheduled` table with `(msg_id, contact_handle)` unique constraint to prevent multi-schedule. Dedup ring is for *active* messages; DB constraint is for idle ones.

- **Autoresponder draft quality without M2 (MEDIUM/SMALL)** — AC-3.3 says "use `hu_autoresponder_generate()`" but draft quality depends on per-contact context from M2. If M2 is not yet wired, the follow-up draft will be generic. **Mitigation**: US-48-2 lands first (dependency in backlog). Design assumes M2 context is available; if not, draft falls back to persona-level context + static template. AC-3.3 is still satisfied (draft uses autoresponder); quality is reduced but not broken.

## Test strategy

- **Unit tests** (test_follow_up.c extensions): Predicate truth table (9 cases: LARK/OWL/INTERMEDIATE × within-24h/stale × throttled/allowed).
- **Integration tests** (test_follow_up_daemon_integration.c new): Fixture iMessage chat.db with unresponded reads; daemon tick orchestration; verify flush fires at correct local time for contact's chronotype.
- **Throttle unit tests** (test_proactive_throttle.c extensions): Per-contact daily cap (3 tests: first send allowed, second send today blocked, second send tomorrow allowed).
- **Config gate test** (test_config_gated_subsystems.c, if US-48-4 lands): Verify disabled tick logs once.

## Acceptance criteria mapping

- **AC-3.1** (detect unresponded every 5 min) → Covered by tick registration test + mock iMessage channel test
- **AC-3.2** (compute send time + store in table) → Covered by unit test of predicate + integration test of table insert
- **AC-3.3** (flush via autoresponder + iMessage) → Covered by integration test (dummy send, verify draft was generated)
- **AC-3.4** (throttle max 1/day per contact) → Covered by test_proactive_throttle.c per-contact daily cap tests
- **AC-3.5** (chronotype active hours honored) → Covered by test_follow_up_daemon_integration.c::test_scheduled_flush_honors_chronotype_active_hours

## Out of scope

- M3 frontier-model personalization (follow-ups still use reference model for draft)
- DPO collector integration for follow-up feedback (wired in later sprint)
- Slack, Discord, Telegram proactive (iMessage only in this sprint)
- Multi-contact follow-up throttle (e.g., "max 5 per hour globally") — only per-contact daily cap is implemented
- Follow-up retry logic (if send fails, we don't reschedule; log the failure and move on)

## One-shot log discipline

Per `.claude/rules/silent-config-gated-subsystems.md`:

- `hu_daemon_tick_follow_up_watcher()` on first disabled invocation:
  ```
  hu_log_info_once("follow_up_watcher",
    "follow_up_watcher subsystem disabled by config (cfg->follow_up_watcher.enabled=false); "
    "set follow_up_watcher.enabled=true in config.json to activate")
  ```
- On first enabled invocation:
  ```
  hu_log_info_once("follow_up_watcher",
    "follow_up_watcher subsystem activated (cfg->follow_up_watcher.enabled=true); "
    "polling iMessage chat.db every %d seconds for unresponded reads",
    cfg->follow_up_watcher.interval_seconds)
  ```

Same pattern for proactive_throttle (if it gains a config gate; currently no gate).
