# Design for US-48-2: Wire per-contact M2 personal-model slice into iMessage agent turn

## Approach

**Single `personal_model.db` with contact-scoped rows** (stakeholder decision overrides AC-2.3). Add `contact_handle TEXT NOT NULL` column to fact storage table. Load per-contact facts before autoresponder prompt assembly; inject "Contact insights: [top 3 facts by effective confidence]" into autoresponder system prompt. Fact extraction fires on ingest (seth's outbound messages), half-life decay applies exponentially over 90 days per `hu_heuristic_fact_effective_confidence()`.

## Schema migration & storage

**Current**: `personal_model.bin` — binary blob with fixed-size struct (no SQL).
**Change**: Migrate to SQLite to support contact-scoped rows without per-handle file explosion.

**DDL**:
```sql
CREATE TABLE facts (
    id INTEGER PRIMARY KEY,
    contact_handle TEXT NOT NULL,     /* "" for global facts; specific handle for contact-scoped */
    type INTEGER,                      /* HU_KNOWLEDGE_PROPOSITIONAL / PRESCRIPTIVE */
    subject TEXT, predicate TEXT, object TEXT,
    confidence REAL,
    source_hint TEXT,
    last_seen_at INTEGER,             /* Unix seconds */
    provenance_tier INTEGER,          /* HU_TRUST_USER_DIRECT, etc. */
    created_at INTEGER,
    PRIMARY KEY (contact_handle, subject, predicate)
);
```

**Migration path**: 
- Load existing `personal_model.bin`; initialize new SQLite at `~/.human/models/personal_model.db`
- INSERT global facts from struct into table with `contact_handle=""` (NULL → "" for indexing)
- On subsequent saves, write ALL facts to SQLite atomically (same tmp+fsync+rename pattern)
- Binary blob is retired after successful first SQLite save; kept as backup for 7 days

**Backwards compatibility**: 
- `hu_personal_model_load()` detects `.bin` vs `.db` and migrates on first call
- Tests of global-scope model (existing `test_personal_model.c`) continue to pass: `contact_handle=""` is invisible to legacy code paths

## Integration points

### Fact extraction (US-48-2.2 AC-2.2)
- `hu_fact_extract(text, …)` remains contact-agnostic (extracts pure facts)
- New wrapper `hu_fact_extract_for_contact(text, contact_handle, …)` stamps `contact_handle` into each extracted fact's struct field (new field added to `hu_heuristic_fact_t`)
- Provenance is set by caller (typically `hu_channel_trust_stamp` from iMessage channel)


```c

```

## Risks & mitigation

- **Backwards compat (LOW/SMALL)**: `.bin` → `.db` migration on first load. Mitigation: migration runs once per process startup; existing tests continue to use `contact_handle=""` (global scope) and remain green.
- **Concurrency (MED/SMALL)**: Per-contact writes use existing atomic save (tmp+fsync+rename). Daemon is single-threaded; no races. Mitigation: design remains atomic.
- **Performance (LOW)**: SQLite INSERT per fact is **slower** than struct copy, but limited to ~60 facts per model per contact (HU_PM_MAX_FACTS). One INSERT per message ingest ≈ <5 ms. Acceptable for per-turn save. Mitigation: batch INSERTs if needed (not in v1).
- **Half-life decay (MED)**: Ensure `hu_heuristic_fact_effective_confidence()` is called at prompt-build time, not at write time, so decay is live. Mitigation: test fixture `test_half_life_decay_applies_to_contact_facts` pins behavior.
- **Schema version mismatch (LOW)**: SQLite schema version is incremented; migration code handles both old and new. Mitigation: `HU_PM_VERSION` constant controls schema; load path already has migration logic.
