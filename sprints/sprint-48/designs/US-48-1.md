# US-48-1 Design: A-loop Blind Eval

## Approach

Blind eval framework that compares persona-aware autoresponder replies vs baseline (raw frontier model, no persona) on 50 of seth's iMessage conversations. Two arms run against same frontier model; only persona overlay differs. Responses are scored by three pure C scoring predicates (tone, length, formality, each 0-10), then aggregated to compute win-rate (AC-1.4) and per-contact breakdowns (AC-1.5). Blinding is structural: both responses are hashed deterministically, shuffled in eval output, unblinded only in final reporting.

**Key design choices:**
1. **Eval framework location**: `tests/test_autoresponder_eval.c` — integration test suite, not a separate binary. Easier to ship with code; verifier can run it directly.
2. **Chat.db ingestion**: Fixture-based. Create `tests/fixtures/seth_chats_50.db` (or populate from live `chat.db` at build time via a script, guarded by `HU_IS_TEST`). No real network, deterministic inputs.
3. **Rubric functions**: Three pure C functions in `src/persona/eval_rubric.c` returning int 0-10. Each scores one dimension independently. No provider calls — text-only analysis.
4. **Blinding**: Store (arm_A, arm_B, contact, message_idx) tuples. Compute SHA256(arm_A || arm_B || rand_seed) to produce a deterministic but unbiased order. Reveal identity only in final JSON output via `"arm_A_persona": <score>, "arm_B_baseline": <score>`.
5. **Win-rate**: For each message pair, winner = arm with higher aggregate score; ties are ties. p50 = median of all pairs; win_rate = (wins + 0.5*ties) / total.
6. **Output format**: JSON (one-line-per-contact) written to `~/.human/eval/aloop_blind_<timestamp>.json`. Includes p50, win_rate, per-message breakdowns.

## Function signatures (new)

```c
/* Pure scoring predicates. Each returns int 0-10.
 * text1/text2 are NUL-terminated. */

/* Tone alignment: does autoresponder reply match the tone of incoming msg?
 * Checks for: urgency markers, sentiment consistency, emoji matching.
 * Lower score = mismatch (e.g. formal reply to casual joke). */
int hu_eval_rubric_tone_match(const char *incoming, const char *reply_baseline,
                              const char *reply_persona);

/* Length alignment: does autoresponder stay within contact's typical range?
 * Measures char count relative to incoming msg. */
int hu_eval_rubric_length_match(const char *incoming, const char *reply_baseline,
                                const char *reply_persona);

/* Formality alignment: does autoresponder match contact's register?
 * Uses word-boundary classifier on bucket keywords (same shape as
 * `src/persona/render.c::str_contains_word_ci`). */
int hu_eval_rubric_formality_match(const char *incoming, const char *reply_baseline,
                                   const char *reply_persona);

/* Pure helper for blinding. Deterministic hash of two responses to
 * shuffle eval order without revealing identity. Used by test only. */
uint64_t hu_eval_rubric_hash_for_blind_order(const char *response_a,
                                             const char *response_b,
                                             uint32_t seed);
```

## Implementation sequencing

1. **Create stub eval_rubric.c** with function signatures (no logic, return 5 for all).
2. **Write test fixtures**: create `seth_chats_50.db` with 50 sample conversations (5-10 contacts, 3 messages each). Can be synthetic or extracted from live DB.
3. **Skeleton test_autoresponder_eval.c**: Load fixture DB, run autoresponder twice (with persona, without), call stubs, verify output structure. Test should FAIL until rubric logic lands.
4. **Implement tone_match**: Check for sentiment markers (exclamation, question marks, emoji count). Award points if persona reply mirrors incoming tone better than baseline.
5. **Implement length_match**: Measure reply length relative to incoming. Award points if persona reply is closer to "typical for this contact" than baseline.
6. **Implement formality_match**: Use word-boundary classifier (`str_contains_word_ci` pattern from substring-classifier-pitfalls.md) on formal/casual keywords. Award points if persona matches incoming formality.
7. **Implement blinding + aggregation**: Hash-shuffle responses; compute p50, win_rate; output JSON per AC-1.5.
8. **Test adversarial inputs**: per `tests-that-pin-bugs.md`, write synthetic test messages and verify rubric doesn't produce inverted scores (e.g., formal response to casual input scoring higher than casual response).

## Risks

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|-----------|
| **Rubric subjectivity** | Medium | Medium | Rubric functions are deterministic (no LLM judge). Adversarial test suite (AC-1.6 implicit) validates tone/length/formality don't invert on edge cases (all-caps, single emoji, very short msg, etc.). |
| **Small-sample noise** (50 convs) | Medium | Medium | p50 is more robust than p95; 50 messages ≈ 150 scoring pairs. Sufficient for a directional signal ("persona ≥ baseline at p50"). If near-parity emerges, spike to 100 convs + manual spot-checks. |
| **Fixture stale** (doesn't match live seth behavior) | Low | Small | Fixture is synthetic/curated; if eval is launched to prod later, replace with live chat.db read (gated by HU_IS_TEST). For now, synthetic is reproducible. |
| **Per-contact M2 not ready** (US-48-2 delayed) | Medium | Medium | Eval harness is written to handle NULL persona_summary gracefully (persona-aware arm degrades to baseline). If US-48-2 slips, test still runs, comparing "empty persona" vs "no persona". Still validates framework. |
| **Chat.db schema drift** | Low | Small | Fixture DB is read-only; hardcoded schema in fixture creation. If iMessage channel schema changes, fixture can be regenerated. |

## Test strategy (per AC)

**AC-1.1 (Load seth's chat.db)**: `test_autoresponder_eval_loads_fixture_db` — opens `tests/fixtures/seth_chats_50.db`, counts conversations, verifies ≥40.

**AC-1.2 (Extract 3 test messages, run through autoresponder)**: `test_autoresponder_eval_generates_pairs_with_and_without_persona` — for each conversation, extracts first 3 user-received messages, calls `hu_autoresponder_generate_reply()` twice (once with persona, once with NULL persona_summary), verifies both replies are non-empty.

**AC-1.3 (Score via rubric)**: `test_autoresponder_eval_rubric_scores_all_dimensions` — calls tone/length/formality on synthetic test pairs; verifies scores are 0-10. Include adversarial inputs:
  - Formal incoming, casual reply (should score low for formality_match)
  - 50-char incoming, 10-char reply (should score low for length_match)
  - Excited incoming (!!!), flat reply (should score low for tone_match)

**AC-1.4 (p50 + win-rate ≥60%)**: `test_autoresponder_eval_aggregates_win_rate` — runs eval on 10 synthetic conversations, computes win_rate, asserts ≥60%. (Real 50-conversation eval is run as part of the integration test, not a gated unit test — allows for human review of near-parity cases.)

**AC-1.5 (Per-contact breakdown output)**: `test_autoresponder_eval_outputs_json_per_contact` — verifies output file exists, is valid JSON, contains "contact", "p50", "win_rate" keys, and per-message fields with both arm scores.
