# Post-mortem — CoT / Prompt-Context Leak via iMessage (2026-05-12)

**Status:** Resolved (Sprints 29-36, branches in `human-sprint-4`).
**Severity:** S1 (privacy/safety — internal reasoning sent to live human contact).
**Author:** h-uman engineering.
**Last update:** 2026-05-16 (Sprint 36 — G8 persona identity / core-anchor echo).

## Summary

On 2026-05-12, the `human-daemon` autonomous service-loop sent a message
to `<recipient A>` (a real human contact, not a test fixture) consisting
**entirely of internal model reasoning** — numbered analysis bullets,
third-person profile statements about the operator, the literal phrase
`per scene direction`, and `Wait, the prompt says...`. The operator
deleted the message manually within ~2 minutes; an audit later
established blast radius.

A subsequent audit of `~/Library/Messages/chat.db` surfaced **four
additional leaks of the same class** that we had missed in the original
incident report (rowids 56049, 56055, 56063, 56065 to `<recipient B>`,
and rowid 56354 to `<recipient C>` cross-contact-fanout). All five
leaks fall into a small number of structural patterns that the response
guard was not yet checking for.

## Impact

- Privacy: model's plan, candidate-response list, third-person statements
  about the operator, and prompt-template structure all sent to two
  real human contacts.
- Trust: the system's whole thesis ("an assistant that's actually yours,
  private by architecture") was directly contradicted by the wire output.
- Operational: required manual deletion in iMessage. No replicable
  recovery path beyond that.
- Reputational: would have ended the product if it had happened to a
  user instead of the operator.

## Root cause

Three layered failures, each independently sufficient to ship the leak:

### 1. Response guard returned `REWROTE` instead of `REJECT`

The 2026-05-12 leak surface (rowids 56354/56355) tripped the existing
G2-class pattern detection (`<|channel`, `<|message`) but the guard
was emitting `HU_GUARD_REWROTE` with the substrings stripped, not
`HU_GUARD_REJECT`. Stripping a few special tokens does **not** make
internal reasoning safe to send. The remaining ~1.8 KB was still pure
chain-of-thought.

### 2. Quality gate "MARGINAL" policy permitted send

Downstream of the guard, the quality gate scored these messages as
"MARGINAL" (length anomaly, profile-pattern density) — but the gate's
policy was MARGINAL → send-anyway. There was no kill switch on a clearly
out-of-distribution length spike (5-30x normal reply length).

### 3. No retry path was invoked

`response_guard_retry.c` exists to ask the model for a clean rewrite
when the guard fails. It was bypassed because the guard emitted
`REWROTE` (case 1), not `REJECT`. The retry path is only triggered
on `REJECT`.

### Underlying contributors

- The historical leaks (rowids 5604x/5605x/5606x, 2026-05-11) had
  already happened **a day before** the high-severity incident and we
  hadn't seen them because we only inspected the visible iMessage UI,
  not `chat.db`. The system had been silently leaking for ~17 hours.
- Persona context (operator's name, age, profession, role, living
  situation) was being ingested verbatim into the system prompt and
  the model was happily echoing it back third-person.
- Multi-turn / multi-recipient fanout: rowid 56355 was sent to
  `<recipient C>` ~3 minutes after rowid 56354 was sent to
  `<recipient A>`. The model had cached the leaked context and reused
  it across the recipient boundary.

## What went well

- **Verbatim regression pinning.** Every leak we found is now a checked-in
  string fixture. Future regressions will fail the test immediately.
- **Layered, redundant detection.** Each leak in the audit hits 2-4
  independent detectors. Removing any one would not have been enough
  to ship the leak.
- **Open-source-safe signatures.** Sprint 30 explicitly removed
  hardcoded persona PII (operator's name, employer) from G3 patterns
  and replaced them with role/relationship/lifestyle structural
  signatures. Detection works for any persona without leaking the
  current operator's identity into git.
- **Opt-in `_ex` API.** Sprint 31 introduced `hu_response_guard_check_ex`
  rather than breaking the existing call sites. Production code can
  migrate one call site at a time, with the no-context default being
  byte-identical to the old behavior.
- **Audit-first habit.** Using `chat.db` directly (vs. the iMessage UI)
  was the single biggest lever — it found 4 of the 6 leaks the
  operator never saw.
- **Test isolation.** When Sprint 31 G5 tests started failing because
  long fixtures tripped the earlier degenerate-repetition detector,
  we built `guard_test_make_benign_long()` (varied English phrase
  loop) instead of fighting the detector. Right call.

## What went wrong

- **17-hour silent failure window.** Four leaks landed on 2026-05-11
  before the operator noticed on 2026-05-12. We had no telemetry on
  outbound message classification — only the UI.
- **MARGINAL → ship-anyway gate.** The quality gate flagged these
  messages as anomalous but the policy permitted send. Anomalous +
  outbound to humans should be the strictest gate, not the loosest.
- **Stripped payload is not a safe payload.** `REWROTE` after stripping
  `<|channel>` left a 1.8 KB CoT dump. The guard's "tokens removed,
  ship it" branch was always wrong on long inputs.
- **Audit was ad-hoc.** The 2026-05-12 audit was three throwaway
  shell scripts in `/tmp/`. Sprint 32 promoted it to a checked-in tool;
  it should have been one from the start.
- **Cross-recipient fanout was not anticipated.** rowid 56355 reused
  context from rowid 56354 across a recipient boundary, ~3 minutes
  apart. We had no model-state hygiene between turns.

## Lessons

1. **Trust the database, not the UI.** Wire-level audits found 4 of
   the 6 leaks the operator never saw. Build the audit tool first.
2. **REWROTE is dangerous.** Stripping a substring from a 2 KB chain-of-thought
   does not make it safe. If the response is anomalous, REJECT and retry,
   don't sanitize-and-ship.
3. **Anomalous + outbound to humans = strictest gate.** A "MARGINAL" signal
   on a message about to land in a real person's inbox should default-deny.
4. **Persona context is sensitive.** It must never appear verbatim in
   outbound messages. Build the persona-derived detector that knows
   the operator's name and rejects any verbatim quote of it.
5. **Layer detectors; pin verbatim.** Six independent detectors guarantee
   that no single bug ships a leak. Verbatim regression fixtures
   guarantee the *exact* leaks we've already seen never recur.
