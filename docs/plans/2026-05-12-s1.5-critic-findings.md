## HIGH (fix before or immediately after landing)

### H1 — `apply_steering` state never reset between turns
**File:** `src/agent/agent_turn.c` (no specific line — absence of a call)

**Evidence:**
`hu_provider_apply_steering(&agent->provider, steering_vec, HU_STEERING_VEC_DIM)` is
called at ~line 4826 on retry attempts. The provider vtable docstring at
`include/human/provider.h:282` explicitly says:

> "Calling with vec == NULL and dim == 0 disables steering. Use **between turns** or to
> cancel mid-turn injection."

There is no `hu_provider_apply_steering(&agent->provider, NULL, 0)` call at any of the
turn exit paths (normal return, HU_ERR_PROVIDER_RESPONSE, HU_ERR_TIMEOUT, iterations
exhausted). The steering vector from the last rejected retry of turn N will remain active
in any provider that implements the `apply_steering` vtable slot — directly violating the
design contract.

**Impact today:** Zero — no shipping provider implements `apply_steering` (only the test
mock does). **Impact at init-04 landing:** The first on-device provider to implement
`apply_steering` will inherit turn N's steering vector on turn N+1's first (unsteered)
attempt, corrupting the determinism contract that `test_agent_turn_first_attempt_has_no_steering_directive` pins.

**Suggested fix:** Add at the top of `hu_agent_turn` (after function-local var setup) a
reset call on entry so any stale state from a prior turn is cleared:
```c
/* Clear any steering residue from a previous turn's retry path. */
(void)hu_provider_apply_steering(&agent->provider, NULL, 0);
```
Alternatively, reset at the BOTTOM of each successful retry and at all exit paths. The
entry-point reset is simpler and correct.

### H2 — `lora.h` public docstring falsely claims helper enforces `spec->alloc != NULL`
**File:** `include/human/lora.h:88–90`, `src/providers/helpers.c:168–171`

**Evidence:**
`lora.h` struct docstring for the `alloc` field:
> "NULL is permitted only when the impl explicitly documents that it uses an internal
> allocator — none of the in-tree impls do this today. **The helper
> `hu_provider_load_adapter` enforces non-NULL for safety.**"

`helpers.c` at the corresponding validation block:
```c
/* `alloc` is allowed to be NULL only when the provider docs say so;
 * none in-tree do today, but we don't enforce here — providers that
 * need it will fail their own validation. */
```

The helper EXPLICITLY SKIPS the `spec->alloc` NULL check. The public header makes the
opposite claim. A direct-vtable caller reading the header will believe the helper is their
safety net — it isn't.

**Impact:** Low for today (each impl validates alloc itself). High for API correctness:
the public header contract is a lie, and any future caller that bypasses impls (e.g. a
mock vtable without its own alloc check) will silently receive a NULL allocator.

**Suggested fix (two options, pick one):**
1. Add `if (!spec->alloc) return HU_ERR_INVALID_ARGUMENT;` to the helper after the
   source-mutex check, making the header claim true.
2. Remove the sentence from the header: replace with "When writing an impl that requires
   alloc, validate spec->alloc in the impl itself."

Option 1 is preferred — the public contract is already written and other providers
consumed it.

## Half-fixes (defer with explicit ticket)

### HF1 — `mlx_qwen3.c` allocates with `spec->alloc`, frees with `c->alloc`
**File:** `src/providers/mlx_qwen3.c:369–376`, `src/providers/mlx_qwen3.c:158–170`
**Defer to:** init-04 wrap-up / allocator-audit ticket

**Evidence:**
`mlx_qwen3_load_adapter` does:
```c
hu_allocator_t *alloc = spec->alloc;
char *new_id   = hu_strndup(alloc, spec->id,   spec->id_len);
char *new_path = hu_strndup(alloc, spec->path, spec->path_len);
...
clear_active_adapter(c);          // uses c->alloc internally
c->active_adapter_id   = new_id;  // allocated by spec->alloc
c->active_adapter_path = new_path;
```
`clear_active_adapter` frees via `c->alloc->free(c->alloc->ctx, ...)`. If
`spec->alloc != c->alloc` (different allocator instance — not just a stack copy of the
same underlying allocator), this is a mismatched free. For `hu_system_allocator()` all
callers today share the same backing `malloc`/`free`, so `c->alloc.ctx` and
`spec->alloc.ctx` are both NULL and the free is correct. But the API makes no guarantee
they're equivalent, and the lora.h comment says `spec` is "short-lived" and callers may
pass any allocator they have handy.

`lora_training_runner.c:109` passes `spec.alloc = &load_alloc` where `load_alloc` is a
shallow copy of `ctx->alloc` — same function pointers and ctx, so fine today. But it is
a value copy at a different stack address, not the same `c->alloc` pointer the provider
stores.

**Suggested fix:** Store `spec->alloc` in `mlx_qwen3_ctx_t` at load time and update
`c->alloc` to match, OR require the caller to always pass the creation-time allocator
(add a note to lora.h). The simplest fix: at the start of `mlx_qwen3_load_adapter` after
validating alloc, `c->alloc = spec->alloc;` to keep them in sync.

### HF2 — CLI typing "error fallback" test doesn't test the actual error branch
**File:** `tests/test_channel_cli.c:265–302` (`test_cli_typing_send_error_falls_back_to_direct_write`)

**Evidence:**
The test comment says it exercises the `err != HU_OK` fallback in `cli_send`:
```c
if (err != HU_OK)
    return cli_raw_send(ctx, ...);
```
But the test does NOT trigger a non-OK return from `hu_typing_send`. It sends an empty
payload (message_len=0), which `hu_typing_send` handles with `budget=0` and returns
`HU_OK`. The `err != HU_OK` branch is never actually executed by any test.

The test's own comment admits: "In practice, the typing simulator returns HU_OK for all
reasonable inputs … The only error branch is HU_ERR_INVALID_ARGUMENT, which the CLI
wiring never triggers because it always passes its own non-NULL channel + raw vtable."

The fallback exists to protect callers from a typing-simulator regression. If `hu_typing_send` were to start returning errors on a valid input, we'd never know because the fallback path silently absorbs it and no test catches the discrepancy.

**Suggested fix:** In `test_channel_cli.c`, add a test that passes a NULL `channel.vtable->send` into `hu_typing_send` to force a non-OK result, then confirm the CLI output still appears (from the fallback). Alternatively, add a narrow test for `cli_send` that patches the raw vtable's `send` to return `HU_ERR_PROVIDER_RESPONSE` and verifies the outer cli_send returns `HU_OK` (defensive no-crash test).

### HF3 — `steering_now = time(NULL)` in retry path: directive is non-deterministic in production
**File:** `src/agent/agent_turn.c:4790`

**Evidence:**
```c
long long steering_now = (long long)time(NULL);
hu_error_t sv_err = hu_persona_steering_vector(
    agent->persona, &agent->personal_model, steering_now, steering_vec, ...);
```
The comment on the test file says "same persona + same retry attempt → byte-identical
directive suffix across runs (no clock reads, no RNG perturb the projection **when the
personal_model is empty**)." The test controls this by using `HU_IS_TEST` to bypass
`hu_personal_model_ingest`. However `hu_persona_steering_vector` receives a live wall
clock and, for a non-empty personal_model with circadian-timing logic, the steering vector
will differ on every retry call. Two retry iterations in the same turn see different
`time(NULL)` values → potentially different directives → non-monotonic steering intensity
despite the boost ramp.

**Impact:** Low for today (personal_model is sparsely populated for new users). High
for power users with >50 conversations where the model is populated. The boost
(`1.0 → 1.5 → 2.0`) may be undermined by circadian variance between retries.

**Suggested fix:** Snapshot `steering_now` ONCE before the retry loop (at turn setup,
alongside `retry_attempt = 0`) and reuse the same timestamp for all retry attempts in a
single turn.

### HF4 — CoT-driven retries never receive persona steering
**File:** `src/agent/agent_turn.c:5078–5083`

**Evidence:**
At line 5083, when a CoT audit fails, the loop does `continue` without incrementing
`retry_attempt`. On the next iteration, `retry_attempt` is still 0, so the steering
block at line 4786 does not fire. Only the reflection-critique path (line 5289) increments
`retry_attempt`. Chain-of-thought quality failures get zero persona steering even on
repeated failure.

Whether this is intentional is undocumented. The comment at the retry counter says "each
reflection-driven `continue` increments it" — reflection-driven only, not CoT-driven.

**Defer to:** init-01 follow-up design decision. Open a ticket to explicitly document
whether CoT retries should steer, and if not, add a comment at line 5083 explaining the
intentional asymmetry.

### HF5 — CLI typing tests use `int` sentinel as persona handle; breaks when init-02 wires `hu_typing_profile_resolve`
**File:** `tests/test_channel_cli.c:234, 278, 307` and `src/agent/typing_simulator.c:188`

**Evidence:**
Tests pass `int sentinel = 0xC0FFEE` (and `int sentinel = 7`, `int sentinel = 0`) as
the persona handle to `hu_cli_set_persona`. These are raw stack integers, not
`hu_persona_t *`. The current `hu_typing_profile_resolve` implementation:
```c
void hu_typing_profile_resolve(const void *persona, ...) {
    ...
    (void)persona;  /* ignored — init-02 wires per-channel overlay here */
}
```
When init-02 changes this to actually dereference the persona, these tests will access
invalid memory at best, or silently read garbage fields at worst.

**Defer to:** init-02 pre-landing. Before init-02 touches `hu_typing_profile_resolve`,
update the CLI tests to use a real `hu_persona_t` (even a zero-initialized one) as the
sentinel.

## Pre-existing issues (not introduced by this diff)

### PE1 — `llamacpp_unload_adapter` leaks `active_adapter_id` and `active_adapter_path`
**File:** `src/providers/llamacpp.c:469–497`

**Evidence:** `llamacpp_unload_adapter` frees the live `struct llama_adapter_lora *` and
resets the KV cache, but explicitly does NOT free `c->active_adapter_id` or
`c->active_adapter_path`. The comment reads:
> "Without an allocator on this hook we cannot free the cached id, so we just zero the
> live adapter. The next replace cycle in load_adapter() picks up the cleanup."

`deinit` calls `clear_active_adapter(c, alloc)` and frees both strings, so there is no
permanent leak if deinit is called. But any call sequence `load_adapter → unload_adapter
→ ... (no further load) → deinit` has the strings freed by deinit correctly. The leak
window is between `unload_adapter` and either the next `load_adapter` or `deinit`.

**Not introduced by this diff.** The diff does not change `llamacpp_unload_adapter`.
ASan does not flag it because `deinit` recovers the memory. Defer until the vtable
surface is next touched — the root fix is adding an `alloc` parameter to
`unload_adapter` (asymmetric with the widening done here for `load_adapter`).

### PE2 — `spec->bytes` at the impl level returns INVALID_ARGUMENT, not NOT_SUPPORTED
**File:** `src/providers/huml.c:383`, `src/providers/llamacpp.c:412`,
`src/providers/mlx_qwen3.c:335`

**Evidence:** All three impls check `spec->bytes` via the pattern:
```c
if (!spec->path || spec->path_len == 0 || spec->bytes)
    return HU_ERR_INVALID_ARGUMENT;
```
A bytes-only call (valid `bytes` + NULL `path`) passes the helper's source-mutex check
(`has_bytes == true`, `has_path == false` → not equal → passes through), but the impl
returns `HU_ERR_INVALID_ARGUMENT` because `spec->bytes != NULL`. Init-08's federated
aggregation dispatch will probe bytes support by checking for `HU_ERR_NOT_SUPPORTED`; it
will instead get `HU_ERR_INVALID_ARGUMENT` and may misinterpret it as a caller bug rather
than a "feature not yet supported" signal.

**Not introduced by this diff** (the bytes field is new but the rejection rationale is
documented). **Impact:** Init-08 must handle INVALID_ARGUMENT as an additional "not
supported here" signal, or the impls must be updated to return NOT_SUPPORTED for
bytes-only specifically.

## Cross-initiative concerns

### CI-1 — Init-02 (MoLoRA): STACK behavior change is a silent breaking contract
**Relevant files:** `include/human/lora.h:36–44`, `include/human/providers/mlx_qwen3.h:66–70`

The old `mlx_qwen3.h` documented STACK as: "falls through to REPLACE and is documented
as a v1.5+ feature." The new `lora.h` documents STACK as: "MUST return NOT_SUPPORTED
rather than silently downgrading." These are opposite contracts. No current production
caller passes STACK (all four call sites use REPLACE), so there is no runtime regression.
But any init-02 draft code written against the old "falls through gracefully" guarantee
would now get NOT_SUPPORTED and break. The lora.h comment explains the new contract
clearly; the old mlx_qwen3.h comment is removed. Confirm that init-02 design docs have
been updated to reflect NOT_SUPPORTED semantics.

### CI-2 — Init-08 (federated LoRA): bytes-only path gets wrong error code
**See PE2 above.** Init-08's "federated aggregation result handoff" feature passes
pre-computed weights via `spec->bytes`. When it first attempts a bytes-only load, it
will receive `HU_ERR_INVALID_ARGUMENT` from the impl (not `HU_ERR_NOT_SUPPORTED`). This
affects init-08's capability-detection logic. Resolution: update impls to specifically
check `spec->bytes && !spec->path` and return `HU_ERR_NOT_SUPPORTED` (not
`INVALID_ARGUMENT`) for that specific case before the mixed-arg INVALID checks.

### CI-3 — Init-04 (on-device MLX): `apply_steering` state leak (see H1)
The new `apply_steering` vtable slot is introduced by this diff. The reset contract says
to call `(NULL, 0)` between turns. This turn-end reset is missing. Init-04 MUST add the
reset call as part of its vtable impl work, or add a shared turn-lifecycle hook, before
shipping a provider that implements `apply_steering`.

### CI-5 (MLX helper subprocess): No wire-format change required
The MLX Qwen3 helper subprocess (JSON RPC over pipes) is path-based and is not affected
by this diff. The `spec->path` is still passed through as a file path. No wire-format
change is needed to preserve parity.

## What's actually good

1. **Source-mutex contract is airtight at both layers.** The helper enforces "exactly one
   of path or bytes" via the `has_path == has_bytes` test. Each impl separately enforces
   the same constraint as a second line of defense. A direct-vtable caller can't silently
   pass both and get undefined behavior — they get INVALID_ARGUMENT at the impl.

2. **STACK downgrade-silence is now correctly illegal.** The old mlx_qwen3.h silently
   downgraded STACK to REPLACE. The new code correctly returns NOT_SUPPORTED so MoLoRA's
   dispatcher (init-02) can make an informed decision. The lora.h docstring that explains
   WHY silent downgrade is wrong ("the caller needs to know whether stacking actually
   happened to schedule the next expert correctly") is clear and actionable.

3. **`steered_prompt` memory management is correct.** The allocation at ~line 4813 is
   freed unconditionally at ~line 4883, which is BEFORE the `HU_ERR_PROVIDER_RESPONSE`
   and `err != HU_OK` return paths at ~line 4976 and ~line 5004. There is no
   `steered_prompt` leak on any turn-exit path. The `msgs[0].content` restoration before
   the free is a good defensive touch.

4. **Determinism contract is mechanically enforced where it counts.** `retry_attempt == 0`
   is a hard gate on the entire steering block. Existing agent_turn tests cannot be
   affected by the steering injection because the gate fires before any steering code
   runs on a first attempt.

5. **`cli_raw_vtable` recursion prevention is clean.** Splitting into `cli_raw_send` +
   `cli_send` + `cli_raw_vtable` avoids the `cli_send → hu_typing_send → cli_send`
   infinite loop with zero indirection overhead. The pattern is self-documenting.

6. **Annotation file (d) is accurate.** `git show 96968daf --stat` confirms the
   `src/providers/mlx_qwen3.c +547` claim exactly. The bundle decomposition is correct
   and the recommended commit message replacements are well-formed.
