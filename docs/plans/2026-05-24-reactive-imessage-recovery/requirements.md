# Reactive iMessage Recovery — Requirements

**Status:** Draft (2026-05-24)
**Owner:** TBD
**Motivation:** Seth (h-uman's owner) wants h-uman to "talk to him" via iMessage. Diagnosis on 2026-05-24 found h-uman cannot reply to ANY iMessage regardless of provider. This spec defines the recovery work, sequenced so the reactive path is verifiable end-to-end before any proactive scheduling lands.

## Goals

1. **Reactive replies work end-to-end.** Texting `+14845661687` from Seth's phone produces an actual iMessage delivered back, generated by whichever LLM provider is configured as default. Verified by Seth observing the reply on his phone, not by reading logs.

2. **Slice 1 unblocks slice 2 unblocks slice 3.** A real text → reply cycle is the prerequisite for any scheduled or event-driven outreach. Do not wire proactive paths until reactive is verified.

3. **Make the failure mode loud.** When the reply path silently returns empty content, the daemon should log enough context that a future debugging pass takes minutes, not hours. Today the only signal is `[human] empty assistant response (consecutive=1) — check MLX server, response_guard retry, and cloud fallback logs`, with no body, no model, no upstream status code.

## Non-Goals

- **Persona retraining.** The `seth-v3-fused` model is broken (catastrophic instruction-following collapse). Fixing the fine-tune is a separate M3 sprint. This spec uses a stock model or cloud provider until then.
- **Adding new providers.** OpenAI, Gemini, Anthropic, MLX are already wired. We fix what's there.
- **Changing the iMessage transport.** AX bridge works (typing indicator confirmed end-to-end on 2026-05-24). Don't touch it.
- **Slice 2 (scheduled check-ins to Seth)** and **slice 3 (event-driven outreach)**. They appear here in `tasks.md` only as downstream items; they don't ship in this spec.

## Acceptance Criteria

**AC-1: Live reactive reply works.**
Seth texts "hello" to `+14845661687` from his phone (`+18018285260`). Within 60 seconds, his phone receives an iMessage reply containing real, on-topic text (not empty, not markdown bullets, not a stock placeholder). Verified live by Seth, twice, with two different opening messages. Daemon log shows `agent turn result: err=ok response_len=<N>` where `N > 0`.

**AC-2: Reactive reply works for at least TWO providers.**
After AC-1 passes with the default provider, swap `default_provider` to a second value (any of `mlx_local`, `gemini`, `openai`, `anthropic`), restart daemon, repeat AC-1 verification. Both pass. Proves the bug surface isn't isolated to one provider's response parser.

**AC-3: agent_turn never returns `err=ok response_len=0` silently.**
When the agent turn completes with empty content, the daemon emits ONE log line at WARN level naming: provider, model, tool_calls count (if any), upstream HTTP status (if any), raw response body length. This is the diagnostic affordance the current code is missing.

**AC-4: `human agent run --once --prompt "hi"` succeeds.**
The CLI path uses the same provider stack as the daemon and produces non-empty output. Today this returns "provider authentication failed" for Gemini even though Vertex ADC is valid. Fixed.

**AC-5: Local MLX path returns extractable text from `gemma-4-31b-it-4bit` (stock).**
With `mlx_local.model = mlx-community/gemma-4-31b-it-4bit` and `mlx_local` as default_provider, AC-1 passes. The fix is either in mlx-server.py's `strip_thought_channels` (extract last non-bulleted line as reply) OR in a chat-template tweak that produces proper `<channel|>` close markers. Either fix is acceptable; the test is AC-1 with the stock model.

**AC-6: A regression test pins each bug.**
For each of the three bugs, a test exists in `tests/` that fails against the broken state and passes against the fix. The agent_turn empty-content test should NOT require a live network or LLM (use a fake provider that returns the empirically-observed empty-with-tool_call shape).

## Out of Scope (Explicit)

- Fixing the fused `seth-v3-fused` model itself — defer to M3 personalization sprint
- Adding a markdown-thinking-extractor as a permanent shipped feature (it's a band-aid)
- Web/PWA channel parity (iMessage only)
- Multi-recipient handling (single contact_id at a time)

## Risks

- **R-1: agent_turn bug may be a much larger refactor.** If the empty-response path is structural rather than a missed case, the fix could touch streaming/tool-routing/dispatcher. Mitigation: timebox investigation, escalate to architectural discussion if scope balloons past 1 sprint.
- **R-2: Provider parity might hide more bugs.** Switching providers in AC-2 could uncover provider-specific bugs that today look the same as the agent_turn issue. Mitigation: AC-3's diagnostic logging gives us evidence to triage quickly.
- **R-3: Spec scope creep into proactive.** "While we're in here" temptation. Mitigation: this spec ends at AC-6. Proactive is a separate spec.
