# The AGI Path for h-uman (2026-05-19)

> Not General Intelligence. The specific AGI-class property we're after
> is **continuous self-improvement from production experience**: every
> outbound is training data, every reaction is reinforcement, the
> classifier and persona retrain themselves on the latest data without
> human curation. After 4 weeks of texting, h-uman is measurably more
> Seth than it was at week 1.

## What "AGI" means here, specifically

| Property | LLM today | h-uman today | h-uman target |
|---|---|---|---|
| Responds to prompts | ✅ | ✅ | ✅ |
| Maintains persona | partially | ✅ (compact persona injection) | ✅ |
| Learns from feedback in-session | no (no weight update) | no | YES (tapback → preference pair → ORPO) |
| Improves across sessions | no | partial (DPO pairs, but no retrain trigger) | YES (nightly retrain on latest outcomes) |
| Knows what it doesn't know | no | no | YES (P(Seth) < 0.5 → defer or best-of-N) |
| Consolidates long-term memory | no | partial (personal_model is static) | YES (per-conversation summary → personal_model update) |
| Pursues goals across turns | no | partial (commitment store) | YES (proactive follow-up when commitment lapses) |

The five missing capabilities (rows 3-7) are the AGI-target deliverables.

## Five concrete capabilities to ship

### Capability 1 — outcome-driven self-update loop (FOUNDATION)

**The bottleneck for everything else.** Today we have:
- L5 best-of-N: works
- DPO miner: identifies inverted pairs
- ORPO trainer: runs against dpo_pairs
- Watcher: nightly cron

What's MISSING is the **production outcome stream** that feeds dpo_pairs
with real data, not just the curated example_banks.

Design:

1. **`production_outcomes` table** (new):
   ```
   id INTEGER PRIMARY KEY
   channel TEXT NOT NULL          -- "imessage" / "slack" / etc.
   target TEXT NOT NULL           -- contact ID
   prompt TEXT NOT NULL           -- incoming + context that led to this send
   chosen TEXT NOT NULL           -- the response we sent
   alternatives TEXT              -- JSON of best-of-N rejects (for DPO pairs)
   p_seth_at_send REAL            -- v2 classifier score on chosen
   send_timestamp INTEGER
   -- outcome columns (filled later as reactions arrive)
   tapback_polarity INTEGER       -- +1 = positive tapback, -1 = negative, NULL = none yet
   reply_latency_s INTEGER        -- seconds until they replied, NULL if no reply
   reply_length INTEGER           -- chars of their next message
   reply_sentiment REAL           -- future: sentiment classifier output
   user_edited INTEGER            -- 1 if user manually edited before send
   outcome_resolved_at INTEGER    -- timestamp the outcome was determined
   ```

2. **Write-side wire (`src/daemon.c` send path)**: after each iMessage
   outbound, INSERT into production_outcomes with prompt/chosen/p_seth.
   The alternatives column gets the L5 best-of-N losers (when L5 fires).

3. **Update-side wire (`src/agent/reaction_handler.c` + daemon ingest)**:
   when a tapback or reply arrives on a message_id we sent, UPDATE the
   matching production_outcomes row with the outcome columns.

4. **Reader (`scripts/production_outcomes_to_dpo.py`)**: nightly job
   reads production_outcomes, generates dpo_pairs from outcomes:
   - row with positive tapback + best-of-N alternatives → write
     (chosen=our_send, rejected=each_alt) pair, source='outcome_tapback'
   - row with negative tapback → CONSIDER excluding chosen from
     future similar prompts (a different signal, not a pair)
   - row with very long reply latency on Seth-shape message → that
     response might not be Seth-shape; mark as low-confidence pair

5. **Retrain trigger**: when production_outcomes has ≥100 resolved
   rows since last retrain, fire `human ml dpo-train` automatically.

**Effort:** ~6-8 hours C work + ~2 hours Python. The single biggest
multiplier in the plan because every other capability needs the data
this loop produces.

### Capability 2 — meta-cognitive uncertainty

When `p_seth_at_send < 0.5`, the model is producing something it can't
confidently call "Seth-shape." Today we still ship it. AGI move:

- if P(Seth) >= 0.8: ship as today
- if 0.5 <= P(Seth) < 0.8: trigger best-of-N (L5) automatically
- if P(Seth) < 0.5: defer the turn (send a clarifying question or no
  response and log for review)

This uses the classifier we already have. It's a routing layer between
agent_turn's output and the channel send.

**Effort:** ~2 hours after Capability 1 is in place.

### Capability 3 — per-conversation summary → personal_model update

After a conversation ends (no message in ≥6 hours), generate a structured
summary of facts learned about the contact, add to personal_model.

- "Casey is moving to Austin in July"
- "Morgan's manager moved a deadline causing tension on 2026-05-19"
- "Pat figured out the timezone bug in their tests"

These facts then feed back into future turns as context. The model
LITERALLY learns about people from talking to them.

**Effort:** ~4 hours. Requires LLM summarization call + facts ingestion.

### Capability 4 — commitment-based proactive follow-up

We already have a `commitment_store`. Today commitments are recorded
but not acted upon. AGI move:

- when a commitment's `due_date` is approaching (within 24h), check if
  it's still relevant (the conversation didn't resolve it)
- if relevant + still unresolved: trigger a proactive follow-up draft
  ("hey did you ever..." / "still on for...")

This is the difference between "responds when asked" and "remembers
and follows up."

**Effort:** ~4 hours.

### Capability 5 — reflexion on negative outcomes

When a sent message gets:
- a negative tapback, OR
- no reply within 6 hours when the prior reply latency was <1 hour

Trigger a reflexion step: "the response I sent didn't land. What was wrong
with it?" Output is a one-line instruction added to the persona prompt
for similar-context messages.

This is the Voyager / Reflexion paper architecture. After enough negative
samples, the persona prompt has a list of "don't do X in context Y"
rules that aren't from initial training — they're from real production
failures.

**Effort:** ~6 hours. Requires the outcome stream from Capability 1.

## Build order

```
1. Capability 1 (foundation, ~8 hours)
   └─→ unblocks Capability 2 (~2 hours)
   └─→ unblocks Capability 5 (~6 hours)
   └─→ unblocks improved nightly retrain (no extra work, just data)

2. Capability 3 (independent, ~4 hours)

3. Capability 4 (independent, ~4 hours)
```

Total: ~24 hours of focused work. Best done in 5-6 sessions of
3-5 hours each.

## The design decision the user has to make

Capability 1's `production_outcomes_to_dpo.py` weights multiple signals:
tapback polarity, reply latency, reply length, manual edits. The
**weighting** of these signals determines what h-uman optimizes for.

Different weightings produce different "Seths":

- **Tapback-dominant**: optimizes for messages people positively react
  to. Risk: trains to maximize external validation, can become
  sycophantic.
- **Latency-dominant**: optimizes for messages that get quick replies.
  Risk: trains to be inoffensive/safe, loses voice.
- **Edit-dominant**: optimizes for messages the user keeps as-is. Risk:
  needs the user to actually use a draft-edit flow consistently.
- **Composite**: combines all three with manual weights. Risk: hyper-
  parameters need tuning.

That's a real product/personality question. Each path makes h-uman
better-at-something-different.

## What this isn't

- Not "AGI" in the general-intelligence sense.
- Not a model architecture change.
- Not a Frontier-API replacement.
- Not autonomous goal-seeking beyond conversational follow-up.

What it IS: the **fully closed self-improvement loop** that the
6-month SOTA plan described in the abstract. Five rounds of
infrastructure work to get to the point where this is feasible.
Round 4 is when it starts shipping.
