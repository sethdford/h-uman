## CRITICAL (must fix before merge)

### [CRITICAL-1] huml.c: no `..` / embedded-NUL path traversal guard
**CWE-22** (Path Traversal)  
**File**: `src/providers/huml.c::huml_load_adapter` (around line 383–404)

```c
/* Current code — no traversal scan */
if (!spec->path || spec->path_len == 0 || spec->bytes)
    return HU_ERR_INVALID_ARGUMENT;
/* …then straight into: */
memcpy(path_buf, spec->path, spec->path_len);
path_buf[spec->path_len] = '\0';
hu_error_t err = hu_lora_load(alloc, path_buf, &fresh);   /* fopen() */
```

**Attack scenario**: caller supplies `spec->path = "../../../etc/shadow"` with
`spec->path_len = 19`. The `path_len >= sizeof(path_buf)` guard is the only
check; it passes. `path_buf` ends up as `"../../../etc/shadow\0"`, handed
directly to `hu_lora_load` → `fopen(path, "rb")`. The process will attempt
to open an arbitrary path relative to its CWD. If the LORA magic-byte check
fails, it returns `HU_ERR_IO` — leaking path-probing oracle. If an attacker
crafts or pre-places a file with LORA magic bytes at the traversal target,
the adapter load succeeds with attacker-controlled weight data, triggering
memory corruption in `hu_lora_create` / `fread` into float arrays.

`hu_lora_load` itself has **no path validation** (line 340 of `src/ml/lora.c`
just does `fopen(path, "rb")`). There is no test for path traversal in
`tests/test_ml.c` for the `huml_load_adapter` path.

**Contrast**: `mlx_qwen3_load_adapter` has a correct loop that rejects any
`..` pair or embedded NUL at positions `0..path_len-2`. huml has neither.

**Remediation**: copy the mlx_qwen3 scan verbatim into `huml_load_adapter`
immediately after the source-mutex guard, before the `path_len >= sizeof
(path_buf)` check. Add `test_huml_load_adapter_rejects_path_traversal` in
`tests/test_ml.c` mirroring `test_mlx_qwen3_load_adapter_rejects_path_traversal`.

### [CRITICAL-2] llamacpp.c: no `..` / embedded-NUL path traversal guard
**CWE-22** (Path Traversal)  
**File**: `src/providers/llamacpp.c::llamacpp_load_adapter` (around line 408–430)

```c
if (!spec->path || spec->path_len == 0 || spec->bytes)
    return HU_ERR_INVALID_ARGUMENT;
/* …no traversal scan, then: */
char *path_buf = alloc->alloc(alloc->ctx, spec->path_len + 1);
memcpy(path_buf, spec->path, spec->path_len);
path_buf[spec->path_len] = '\0';
struct llama_adapter_lora *adapter = llama_adapter_lora_init(c->model, path_buf);
```

**Attack scenario**: identical to CRITICAL-1. `llama_adapter_lora_init` is a
C function in the llama.cpp shared library; it performs `fopen()` internally
with no path validation. The path `"../models/stolen-weights.gguf"` would be
attempted relative to CWD. Even a failed load (wrong magic bytes) provides a
timing-based path-existence oracle.

No test for path traversal on the llamacpp provider.

**Remediation**: apply the same `..`/NUL scan before the `path_len + 1`
allocation. Add a path-traversal test in `tests/test_llamacpp_provider.c`
mirroring the mlx_qwen3 case.

## HIGH (should fix in S1.5)

### [HIGH-1] No absolute-path / `~/.human/` prefix guard in any provider
**CWE-22** (Path Traversal — absolute paths)  
**Files**: all three provider impls

The `..` guard in mlx_qwen3 (and the missing guards in huml/llamacpp) only
prevents relative traversal. An absolute path such as `/var/tmp/evil.lora`
or `/etc/cron.d/malicious` bypasses the `..` check entirely. The design
doc §891 calls for the path to be validated against `~/.human/` (expanded).
None of the three impls expand the home directory and none enforce a prefix.

**Attack scenario**: in a context where the daemon accepts adapter specs from
a partially-trusted source (e.g., init-08 IPC before the bytes path lands,
or a misconfigured config file), passing an absolute path outside the
expected adapter directory would cause the provider to attempt loading an
arbitrary file.

**Remediation**: in each provider's load path (or in the helper before
dispatch), expand `~` and verify `realpath(spec->path)` has the expected
prefix (e.g., `hu_path_within_home_dir(path_buf, ".human/")`). At minimum,
reject paths that start with `/` until the prefix check is implemented.
Create a LINEAR ticket for the full `realpath`-based prefix check (it
requires knowing the effective home directory, which the daemon should pass
in via the existing config struct).

### [HIGH-2] mlx_qwen3: free-size mismatch when `spec->id` contains embedded NUL
**CWE-131** (Incorrect Calculation of Buffer Size)  
**File**: `src/providers/mlx_qwen3.c` (deinit / replace path)

```c
/* Allocation — hu_strndup allocates id_len + 1 bytes */
char *new_id = hu_strndup(alloc, spec->id, spec->id_len);

/* Free (inside replace or deinit) — uses strlen, not id_len */
alloc->free(alloc->ctx, c->active_adapter_id,
            strlen(c->active_adapter_id) + 1);   /* ← WRONG when NUL in middle */
```

If `spec->id` contains an embedded NUL at position `k < id_len`,
`hu_strndup` allocates `id_len + 1` bytes but copies the NUL faithfully.
`strlen(c->active_adapter_id)` then returns `k`, so the `free` is called
with size `k + 1` instead of `id_len + 1`. For custom allocators that use
the size argument for slab-bucket selection or size-class validation (common
in embedded arenas, pool allocators, ASan-instrumented builds), this is a
heap-safety violation that can cause silent corruption or an assertion abort.

**Note**: the standard libc `free` ignores the size argument, so this is
benign with the default system allocator. The bug surfaces under any
non-trivial `hu_allocator_t`.

**Remediation**: change the free to use the stored length, not `strlen`.
Either store `id_len` in `mlx_qwen3_ctx_t` alongside `active_adapter_id`,
or (preferred) reject embedded NULs in `spec->id` at the provider level
(see LOW-1 below), which makes the `strlen` and `id_len` agree.

## MEDIUM (defer with explicit ticket)

### [MEDIUM-1] Provider enum accepts out-of-range `mode` values as REPLACE
**CWE-20** (Improper Input Validation)  
**Files**: all three provider impls

All three providers guard only `if (mode == HU_LORA_APPLY_MODE_STACK) return
HU_ERR_NOT_SUPPORTED`. They do not check for unknown enum values. Because
`HU_LORA_APPLY_MODE_REPLACE = 0` and the only other valid value is STACK=1,
an out-of-range value such as `mode = 99` satisfies neither check and falls
through as if it were REPLACE.

The helper (`helpers.c`) does perform:
```c
if (mode != HU_LORA_APPLY_MODE_REPLACE && mode != HU_LORA_APPLY_MODE_STACK)
    return HU_ERR_INVALID_ARGUMENT;
```
so callers going through `hu_provider_load_adapter` are protected. However,
any future caller that invokes the vtable directly (e.g., the init-02 MoLoRA
dispatcher to avoid helper overhead) would bypass this fence.

**Remediation**: add per-provider enum validation mirroring the helper's
check:
```c
if (mode != HU_LORA_APPLY_MODE_REPLACE && mode != HU_LORA_APPLY_MODE_STACK)
    return HU_ERR_INVALID_ARGUMENT;
```
before the STACK-specific check. This makes providers self-defending at
negligible cost. Create a LINEAR ticket tagged `init-02 MoLoRA pre-condition`.

### [MEDIUM-2] helpers.c: `spec->alloc` NULL check is not centralized
**CWE-476** (NULL Pointer Dereference — defense-in-depth)  
**File**: `src/providers/helpers.c::hu_provider_load_adapter`

The helper comment reads:
> "`alloc` is allowed to be NULL only when the provider docs say so; none
> in-tree do today, but we don't enforce here — providers that need it will
> fail their own validation."

All three in-tree providers do check `!spec->alloc` and return
`HU_ERR_INVALID_ARGUMENT`. However, delegating this to per-provider logic
means a future provider that forgets the check will crash rather than return
a structured error. The helper is the natural single fence for this.

**Remediation**: add `if (!spec->alloc) return HU_ERR_INVALID_ARGUMENT;`
to `hu_provider_load_adapter` and remove the hedge comment. The cost is
one pointer comparison per call.

### [MEDIUM-3] `spec->bytes_len == 0` treated inconsistently between helper and providers
**CWE-20** (Improper Input Validation — edge case)  
**Files**: `src/providers/helpers.c`, all three provider impls

The helper defines:
```c
const bool has_bytes = (spec->bytes != NULL && spec->bytes_len > 0);
```
A caller that sets `spec->bytes = some_ptr` with `spec->bytes_len = 0` is
treated by the helper as having **no bytes source** (has_bytes = false).
If `spec->path` is also set, the source-mutex passes and the call is
dispatched to the provider.

Each provider, however, checks `spec->bytes` (pointer alone, not `bytes_len`):
```c
if (!spec->path || spec->path_len == 0 || spec->bytes)   /* ← rejects non-NULL bytes */
    return HU_ERR_INVALID_ARGUMENT;
```
So the provider rejects the call. The net effect is safe (provider is more
strict than the helper) but the behavior is surprising: a caller with a
non-NULL, zero-length `bytes` pointer and a valid `path` receives
`HU_ERR_INVALID_ARGUMENT` from the provider with no indication that the
helper's source-mutex logic passed. This is a latent bug in init-08 hookup.

**Remediation**: align the helper's `has_bytes` check with the provider
check: treat any non-NULL `bytes` pointer as a bytes-source regardless of
`bytes_len`. Either reject `bytes_len == 0` explicitly, or define `has_bytes
= (spec->bytes != NULL)`. Update the lora.h comment accordingly.

## LOW / Informational

### [LOW-1] `spec->id` NUL bytes not validated; truncation causes unload-ID mismatch
**CWE-158** (Improper NUL Termination)  
**Files**: all three provider impls

No provider scans `spec->id` for embedded NUL bytes before calling
`hu_strndup`. A caller that passes `id = "persona\0evil"` with `id_len = 13`
will have the full 13 bytes stored. `active_adapter()` returns a C-string
whose `strlen` is 7 (`"persona"`). A subsequent `unload_adapter("persona\0evil",
13)` in mlx_qwen3 compares `active_len (7) != adapter_id_len (13)` → mismatch
→ the adapter cannot be unloaded via the original id, leaking it resident.

No security escalation in the current trusted-caller model, but confusing
correctness behaviour that will complicate init-08 IPC, where id values may
originate from a serialized message.

**Remediation**: in each provider (or centrally in the helper alongside the
`alloc` check), scan `spec->id[0..id_len-1]` for `'\0'` and return
`HU_ERR_INVALID_ARGUMENT` if found. This also resolves HIGH-2.

### [LOW-2] mlx_qwen3 path NUL check misses the final byte
**CWE-626** (Null Byte Interaction Error — marginal)  
**File**: `src/providers/mlx_qwen3.c::mlx_qwen3_load_adapter`

```c
for (size_t i = 0; i + 1 < spec->path_len; i++) {
    if (spec->path[i] == '.' && spec->path[i + 1] == '.')
        return HU_ERR_INVALID_ARGUMENT;
    if (spec->path[i] == '\0')
        return HU_ERR_INVALID_ARGUMENT;
}
```

The loop runs for `i` in `[0, path_len-2]`. The NUL check covers indices
`0..path_len-2`; the byte at `path_len-1` is never checked for `'\0'`.

**Impact**: practically nil — a trailing NUL just makes the effective path
one byte shorter (C-string semantics). The `..` check IS correctly applied
to the final character pair `(path[path_len-2], path[path_len-1])`, so
traversal is still blocked. The only observable effect is that
`"/home/.human/adapter\0"` (with NUL as the last byte, path_len = 22)
would pass as `"/home/.human/adapter"`. This is harmless.

**Remediation**: change the loop bound to `i < spec->path_len` and move the
`'..'` check to only fire when `i + 1 < spec->path_len`. Or simpler: add a
single `if (spec->path[spec->path_len - 1] == '\0') return
HU_ERR_INVALID_ARGUMENT;` before the loop. Apply the same fix to huml and
llamacpp once CRITICAL-1/2 are addressed.

### [LOW-3] Future init-08 `spec->alloc` vtable trust model needs explicit policy
**CWE-20** (Improper Input Validation — design note)  
**File**: `include/human/lora.h` (struct docstring)

When init-08 introduces the federated LoRA path (`spec->bytes != NULL`),
the `spec->alloc` vtable will arrive over IPC alongside attacker-influenced
data. A malicious or corrupted peer could supply a fake `alloc` struct with
crafted `alloc->alloc` / `alloc->free` function pointers, redirecting memory
operations to arbitrary code. The struct docstring acknowledges this ("always
supply it when you can") but does not document the trust boundary.

No current attack path exists because `spec->bytes` is rejected by all
providers and the spec is stack-allocated by trusted daemon code. This
becomes critical when init-08 deserializes a spec from the network.

**Remediation**: before init-08 lands, document in `lora.h` that `spec->alloc`
MUST be a locally-owned allocator (never deserialized or IPC-supplied). The
init-08 IPC protocol should deserialize `bytes` only and inject a
locally-trusted allocator, never exposing function pointer slots across the
trust boundary.

## init-08 (federated LoRA) preview

**Does this widening enable or block init-08?**

**Enables with a safe-by-default posture**: the `bytes` / `bytes_len` fields
exist in `hu_lora_adapter_spec_t` and are documented as the init-08 IPC path.
The helper's source-mutex validation and the per-provider `spec->bytes != NULL`
rejection are a correct incremental approach:

- init-08 can land without a vtable signature change — providers flip their
  individual `spec->bytes` guard when they're ready.
- The `alloc` field is already in the struct so providers can use a local
  allocator for deserializing the blob.
- The mode field is already in place for future STACK work (init-02 MoLoRA).

**Gaps init-08 must address before going live**:

1. **Trust model for `spec->alloc`** (see LOW-3): when bytes arrive over IPC,
   the alloc vtable MUST come from the daemon, not from the peer.
2. **`bytes_len` overflow**: once a provider implements the bytes path, a
   crafted `bytes_len` (e.g., `SIZE_MAX - 4`) passed to `hu_lora_create` or
   a manual malloc will overflow. Add `bytes_len > MAX_ADAPTER_BYTES` guard
   at the helper layer.
3. **HMAC provenance** (noted in `lora.h` reserved fields): federated weights
   arriving without a signature verification step are a supply-chain injection
   vector. The `signature` field placeholder in the header is the right
   direction.

Overall: the S1.5 widening is a net enabler for init-08; it does not close
the path. The safe-by-default reject is correct posture while the trust
model is unresolved.
